## 1. Загальні положення

Лабораторні роботи виконуються послідовно в межах одного наскрізного навчального бекенд-проєкту — вебзастосунку **«Менеджер завдань» (Task Manager)**. Кожна наступна лабораторна робота органічно розвиває результат попередньої: від базового процедурного виведення у розмітку до повноцінного об'єктно-орієнтованого MVC-застосунку з роботою з базою даних через PDO, автозавантаженням Composer та комплексною системою безпеки.

Для всіх робіт використовується **один спільний Git-репозиторій**, розміщений на GitHub. Створення окремих репозиторіїв або дублювання копій папок проєкту під кожну лабораторну роботу суворо заборонено.

Нумерація лабораторних робіт: **№1–16** у межах 3 семестру.

## 2. Організація репозиторію

Назва репозиторію має однозначно ідентифікувати студента та дисципліну: `php-programming-NameSurname` або `php-task-manager-NameSurname`. Ім'я та прізвище записуються латиницею, без пробілів і спеціальних символів.

Приклад: `php-programming-TarasShevchenko`

У корені репозиторію розміщуються:

- `README.md` — титульний аркуш та опис проєкту, інформація про автора, інструкція із запуску вебсервера та імпорту бази даних, стан виконання робіт;
- `.gitignore` — **обов'язковий** перелік файлів і каталогів, які не повинні потрапляти у Git (каталог `vendor/`, файл конфігурації `.env`, локальні завантаження користувачів, службові каталоги IDE `.vscode/` чи `.idea/`);
- `.env.example` — приклад конфігураційного файлу змінних оточення без реальних паролів (параметри з'єднання з БД `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASS`);
- `database/` (або `task_manager.sql`) — дамп структури бази даних MySQL та початкові тестові дані для розгортання;
- `docs/labs/` — короткі звіти до лабораторних робіт у форматі Markdown (`lab-01.md`, `lab-02.md` ... `lab-16.md`).

До репозиторію категорично **заборонено комітити**:
- паролі, секретні ключі та бойові конфігурації (`.env`);
- сторонні залежності та бібліотеки (каталог `vendor/`);
- локальні дампи з реальними даними, тимчасові файли або логи сервера.

Викладач повинен мати доступ до репозиторію (якщо репозиторій приватний, доступ надається до моменту здавання першої лабораторної роботи).

## 3. Вимоги до якості та оформлення коду

Код на PHP повинен бути безпечним, суворо типізованим, структурованим та відповідати сучасним індустріальним стандартам. Дотримання культури написання коду безпосередньо впливає на оцінку робіт.

### 3.1. Стандарти коду PHP та правила PSR-12

- **Стандарт PSR-12:** увесь код проєкту оформлюється відповідно до стандартів коду групи PHP-FIG (PSR-1 та PSR-12). Рекомендується налаштувати лінтер у VS Code (PHP Intelephense або phpcs).
- **Сувора типізація:** кожен PHP-файл з оголошенням класів або функцій обов'язково починається з директиви суворої типізації:
  ```php
  <?php

  declare(strict_types=1);
  ```
- **Відступи та синтаксис:** використовується відступ у 4 пробіли (табуляція не застосовується). Відкриваюча фігурна дужка для класів і методів переноситься на новий рядок, для керуючих конструкцій (`if`, `foreach`) залишається на тому ж рядку.
- **Правила іменування:**
  - для класів, інтерфейсів і трейтів використовується `PascalCase` (`TaskRepository`, `TaskService`, `TimestampableTrait`);
  - для методів і змінних використовується `camelCase` (`getAllTasks`, `$taskDeadline`, `$isCompleted`);
  - для констант використовується `UPPER_SNAKE_CASE` (`STATUS_PENDING`, `DEFAULT_PAGE_LIMIT`);
  - назви файлів з класами повинні суворо відповідати імені класу з розширенням `.php` (`Task.php`, `Database.php`).
- **Обов'язкова типізація (Type Hinting):** усі параметри функцій та повернені значення повинні мати явно вказані типи даних:
  ```php
  public function findById(int $id): ?Task
  ```
  Для властивостей класів використовуються типізовані властивості (Typed Properties) та лаконічне оголошення через конструктор (Constructor Property Promotion).

### 3.2. Архітектура застосунку та шаблонізація

- **Розділення відповідальностей (MVC):**
  - Моделі (`Models`, `Repositories`) відповідають лише за дані, правила валідації та роботу з базою даних;
  - Контролери (`Controllers`) приймають HTTP-запит, звертаються до сервісів чи репозиторіїв та передають результат у представлення;
  - Представлення (`Views`) відповідають виключно за генерацію HTML і не повинні містити SQL-запитів чи бізнес-розрахунків.
- **Синтаксис шаблонів:** у файлах представлень для циклів та умов використовується альтернативний синтаксис керуючих конструкцій:
  ```php
  <?php if (!empty($tasks)): ?>
      <?php foreach ($tasks as $task): ?>
          <div class="task-card"><?= htmlspecialchars($task->getTitle(), ENT_QUOTES, 'UTF-8') ?></div>
      <?php endforeach; ?>
  <?php else: ?>
      <p>Список завдань порожній.</p>
  <?php endif; ?>
  ```
  Жодних прямих `echo "<div class='task-card'>" . $row['title'] . "</div>";` у бізнес-коді.

### 3.3. Безпека вебзастосунків (Security First)

Безпека бекенду є критичним критерієм під час перевірки. Проєкт повинен бути надійно захищений від типових загроз:

- **Захист від SQL-ін'єкцій (SQL Injection):** категорично заборонено пряме склеювання (конкатенація) змінних у SQL-запити. Будь-які параметри передаються виключно через підготовлені вирази PDO (Prepared Statements):
  ```php
  // ПРАВИЛЬНО:
  $stmt = $pdo->prepare('SELECT * FROM tasks WHERE user_id = :userId AND status = :status');
  $stmt->execute(['userId' => $userId, 'status' => $status]);

  // СУВОРО ЗАБОРОНЕНО:
  $pdo->query("SELECT * FROM tasks WHERE user_id = " . $_GET['user_id']); // Вразливість SQLi!
  ```
- **Захист від XSS (Cross-Site Scripting):** будь-які дані, що надходять від користувача або з бази даних, перед виведенням у HTML-розмітку обов'язково екрануються за допомогою `htmlspecialchars($value, ENT_QUOTES, 'UTF-8')`. Рекомендується створити коротку допоміжну функцію `e($value)`.
- **Захист від CSRF (Cross-Site Request Forgery):** усі форми, що виконують зміну даних (POST-запити: створення, редагування, видалення, зміна статусу), повинні містити приховане поле з одноразовим випадковим CSRF-токеном, який звіряється зі збереженим у сесії.
- **Безпечна автентифікація та паролі:** паролі ніколи не зберігаються у відкритому вигляді чи у застарілих ненадійних хешах (`md5`, `sha1`). Для хешування використовується функція `password_hash($password, PASSWORD_BCRYPT)` (або `PASSWORD_ARGON2ID`), а для перевірки — `password_verify($password, $hash)`.
- **Безпека завантаження файлів:** завантажувані файли перевіряються на фактичний MIME-тип (а не лише розширення), генерується унікальне випадкове ім'я файлу, а каталог для завантажень налаштовується так, щоб заборонити виконання будь-яких PHP-файлів.
- **Ізоляція секретів:** конфігураційні паролі до бази даних та секретні токени зчитуються з файлу `.env` через бібліотеку `phpdotenv` і ніколи не фіксуються в репозиторії.

### 3.4. Робота з базою даних MySQL та PDO

- **Використання PDO:** робота з MySQL здійснюється виключно через бібліотеку PDO (PHP Data Objects). Використання застарілого процедурного розширення `mysqli_*` або функцій `mysql_*` неприпустимо.
- **Конфігурація PDO:** об'єкт PDO обов'язково створюється з увімкненим режимом генерації винятків та асоціативним виправленням:
  ```php
  $pdo = new PDO($dsn, $user, $pass, [
      PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
      PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
      PDO::ATTR_EMULATE_PREPARES   => false,
  ]);
  ```
- **Реляційність та цілісність:** таблиці бази даних повинні містити відповідні первинні ключі (`PRIMARY KEY`), індекси для часто запитуваних полів та зовнішні ключі (`FOREIGN KEY`) з правильними правилами каскадного оновлення або видалення.
- **Транзакції:** операції, що складаються з кількох пов'язаних змін у базі даних (наприклад, реєстрація користувача з одночасним створенням дефолтного проєкту), обов'язково обгортаються у транзакцію (`beginTransaction()`, `commit()`, `rollBack()`).

### 3.5. ООП, простори імен та автозавантаження PSR-4

- **Простори імен (Namespaces):** усі класи структуруються за просторами імен відповідно до стандарту PSR-4 (наприклад, корінь `src/` відповідає простору імен `App\`).
- **Автозавантаження Composer:** використання розрізнених викликів `require` чи `require_once` для підключення класів заборонено. Усі класи повинні завантажуватися автоматично через `vendor/autoload.php`.
- **Інкапсуляція:** усі властивості класів оголошуються як `private` або `protected`. Прямий доступ до внутрішнього стану об'єкта заборонений (використовуються методи доступу та бізнес-методи).
- **Обробка винятків (Exceptions):** потенційно небезпечні операції (з'єднання з БД, робота з файловою системою, бізнес-помилки) обробляються через блоки `try...catch`. Неприпустимо глушити помилки оператором `@`.

### 3.6. Коментарі та гігієна коду

- **PHPDoc анотації:** класи та методи документуються за допомогою блоків PHPDoc (`/** ... */`) із зазначенням описів, типів аргументів та можливих винятків (`@throws`), якщо тип неможливо виразити нативним синтаксисом PHP (наприклад, типізовані колекції `Task[]`).
- **Очищення налагоджувального виведення:** перед формуванням коміту та здаванням лабораторної роботи з коду повністю видаляються виклики `var_dump()`, `print_r()`, `die()`, `exit`, а також тимчасові тестові заглушки.
- **Відсутність "мертвого коду":** закоментований або невикористовуваний код видаляється.

## 4. Правила створення комітів

**Коміт фіксує завершену логічну зміну в проєкті.** Кожен коміт повинен бути цілісним і залишати проєкт у працездатному стані. В межах виконання однієї лабораторної роботи зазвичай створюється кілька комітів.

Повідомлення коміту повинно починатися з префікса лабораторної роботи та лаконічно описувати суть змін:

- `lab-04: створено допоміжні функції форматування дат та дедлайнів`;
- `lab-06: зверстано форму додавання завдань та реалізовано обробку POST-запиту`;
- `lab-09: реалізовано авторизацію користувачів та збереження сесії`;
- `lab-12: реалізовано клас підключення до MySQL через PDO`;
- `lab-14: рефакторинг застосунку на архітектуру MVC та Front Controller`.

Повідомлення на зразок `update`, `fix`, `commit` не дають уявлення про історію розробки і вважаються порушенням культури коду.

Перед створенням коміту перевіряється стан робочого дерева:

```bash
git status
git diff
```

Додавання файлів до індексу та створення коміту:

```bash
git add src/Controllers/TaskController.php views/tasks/create.php
git commit -m "lab-14: додано контролер та представлення створення завдання"
```

Фінальний коміт кожної роботи повинен забезпечувати повне та стабільне виконання завдання лабораторної роботи. Приклад повідомлення: `lab-12: final version`.

## 5. Робота з гілками та Pull Request

Гілка `main` містить стабільну працездатну версію бекенд-застосунку.

- **Для лабораторних робіт №1–10:** допускається вести розробку безпосередньо у гілці `main`.
- **Починаючи з лабораторної роботи №11 (поглиблене ООП та робота з базами даних):** кожна робота виконується в окремій гілці функціоналу (наприклад, `work/lab-11`, `work/lab-12`).

Порядок роботи з окремою гілкою:

1. Отримати найсвіжішу версію з `main` та створити робочу гілку:
   ```bash
   git switch main
   git pull origin main
   git switch -c work/lab-12
   ```

2. Виконати завдання, зафіксувати зміни комітами та опублікувати гілку на GitHub:
   ```bash
   git push -u origin work/lab-12
   ```

3. На GitHub створити **Pull Request із робочої гілки до `main`**. У тексті PR навести стислий опис виконаних змін та інструкцію для перевірки.

4. Після самостійної перевірки злити (Merge) Pull Request у гілку `main`. Посилання на відкритий або злитий PR обов'язково додається до матеріалів здавання роботи для перегляду викладачем повного diff-коду.

## 6. Фіксація завершеної роботи тегом

**Git-тег позначає фіксовану версію проєкту, яка подається на перевірку викладачу.** Подальший розвиток проєкту не змінює стан коду у тезі.

Для лабораторних робіт використовуються анотовані теги:
- `lab-01`, `lab-02` ... `lab-16`.

Приклад створення та публікації тегу для лабораторної №12:

```bash
git tag -a lab-12 -m "lab-12: PDO connection and database schema"
git push origin main
git push origin lab-12
```

> [!IMPORTANT]
> Звичайна команда `git push` не надсилає теги автоматично. Публікація тегу обов'язково виконується окремою командою: `git push origin <tag-name>`.

Здані теги не видаляються і не переносяться на інші коміти. Історія зданих робіт не переписується.

## 7. Оформлення короткого звіту

Для кожної лабораторної роботи створюється окремий файл звіту в каталозі `docs/labs/` (наприклад, `docs/labs/lab-12.md`).

Звіт призначений для швидкої перевірки та верифікації функціоналу без необхідності вивчати весь репозиторій з нуля.

> [!NOTE]
> **Обов'язкові пункти короткого звіту:**
>
> 1. **Номер і тема:** номер та офіційна тема лабораторної роботи.
> 2. **Перелік виконаних завдань:** короткий список фактично реалізованих класів, функцій чи механізмів.
> 3. **Інструкція запуску та налаштування:** необхідні дії для перевірки роботи (наприклад, створення нової таблиці в БД через `task_manager.sql`, генерація тестових даних або змінні в `.env`).
> 4. **Сценарій перевірки (Verification Flow):** покроковий алгоритм дій для тестування (яку сторінку відкрити, які дані ввести у форму, які записи мають з'явитися в базі даних або на екрані).
> 5. **Відомі особливості та обмеження:** якщо частина завдання реалізована альтернативним способом або вимагає особливих умов (якщо є).
> 6. **Скриншоти роботи:** скриншоти роботи вебзастосунку в браузері, повідомлень про успіх або помилок валідації, а також стан таблиць у СУБД (якщо передбачено темою).
