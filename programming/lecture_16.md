## Перелік умовних скорочень

- **Bcrypt / Argon2id** — сучасні криптографічні алгоритми одностороннього хешування паролів із регульованими витратами обчислювальних ресурсів і пам'яті;
- **CSRF** — Cross-Site Request Forgery (підробка міжсайтових запитів); вектор атаки, за якого зловмисник змушує авторизований браузер користувача виконати несанкціоновану дію;
- **DocumentRoot** — коренева публічна директорія веб-сервера (`public/`), вміст якої безпосередньо доступний зовнішнім клієнтам через HTTP;
- **Eager Loading** — техніка випереджувального завантаження зв'язаних даних для ліквідації зайвих запитів до бази даних;
- **N+1 запитів** — антипатерн взаємодії з базою даних, за якого для вибірки N сутностей виконується 1 базовий запит і N додаткових запитів у циклі;
- **Prepared Statements** — підготовлені вирази СУБД, які на фундаментальному рівні відокремлюють виконуваний SQL-код від переданих даних користувача;
- **SQLi** — SQL Injection (впровадження SQL-коду); вразливість, що дозволяє зловмиснику впроваджувати довільні SQL-команди в тіло запиту до СУБД;
- **Timing Attack** — атака за часом; техніка вилучення конфіденційних даних через вимірювання мікросекундних відмінностей часу виконання операцій порівняння;
- **XSS** — Cross-Site Scripting (міжсайтовий скриптинг); атака з впровадженням шкідливого виконуваного JavaScript-коду у веб-сторінку жертви.

## Вступ

Протягом попередніх занять наш навчальний проєкт «Менеджер завдань» пройшов шлях еволюції від процедурних скриптів до структурованої модульної системи на базі патерну MVC, автозавантаження за стандартом PSR-4 та відокремленого сервісного шару. Проте працездатність бізнес-логіки не гарантує готовності застосунку до реальної експлуатації у відкритій мережі інтернет.

Будь-який веб-ресурс одразу після публікації потрапляє під сканування автоматизованих ботів, що шукають типові вразливості: незахищені форми, відкриті системні помилки, доступні конфігураційні файли або можливість ін'єкцій. Крім того, під час реального навантаження неефективні запити до бази даних здатні миттєво паралізувати сервер.

Мета цієї лекції — перетворити працюючий функціональний прототип на захищений, стійкий до збоїв і високопродуктивний веб-застосунок. Ми опануємо сучасні криптографічні стандарти збереження паролів, збудуємо надійний захист від вразливостей з рейтингу OWASP Top 10 (SQLi, XSS, CSRF), навчимося централізовано фіксувати збої в системних журналах без витоку внутрішніх даних, ліквідуємо класичний антипатерн N+1 запитів та сформуємо системний чек-лист для безпечного розгортання проєкту на бойовому сервері.

## 1. Криптографічне хешування паролів: функції `password_hash()` та `password_verify()`

### Чому алгоритми MD5, SHA-1 та SHA-256 неприпустимі для паролів

Поширена помилка розробників-початківців — збереження паролів у відкритому вигляді або використання звичайних хеш-функцій загального призначення:

```php
// КАТЕГОРИЧНО ЗАБОРОНЕНО В СУЧАСНІЙ РОЗРОБЦІ:
$badHash = md5($userPassword);
$shaHash = hash('sha256', $userPassword);
```

Функції сімейства MD5, SHA-1 або SHA-256 створювалися для швидкої перевірки цілісності файлів і передачі повідомлень. Їхня головна перевага — **екстремальна швидкість обчислення**. Проте для збереження паролів висока швидкість є критичним недоліком:

- апаратні можливості зловмисників — сучасні графічні процесори (GPU) та спеціалізовані ASIC-чипи здатні перебирати десятки мільярдів хешів SHA-256 за одну секунду;
- райдужні таблиці (Rainbow Tables) — для стандартних хешів існують терабайтні бази даних попередньо обчислених значень, завдяки яким пошук оригінального пароля за його хешем триває кілька мілісекунд;
- неефективність «саморобної солі» — спроби додавати сіль вручну на кшталт `hash('sha256', $salt . $password)` не сповільнюють роботу графічних процесорів і не рятують при витоку вихідного коду проєкту.

### Адаптивні алгоритми хешування: Bcrypt та Argon2id

Для надійного захисту паролів застосовуються спеціальні криптографічні алгоритми формування ключа (Key Derivation Functions). Їхня ключова відмінність — **навмисна, математично контрольована повільність**:

- алгоритм Bcrypt (`PASSWORD_BCRYPT`) — базується на симетричному шифрі Blowfish; використовує параметр `cost` (робочий фактор), де кожне збільшення значення на одиницю подвоює час обчислення хешу;
- алгоритм Argon2id (`PASSWORD_ARGON2ID`) — сучасний криптографічний стандарт, переможець міжнародного конкурсу Password Hashing Competition; захищений як від перебору на GPU через вимоги до оперативної пам'яті, так і від атак за сторонніми каналами;
- автоматична сіль — криптографічна сіль генерується наново для кожного окремого хешування через системний генератор псевдовипадкових чисел і зберігається як невіддільна частина самого підсумкового рядка.

### Робота з вбудованим PHP Password Hashing API

PHP надає надійне низькорівневе API, яке повністю абстрагує генерацію солі, вибір алгоритму та порівняння хешів.

#### Створення хешу пароля через `password_hash()`

Функція `password_hash()` приймає пароль у відкритому вигляді, константу алгоритму та опціональний масив налаштувань:

```php
<?php
declare(strict_types=1);

$password = 'MySecretP@ssw0rd!2026';

// Генерація хешу за алгоритмом за замовчуванням (Bcrypt у сучасних версіях PHP)
$hash = password_hash($password, PASSWORD_DEFAULT);

echo $hash . PHP_EOL;
// Приклад результату:
// $2y$12$e8ZbzKkQ9b/3i6cZ8J2tVu4P7VvLzVjR1O5p0W9q1G6M2H8F3E.Xa
```

Анатомія згенерованого рядка хешу:
- ідентифікатор алгоритму — префікс `$2y$` вказує на алгоритм Bcrypt;
- робочий фактор (cost) — число `$12$` означає $2^{12} = 4096$ ітерацій внутрішнього циклу;
- криптографічна сіль — наступні 22 символи містять унікальну випадкову сіль;
- контрольний хеш — решта 31 символ містить результат обчислення.

За потреби можна вручну керувати складністю або використовувати Argon2id:

```php
// Збільшення складності Bcrypt (за замовчуванням 10 або 12):
$options = ['cost' => 13];
$hashBcrypt = password_hash($password, PASSWORD_BCRYPT, $options);

// Використання Argon2id (якщо модуль скомпільовано в PHP):
if (defined('PASSWORD_ARGON2ID')) {
    $argonHash = password_hash($password, PASSWORD_ARGON2ID, [
        'memory_cost' => 65536, // 64 МБ оперативної пам'яті
        'time_cost'   => 4,     // 4 ітерації обчислень
        'threads'     => 2,     // 2 паралельні потоки
    ]);
}
```

#### Перевірка пароля через `password_verify()`

Для перевірки автентичності ніколи не можна самостійно хешувати введений пароль і порівнювати рядки через `==` або `===`. Необхідно викликати `password_verify()`:

```php
<?php
declare(strict_types=1);

$userEnteredPassword = $_POST['password'] ?? '';
$hashFromDatabase = '$2y$12$e8ZbzKkQ9b/3i6cZ8J2tVu...';

if (password_verify($userEnteredPassword, $hashFromDatabase)) {
    // Пароль валідний — автентифікація успішна
} else {
    // Пароль невірний
}
```

Функція `password_verify()` самостійно зчитує алгоритм, фактор вартості та сіль безпосередньо з рядка `$hashFromDatabase`, обчислює новий хеш на їхній основі та виконує побайтове порівняння, гарантовано захищене від атак за часом.

#### Автоматичне оновлення хешів через `password_needs_rehash()`

З ростом продуктивності серверів старі фактори складності стають занадто швидкими. Функція `password_needs_rehash()` дозволяє непомітно для користувача оновити його хеш у момент входу:

```php
<?php
declare(strict_types=1);

namespace App\Services;

use App\Repositories\UserRepository;

class AuthService
{
    public function __construct(private UserRepository $userRepository) {}

    public function login(string $email, string $password): bool
    {
        $user = $this->userRepository->findByEmail($email);
        if ($user === null) {
            return false;
        }

        if (!password_verify($password, $user->getPasswordHash())) {
            return false;
        }

        // Перевіряємо, чи не застарів хеш (наприклад, змінили cost з 10 на 12)
        $targetOptions = ['cost' => 12];
        if (password_needs_rehash($user->getPasswordHash(), PASSWORD_DEFAULT, $targetOptions)) {
            $newHash = password_hash($password, PASSWORD_DEFAULT, $targetOptions);
            $this->userRepository->updatePasswordHash($user->getId(), $newHash);
        }

        $_SESSION['user_id'] = $user->getId();
        return true;
    }
}
```

## 2. Захист від основних веб-загроз: SQLi, XSS та CSRF

### 2.1. SQL Injection (SQLi)

Вразливість виникає тоді, коли неперевірені дані від користувача підставляються безпосередньо в текст SQL-запиту за допомогою конкатенації рядків.

#### Приклад вразливого коду

```php
// НЕБЕЗПЕЧНО: Пряма інтерполяція введених даних у рядок запиту
$email = $_POST['email'];
$query = "SELECT * FROM users WHERE email = '$email'";
$stmt = $pdo->query($query);
```

Якщо зловмисник введе у поле пошти значення `' OR '1'='1' -- `, кінцевий запит отримає вигляд:

```sql
SELECT * FROM users WHERE email = '' OR '1'='1' -- '
```

У результаті умова `'1'='1'` виконається для кожного рядка таблиці, а коментар `--` відкине залишок запиту, відкривши зловмиснику несанкціонований доступ до першого запису в базі (зазвичай облікового запису адміністратора).

#### Єдине надійне рішення: Підготовлені вирази (Prepared Statements)

Функції екранування рядків (на кшталт `addslashes` чи ручної заміни лапок) є вразливими через особливості багатобайтових кодувань. Єдиним стандартом захисту є використання **параметризованих підготовлених виразів**:

```php
<?php
declare(strict_types=1);

namespace App\Repositories;

use PDO;
use App\Models\User;

class UserRepository
{
    public function __construct(private PDO $pdo) {}

    public function findByEmail(string $email): ?User
    {
        // 1. СУБД компілює структуру запиту з плейсхолдером :email
        $stmt = $this->pdo->prepare('SELECT * FROM users WHERE email = :email LIMIT 1');
        
        // 2. Дані передаються окремим потоком і ніколи не виконуються як код
        $stmt->execute(['email' => $email]);
        
        $data = $stmt->fetch();
        return $data ? User::fromArray($data) : null;
    }
}
```

Критично важливе налаштування PDO для відключення емуляції підготовки на стороні клієнта:

```php
$options = [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    PDO::ATTR_EMULATE_PREPARES   => false, // Використовувати нативні підготовлені вирази СУБД
];
$pdo = new PDO($dsn, $user, $pass, $options);
```

### 2.2. Cross-Site Scripting (XSS)

XSS — це атака, під час якої зловмисник впроваджує шкідливий JavaScript-код на сторінки веб-застосунку. Цей скрипт згодом виконується в браузерах інших користувачів або адміністратора.

Класифікація XSS-атак:
- збережений (Stored / Persistent XSS) — шкідливий скрипт зберігається у базі даних (наприклад, у назві завдання або коментарі) та відображається всім відвідувачам сторінки;
- відображений (Reflected XSS) — скрипт передається через параметри URL і негайно повертається сервером у відповіді (наприклад, у рядку результатів пошуку);
- на основі DOM (DOM-based XSS) — атака виконується виключно на стороні клієнта через небезпечні маніпуляції зі скриптами `innerHTML` або `eval()`.

Наслідки виконання стороннього JS: викрадення токенів авторизації, підміна вмісту сторінки (Deface), перехоплення натискань клавіш (Keylogging) або виконання дій від імені користувача.

#### Правило захисту: Контекстне екранування виведення

Фундаментальне правило: **дані у базу даних слід зберігати в оригінальному вигляді, а екранувати — безпосередньо в момент виведення в HTML-шаблон**.

Для екранування виведення у нативних шаблонах PHP застосовується функція `htmlspecialchars()`:

```php
<?= htmlspecialchars($task->getTitle(), ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8') ?>
```

Значення прапорців:
- прапорець `ENT_QUOTES` — замінює як подвійні (`"`), так і одинарні (`'`) лапки на відповідні HTML-сутності (`&quot;`, `&#039;`), що запобігає виходу за межі атрибутів тегів;
- прапорець `ENT_SUBSTITUTE` — замінює пошкоджені або некоректні послідовності байтів символом заміни `U+FFFD`, запобігаючи зламу кодування;
- кодування `'UTF-8'` — чітко декларує таблицю символів.

Для зручності у проєкті створюють глобальну допоміжну функцію або статичний метод помічника:

```php
<?php
// src/helpers.php
declare(strict_types=1);

if (!function_exists('e')) {
    function e(?string $value): string
    {
        return htmlspecialchars((string)$value, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');
    }
}
```

Використання у представленнях:

```php
<!-- views/tasks/index.php -->
<div class="task-card">
    <h3><?= e($task->getTitle()) ?></h3>
    <p><?= e($task->getDescription()) ?></p>
</div>
```

### 2.3. Cross-Site Request Forgery (CSRF)

CSRF — це атака, яка змушує авторизований браузер користувача виконати небажану дію на довіреному сайті без відома самого користувача.

#### Як працює атака CSRF

Механіка взаємодії:
- користувач авторизувався — студент увійшов до системи «Менеджер завдань», і сервер встановив йому сесійну cookie `PHPSESSID`;
- перехід на небезпечний ресурс — не закриваючи сесію, користувач переходить за посиланням на шкідливий сайт у сусідній вкладці браузера;
- виконання запиту — на шкідливому сайті розміщено приховану форму або скрипт, який автоматично відправляє запит на зміну пароля чи видалення завдання:

```html
<!-- Сторонній шкідливий сайт evil.com -->
<form id="attackForm" action="https://my-tasks.local/tasks/delete" method="POST">
    <input type="hidden" name="id" value="42">
</form>
<script>document.getElementById('attackForm').submit();</script>
```

Оскільки запит спрямовано на домен `my-tasks.local`, браузер користувача **автоматично прикріплює валідні сесійні cookies**. Сервер перевіряє сесію, підтверджує авторизацію користувача і видаляє завдання.

#### Рішення: Synchronizer Token Pattern (CSRF-токени)

Суть захисту полягає у додаванні до кожної форми одноразового, непередбачуваного секретного значення (токена), яке відоме лише серверу та легітимній сторінці форми:

- генерація токена — сервер генерує випадковий рядок високої ентропії та зберігає його у сесії користувача;
- вставка у форму — сервер додає цей токен у приховане поле форми;
- валідація — при отриманні запиту сервер звіряє токен із форми зі значенням із сесії;
- сторонній сайт не може підробити запит — зловмисник не знає вмісту сесії жертви і згідно з політикою Same-Origin Policy не може прочитати токен з іншого домену.

#### Реалізація `CsrfHelper`

```php
<?php
declare(strict_types=1);

namespace App\Security;

class CsrfHelper
{
    private const SESSION_KEY = '_csrf_token';

    public static function getToken(): string
    {
        if (session_status() !== PHP_SESSION_ACTIVE) {
            session_start();
        }

        if (empty($_SESSION[self::SESSION_KEY])) {
            // Генерація 32 криптографічно безпечних випадкових байтів у шістнадцятковому форматі
            $_SESSION[self::SESSION_KEY] = bin2hex(random_bytes(32));
        }

        return $_SESSION[self::SESSION_KEY];
    }

    public static function validate(?string $token): bool
    {
        if (session_status() !== PHP_SESSION_ACTIVE) {
            session_start();
        }

        $sessionToken = $_SESSION[self::SESSION_KEY] ?? null;

        if (!$sessionToken || !$token) {
            return false;
        }

        // КРИТИЧНО: порівняння через hash_equals для захисту від Timing Attacks
        return hash_equals($sessionToken, $token);
    }
}
```

> [!IMPORTANT]
> Для порівняння токенів та хешів завжди використовуйте функцію `hash_equals()`. Звичайний оператор `===` припиняє порівняння на першому незбіглому символі, що дає зловмиснику змогу підібрати токен за мікросекундними різницями у часі відповіді сервера. Функція `hash_equals()` завжди виконується за сталий час.

Вбудовування токена в HTML-форму:

```php

<form action="/tasks" method="POST">
    <input type="hidden" name="_csrf_token" value="<?= e(\App\Security\CsrfHelper::getToken()) ?>">
    
    <label for="title">Назва завдання:</label>
    <input type="text" id="title" name="title" required>
    
    <button type="submit">Створити</button>
</form>
```

Валідація у контролері або middleware:


## 3. Безпека сесій, автентифікації та захисні HTTP-заголовки

### Безпечна конфігурація cookies сесії

Сесійні cookies є ключем доступу до облікового запису користувача. Їхня некоректна конфігурація зводить нанівець усі інші засоби безпеки. Налаштування параметрів слід виконувати **до виклику** `session_start()`:

```php
<?php
// public/index.php
declare(strict_types=1);

$isProduction = ($_ENV['APP_ENV'] ?? 'production') === 'production';

session_set_cookie_params([
    'lifetime' => 86400,            // Час життя cookie (1 доба)
    'path'     => '/',                // Доступність на всіх шляхах сайту
    'domain'   => '',                 // За замовчуванням поточний хост
    'secure'   => $isProduction,      // Передача виключно через HTTPS
    'httponly' => true,               // Заборона читання cookie через JS (захист від викрадення через XSS)
    'samesite' => 'Lax',              // Захист від відправки cookie при сторонніх міжсайтових POST-запитах
]);

session_start();
```

Значення атрибутів:
- атрибут `HttpOnly: true` — JavaScript (`document.cookie`) не має доступу до сесійної cookie, тому навіть у разі наявності XSS зловмисник не зможе викрасти ідентифікатор сесії;
- атрибут `Secure: true` — браузер відправляє cookie виключно зашифрованим протоколом HTTPS, блокуючи перехоплення у незахищених Wi-Fi мережах;
- атрибут `SameSite: 'Lax'` — дозволяє надсилання cookie лише за умови прямого переходу за посиланням з іншого ресурсу, блокуючи сторонні міжсайтові форми (додатковий рубіж проти CSRF).

### Захист від фіксації сесії (Session Fixation)

Атака фіксації полягає в тому, що зловмисник змушує жертву авторизуватися заздалегідь відомим зловмиснику ідентифікатором сесії.

Щоб запобігти цьому, **у момент кожної успішної зміни прав доступу (вхід, вихід, зміна ролі)** необхідно обов'язково викликати функцію регенерації ідентифікатора сесії:

```php
// Після успішної перевірки пароля:
session_regenerate_id(true);
$_SESSION['user_id'] = $user->getId();
```

Параметр `true` змушує PHP видалити старий файл сесії на диску, унеможливлюючи його подальше використання.

### Комплексні HTTP-заголовки безпеки (Security Headers)

Заголовки безпеки передаються сервером клієнту та активують вбудовані захисні механізми сучасних браузерів:

```php
<?php
// public/index.php

// 1. Захист від Clickjacking (заборона вбудовування сайту в чужі <iframe>)
header('X-Frame-Options: DENY');

// 2. Блокування підміни типів файлів (MIME-type Sniffing)
header('X-Content-Type-Options: nosniff');

// 3. Політика реферера (не передавати повну URL із чутливими query-параметрами)
header('Referrer-Policy: strict-origin-when-cross-origin');

// 4. Content Security Policy (суворе обмеження джерел скриптів та стилів)
header("Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com;");

// 5. Примусовий перехід на HTTPS (активувати лише при наявному SSL-сертифікаті)
if ($isProduction) {
    header('Strict-Transport-Security: max-age=31536000; includeSubDomains');
}
```

## 4. Налагодження та логування: конфігурація, помилки та журнал подій

### Відмінність режимів Development та Production

Показ детальних повідомлень про помилки корисний під час розробки, але стає катастрофічним у виробничому середовищі:

```
// Приклад небезпечного витоку інформації на екрані користувача:
Fatal error: Uncaught PDOException: SQLSTATE[HY000] [2002] Access denied for user 
'db_user'@'localhost' (using password: YES) in /var/www/tasks/src/Database.php:14
Stack trace: ...
```

Такий вивід розкриває зловмиснику повні шляхи до файлів на сервері, логіни до баз даних, назви таблиць та версії встановленого програмного забезпечення (Information Disclosure).

Конфігурація середовища в залежності від оточення:

```php
<?php
// config/bootstrap.php
declare(strict_types=1);

$environment = $_ENV['APP_ENV'] ?? 'production';

if ($environment === 'development') {
    // Режим розробки: бачимо всі помилки безпосередньо на екрані
    ini_set('display_errors', '1');
    ini_set('display_startup_errors', '1');
    error_reporting(E_ALL);
} else {
    // Бойовий режим: жодної технічної інформації назовні!
    ini_set('display_errors', '0');
    ini_set('display_startup_errors', '0');
    ini_set('log_errors', '1');
    ini_set('error_log', __DIR__ . '/../storage/logs/php_errors.log');
    error_reporting(E_ALL);
}
```

### Централізований клас логування (Logger)

Замість безсистемних викликів `error_log()` професійний веб-застосунок має вести структурований журнал подій із рівнями критичності згідно зі стандартом PSR-3 (DEBUG, INFO, WARNING, ERROR, CRITICAL).

Реалізація власного логера:

```php
<?php
declare(strict_types=1);

namespace App\Core;

class Logger
{
    public function __construct(private string $logFilePath)
    {
        $dir = dirname($this->logFilePath);
        if (!is_dir($dir)) {
            mkdir($dir, 0755, true);
        }
    }

    public function info(string $message, array $context = []): void
    {
        $this->log('INFO', $message, $context);
    }

    public function warning(string $message, array $context = []): void
    {
        $this->log('WARNING', $message, $context);
    }

    public function error(string $message, array $context = []): void
    {
        $this->log('ERROR', $message, $context);
    }

    private function log(string $level, string $message, array $context = []): void
    {
        $timestamp = date('Y-m-d H:i:s');
        $contextString = !empty($context) ? ' ' . json_encode($context, JSON_UNESCAPED_UNICODE) : '';
        $formattedEntry = sprintf("[%s] [%s] %s%s%s", $timestamp, $level, $message, $contextString, PHP_EOL);

        file_put_contents($this->logFilePath, $formattedEntry, FILE_APPEND | LOCK_EX);
    }
}
```

### Глобальне перехоплення помилок та винятків

Для перехоплення фатальних збоїв у точку входу `public/index.php` додають глобальні обробники:

```php
<?php
// Реєстрація обробників
$logger = new \App\Core\Logger(__DIR__ . '/../storage/logs/app.log');

// Конвертація класичних попереджень PHP у винятки ErrorException
set_error_handler(function (int $severity, string $message, string $file, int $line) {
    if (!(error_reporting() & $severity)) {
        return false;
    }
    throw new \ErrorException($message, 0, $severity, $file, $line);
});

// Перехоплення всіх незловлених винятків
set_exception_handler(function (\Throwable $exception) use ($logger) {
    $logger->error($exception->getMessage(), [
        'file'  => $exception->getFile(),
        'line'  => $exception->getLine(),
        'trace' => $exception->getTraceAsString(),
    ]);

    http_response_code(500);
    
    if (($_ENV['APP_ENV'] ?? 'production') === 'development') {
        echo '<h1>Помилка сервера</h1><p>' . e($exception->getMessage()) . '</p>';
        echo '<pre>' . e($exception->getTraceAsString()) . '</pre>';
    } else {
        // Користувач бачить нейтральне повідомлення без конфіденційних деталей
        echo '<h1>500 — Внутрішня помилка сервера</h1>';
        echo '<p>Вибачте, сталася непередбачена помилка. Наші адміністратори вже повідомлені.</p>';
    }
});
```

## 5. Профілювання та продуктивність: проблема N+1 запитів

### Суть та небезпека проблеми N+1

Проблема N+1 виникає тоді, коли застосунок робить один базовий запит для отримання списку із $N$ сутностей, а потім у циклі для кожного окремого елемента відправляє ще один додатковий запит до бази для отримання зв'язаних даних.

Розглянемо антипатерн на прикладі списку завдань та їхніх виконавців:

```php
// НЕЕФЕКТИВНИЙ КОД:
// Запит 1: Отримання списку 100 завдань
$tasks = $taskRepository->findAll(); 

foreach ($tasks as $task) {
    // Запити 2..101: Для КОЖНОГО завдання окремо йдемо в базу за користувачем!
    $user = $userRepository->findById($task->getUserId());
    echo e($task->getTitle()) . ' — Виконавець: ' . e($user->getName()) . '<br>';
}
```

Чому це критично:
- кількість запитів — для відображення всього 100 завдань виконується $1 + 100 = 101$ запит до СУБД;
- затримка мережі (Network Latency) — кожен окремий запит вимагає мережевого обміну та очікування відповіді від бази;
- вичерпання ресурсів — пул з'єднань із базою даних швидко переповнюється, і сайт перестає відповідати навіть при незначному напливі користувачів.

### Спосіб вирішення 1: Об'єднання вибірок через SQL `JOIN`

Найбільш ефективне вирішення для зв'язків типу «багато до одного» (N:1) — об'єднати обидві таблиці в один SQL-запит на стороні бази:

```sql
SELECT 
    t.id, 
    t.title, 
    t.is_completed, 
    t.deadline, 
    t.user_id,
    u.name AS user_name,
    u.email AS user_email
FROM tasks t
LEFT JOIN users u ON t.user_id = u.id
ORDER BY t.created_at DESC;
```

Реалізація в репозиторії `TaskRepository`:

```php
<?php
declare(strict_types=1);

namespace App\Repositories;

use PDO;

class TaskRepository
{
    public function __construct(private PDO $pdo) {}

    public function findAllWithUsers(): array
    {
        $sql = '
            SELECT 
                t.*,
                u.name AS user_name,
                u.email AS user_email
            FROM tasks t
            LEFT JOIN users u ON t.user_id = u.id
            ORDER BY t.created_at DESC
        ';

        // Замість 101 запиту виконується РІВНО 1 ЗАПИТ!
        $stmt = $this->pdo->query($sql);
        return $stmt->fetchAll();
    }
}
```

### Спосіб вирішення 2: Пакетне завантаження (Eager Loading через `IN`)

Якщо зв'язок є типом «один до багатьох» (1:N, наприклад одне завдання має багато підзавдань або тегів), використання одного `JOIN` може продублювати основні рядки. У цьому разі застосовують пакетне завантаження у **два запити**:

```php
// Запит 1: Отримуємо всі завдання
$tasks = $taskRepository->findAll();
$taskIds = array_map(fn($task) => $task->getId(), $tasks);

if (!empty($taskIds)) {
    // Створюємо плейсхолдери (?, ?, ?) за кількістю ID
    $placeholders = implode(',', array_fill(0, count($taskIds), '?'));
    
    // Запит 2: Вибираємо ВСІ теги для ВСІХ завдань одночасно
    $sql = "SELECT * FROM task_tags WHERE task_id IN ($placeholders)";
    $stmt = $pdo->prepare($sql);
    $stmt->execute($taskIds);
    $allTags = $stmt->fetchAll();
    
    // Групуємо теги за task_id в оперативній пам'яті PHP
    $tagsByTaskId = [];
    foreach ($allTags as $tag) {
        $tagsByTaskId[$tag['task_id']][] = $tag;
    }
}
```

Загальна кількість запитів знизилася з $N + 1$ до **сталих 2 запитів** незалежно від кількості завдань.

### Індексація бази даних

Виконання `JOIN` та вибірок `WHERE` без належних індексів спричиняє повне сканування таблиці (Full Table Scan). Для максимальної швидкодії додають індекси на всі зовнішні ключі та поля сортування:

```sql
-- Індекс на зовнішній ключ зв'язку
ALTER TABLE tasks ADD INDEX idx_tasks_user_id (user_id);

-- Складений індекс для фільтрації за користувачем і статусом виконання
ALTER TABLE tasks ADD INDEX idx_tasks_user_status (user_id, is_completed);
```

## 6. Фіналізація та чек-лист підготовки проєкту до деплойменту

### Чек-лист готовності до продакшену (Production Readiness Checklist)

Перед вивантаженням коду на бойовий сервер необхідно послідовно верифікувати кожен рівень архітектури застосунку.

#### 1. Безпека оточення та файлової системи

Вимоги до ізоляції та конфігурації:
- ізоляція DocumentRoot — корінь веб-сервера (Nginx/Apache) вказує строго на директорію `public/`; каталоги `src/`, `vendor/`, `config/`, `.env` та файли бази даних категорично недоступні через прямий веб-запит;
- конфігурація `.env` — файл `.env` внесено до `.gitignore` і він не потрапляє у репозиторій; на сервері створено окремий бойовий конфіг із надійними паролями та значеннями `APP_ENV=production` і `APP_DEBUG=false`;
- права доступу до файлів — для файлів встановлюються права `644`, для каталогів — `755`; права на запис надаються виключно каталогам журналів і кешу (`storage/logs/`, `storage/cache/`) для користувача веб-сервера (`www-data`).

#### 2. Оптимізація Composer та автозавантаження

У бойовому оточенні неприпустимо завантажувати бібліотеки для тестування (PHPUnit тощо) та динамічно сканувати директорії диска під час кожного виклику класів:

```bash
# Встановлення лише бойових залежностей із оптимізованою картою класів
composer install --no-dev --optimize-autoloader --classmap-authoritative
```

Прапорці:
- `--no-dev` — виключає пакети з секції `require-dev` (тести, відлагоджувачі);
- `--optimize-autoloader` — конвертує правила PSR-4 у статичну асоціативну карту класів `classmap`, що прискорює пошук файлів на диску;
- `--classmap-authoritative` — забороняє Composer шукати файл на диску, якщо його немає в згенерованій карті, прискорюючи виконання та захищаючи від підміни класів.

#### 3. База даних та міграції

Вимоги до налаштування бази даних:
- окремий користувач СУБД — веб-застосунок підключається під обліковим записом із мінімально необхідними привілеями (`SELECT`, `INSERT`, `UPDATE`, `DELETE`), без прав `DROP TABLE` чи доступу до системної схеми `mysql`;
- актуальний стан схеми — виконано всі скрипти міграцій або створення таблиць із необхідними первинними та зовнішніми ключами й індексами;
- підтримка UTF-8 — встановлено повноцінне кодування `utf8mb4` та зіставлення `utf8mb4_unicode_ci` для коректної обробки емодзі та спецсимволів.

#### 4. HTTPS та мережевий захист

Вимоги до транспортного рівня:
- обов'язкове використання SSL/TLS — встановлено дійсний сертифікат безпеки (наприклад, безкоштовний Let's Encrypt через Certbot);
- автоматичне перенаправлення — усі вхідні з'єднання за протоколом HTTP безумовно перенаправляються на захищений протокол HTTPS (код відповіді 301);
- налаштування заголовка HSTS — сервер інструктує клієнтські браузери завжди використовувати виключно шифроване з'єднання.

## Висновки

- криптографічне хешування паролів — функції `password_hash()` та `password_verify()` з сучасними алгоритмами Bcrypt або Argon2id формують надійний захист паролів завдяки регульованій складності обчислень і автоматичній випадковій солі;
- захист від ін'єкцій SQL — використання параметризованих підготовлених виразів (Prepared Statements) у PDO є безальтернативним стандартом взаємодії з базою даних, що надійно розмежовує команди та призначені для запису дані;
- знешкодження міжсайтового скриптингу (XSS) — контекстне екранування виведення даних за допомогою функції `htmlspecialchars()` із прапорцями `ENT_QUOTES | ENT_SUBSTITUTE` усуває загрозу несанкціонованого виконання стороннього JavaScript;
- запобігання підробці запитів (CSRF) — генерація криптографічно стійких одноразових токенів для всіх мутуючих запитів (POST/PUT/DELETE) та їхнє обов'язкове порівняння через функцію `hash_equals()` захищає користувача від прихованих міжсайтових дій;
- безпека сесій та захисні заголовки — директиви `HttpOnly`, `Secure` та `SameSite` у конфігурації сесійних cookies разом із заголовками `X-Frame-Options` і CSP мінімізують імовірність перехоплення або компрометації облікових записів;
- логування замість відображення помилок — категоричне вимкнення відображення повідомлень на бойовому сервері (`display_errors = Off`) на користь централізованого запису в захищений журнал подій запобігає витоку критичної системної інформації;
- оптимізація продуктивності бази даних — ліквідація проблеми N+1 запитів шляхом переходу до SQL `JOIN` або пакетних вибірок `WHERE IN` багаторазово знижує навантаження на сервер і прискорює час генерації сторінок;
- дисципліна виробничого розгортання — ізоляція кореня веб-сервера в каталозі `public/`, зберігання секретів поза репозиторієм у файлі `.env` та оптимізація автозавантажувача Composer забезпечують надійну, безпечну та продуктивну роботу фінального продукту.

## Запитання для самоперевірки

1. Чому використання хеш-функцій загального призначення (MD5, SHA-256) є неприпустимим для збереження паролів, і як алгоритми Bcrypt та Argon2id вирішують проблему апаратного перебору на GPU?
2. Як працює функція `password_verify()`, чому для перевірки хешу не потрібне окреме збереження солі у базі даних, та яку роль відіграє функція `password_needs_rehash()`?
3. Поясніть механізм виникнення вразливості SQL Injection. Чому підготовлені вирази (Prepared Statements) у PDO повністю нівелюють цю загрозу, на відміну від простого ручного екранування рядків?
4. У чому полягає відмінність між збереженим (Stored) та відображеним (Reflected) XSS? Які аргументи функції `htmlspecialchars()` є обов'язковими для надійного знешкодження небезпечних символів?
5. Опишіть життєвий цикл CSRF-атаки на зміну пароля або створення завдання. Як алгоритм Synchronizer Token Pattern запобігає цій атаці, і чому порівняння токенів слід здійснювати саме через `hash_equals()`?
6. Що таке проблема N+1 запитів при роботі зі зв'язаними сутностями у реляційній базі даних? Наведіть приклад її вирішення за допомогою SQL `JOIN` та пакетного завантаження.
7. Чому на продакшен-сервері директива `display_errors` повинна мати значення `Off`, а `log_errors` — `On`? Які ризики несе публікація файлів `.env` та каталогу `vendor/` у публічному доступі веб-сервера?
