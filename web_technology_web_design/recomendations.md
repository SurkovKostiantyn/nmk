## 1. Загальні положення

Лабораторні роботи виконуються послідовно в межах одного наскрізного вебпроєкту. Кожна наступна робота розвиває результат попередньої.

Для всіх робіт використовується **один Git-репозиторій**, розміщений на GitHub. Окремі репозиторії або папки з повними копіями проєкту для кожної лабораторної роботи не створюються.

Нумерація робіт є наскрізною: **№1–16 у першому семестрі та №17–32 у другому**.

## 2. Організація репозиторію

Назва репозиторію має дозволяти ідентифікувати студента та дисципліну, наприклад: `web-technologies-NameSurname`. Ім'я має бути латиницею, без пробілів та спеціальних символів.

Приклад: `web-technologies-TarasShevchenko`

У репозиторії у файлі `README.md` має бути інформація про автора: ім'я, прізвище, група.

Файли проєкту розподіляються за призначенням: HTML-сторінки, стилі, сценарії, зображення, дані та документація. Структура може змінюватися в процесі навчання відповідно до вимог лабораторних робіт.

У корені репозиторію розміщуються:

- `README.md` — опис проєкту, інформація про автора, інструкція запуску та посилання на опублікований сайт;
- `.gitignore` — **обов'язковий** перелік файлів і папок, які не потрібно додавати до Git;
- `docs/labs/` — короткі звіти до лабораторних робіт у форматі Markdown (`.md`), наприклад `lab-01.md`, `lab-02.md` тощо.

До репозиторію не додаються паролі, секретні ключі, папка `node_modules` та інші локальні файли, які не потрібні для відтворення проєкту.

Викладач повинен мати доступ до репозиторію. Якщо він приватний, доступ надається до здавання першої роботи.

### 2.1. Зразок оформлення титульного аркуша (README.md проєкту)

Файл `README.md` у корені репозиторію відіграє роль титульного аркуша та візитівки проєкту. Нижче наведено рекомендований зразок розмітки:

## 3. Вимоги до якості та оформлення коду

Код повинен бути чистим, структурованим і легким для читання. Дотримання культури коду є обов'язковою вимогою та оцінюється під час перевірки.

### 3.1. Форматування та іменування

- **Єдині відступи:** використовується фіксований відступ у 2 або 4 пробіли (табуляція не змішується з пробілами). Рекомендується налаштувати автоматичне форматування при збереженні (Format on Save) у VS Code або використовувати розширення Prettier.
- **Іменування:** назви файлів, папок, класів, змінних і функцій пишуться виключно латиницею:
  - для файлів, папок і CSS-класів використовується `kebab-case` (`product-card`, `filter-panel.css`, `site-header`);
  - для змінних і функцій у JavaScript використовується `camelCase` (`loadProducts`, `isFormValid`, `userList`);
  - для констант глобальних налаштувань використовується `UPPER_SNAKE_CASE` (`DEFAULT_PAGE_SIZE`, `API_BASE_URL`).
- **Змістовність:** назви повинні відображати суть сутності, а не її зовнішній вигляд (наприклад, `.badge-warning` замість `.yellow-text`, `calculateTotal()` замість `calc()`). Заборонено використовувати скорочення типу `a1`, `block2`, `temp`.

### 3.2. Розмітка та семантика (HTML)

- **Семантичні теги:** структура сторінки будується на основі змістових тегів (`<header>`, `<nav>`, `<main>`, `<article>`, `<section>`, `<footer>`) замість бездумного вкладення беззмістовних контейнерів `<div>` («div-soup»).
- **Обов'язкові атрибути:** сторінка повинна містити коректний `<!DOCTYPE html>`, атрибут `lang="uk"`, метатеги `charset="UTF-8"` та `viewport`.
- **Доступність (a11y):** усі інформативні зображення обов'язково мають описовий атрибут `alt`, поля форм зв'язуються з відповідними підписами `<label>` через `for` та `id`, а кнопки створюються тегом `<button>`, а не `<div>` чи `<a>` без дійсного посилання.

### 3.3. Організація стилів (CSS)

- **Розділення відповідальності:** усі стилі виносяться в окремі `.css` файли. Використання інлайн-стилів в атрибутах `style="..."` заборонено (за винятком випадків, коли значення обчислюється динамічно в JavaScript).
- **CSS-змінні:** кольори палітри, базові відступи, радіуси та шрифти виносяться у змінні в блоці `:root` для забезпечення єдиної дизайн-системи.
- **Уникнення `!important`:** заборонено використовувати директиву `!important` для виправлення проблем зі специфічністю селекторів. Специфічність регулюється правильною структурою класів.

### 3.4. Стандарти коду JavaScript

- **Оголошення змінних:** використовуються лише `const` (за замовчуванням) та `let` (якщо значення дійсно переприсвоюється). Використання застарілого `var` заборонено.
- **Суворе порівняння:** для перевірки рівності завжди застосовуються оператори суворого порівняння `===` та `!==`.
- **Чистота функцій:** функції мають бути короткими, вирішувати одну задачу та не створювати небажаних побічних ефектів.
- **Відсутність «магічних значень»:** числові коефіцієнти, граничні значення та спеціальні рядки виносяться в іменовані константи.

### 3.5. Коментарі та гігієна коду

- **Зміст коментарів:** коментарі повинні пояснювати *чому* обрано певне нетривіальне рішення або особливість бізнес-логіки, а не дослівно переказувати очевидний синтаксис (наприклад, коментар `// збільшуємо лічильник` перед `count++` є зайвим).
- **Відсутність «мертвого коду»:** перед створенням фінального коміту необхідно повністю видалити закоментовані невикористовувані блоки коду та застарілі спроби реалізації. Для збереження історії призначений Git.
- **Очищення налагоджувального коду:** у зданій версії не повинно бути тестових викликів `console.log`, `alert()`, закоментованих стилів чи тимчасових рамок на зразок `border: 1px solid red`.

## 4. Правила створення комітів

**Коміт — це зафіксований етап змін у проєкті.** Коміти створюються в процесі виконання роботи після завершення окремої логічної зміни у межах однієї лабораторної роботи. Кожен коміт повинен бути самодостатнім і містити всі необхідні зміни для того, щоб проєкт був працездатним. В межах однієї роботи може бути створено кілька комітів.

Наприклад, окремими комітами можуть бути додавання навігації, створення форми або виправлення адаптивності. Не потрібно робити коміт після кожного рядка коду чи об’єднувати кілька лабораторних робіт в один коміт.

Повідомлення має містити номер лабораторної та короткий опис зміни:

- `lab-04: додано семантичну структуру головної сторінки`;
- `lab-06: створено форму зворотного зв’язку`;
- `lab-12: виправлено переповнення на мобільному екрані`.

Повідомлення на зразок `update`, `готово`, `123` не пояснюють зміст роботи й не використовуються.

Перед комітом необхідно перевірити перелік і зміст змін:

```bash
git status
git diff
```

Далі потрібні файли додаються до індексу й створюється коміт:

```bash
git add index.html
git commit -m "lab-04: додано семантичну структуру головної сторінки"
```

Шлях `index.html` у прикладі потрібно замінити шляхами до файлів, які належать до відповідної зміни.

Коміт зберігає зміни локально. Для передавання їх на GitHub виконується:

```bash
git push origin main
```

Фінальний коміт лабораторної роботи перед її здаванням повинен містити всі необхідні зміни для того, щоб проєкт був працездатним і мав завершений вигляд. Приклад назви: `lab-01: final version`.

## 5. Робота з гілками

Гілка `main` містить поточну працездатну версію проєкту.

**До лабораторної №24 включно** дозволяється працювати безпосередньо в `main`. **Починаючи з лабораторної №25**, зміни виконуються в окремій гілці, наприклад `work/lab-25`.

Перед початком нової роботи потрібно завершити або зберегти попередні зміни, перейти до `main`, отримати актуальну версію та створити гілку:

```bash
git switch main
git pull origin main
git switch -c work/lab-25
```

Коміти виконуються у створеній гілці. Для її першої публікації використовується:

```bash
git push -u origin work/lab-25
```

Після завершення роботи студент створює на GitHub **pull request із робочої гілки до `main`**. У ньому зазначаються номер роботи, виконані зміни та порядок перевірки.

Студент переглядає зміни у pull request і після перевірки працездатності зливає їх до `main`. Посилання на pull request додається до матеріалів здавання, щоб викладач міг переглянути зміни окремого етапу.

Наступна лабораторна починається з оновленої `main`. Робоча гілка використовується для внесення змін, а здана версія фіксується тегом.

## 6. Фіксація завершеної роботи тегом

**Тег позначає конкретну версію проєкту, яка здається на перевірку.** Подальша робота над проєктом не змінює цю версію, якщо тег не переносити.

Для першого здавання використовуються назви:

- `lab-01`;
- `lab-02`;
- …
- `lab-32`.

Перед створенням тегу всі файли роботи, включно зі звітом, мають бути закомічені. Для робіт із pull request тег створюється в `main` після злиття та отримання оновлень.

Приклад фіксації лабораторної №4:

```bash
git tag -a lab-04 -m "lab-04: final version"
git push origin main
git push origin lab-04
```

**Звичайний `git push` не гарантує надсилання тегів**, тому тег публікується окремою командою.

Здані теги не видаляються і не переносяться на інші коміти. Історія зданих робіт не переписується.

## 7. Оформлення короткого звіту

Для кожної роботи створюється окремий файл звіту в каталозі `docs/labs/`, наприклад `docs/labs/lab-04.md`.

Звіт має бути лаконічним і допомагати швидко перевірити результат (переписувати теоретичний матеріал лекції не потрібно).

> [!NOTE]
> **Обов'язкові пункти короткого звіту:**
>
> 1. Номер і тема лабораторної роботи.
> 2. Короткий перелік фактично реалізованих завдань і функцій.
> 3. Інструкція запуску (якщо вона відрізняється від загальної інструкції в `README.md`).
> 4. Порядок перевірки: яку сторінку відкрити, які дії виконати та який результат очікується.
> 5. Відомі недоліки або невиконані пункти (якщо вони є).
> 6. Скриншоти інтерфейсу (якщо передбачено завданням роботи).

## 8. Порядок здавання на перевірку

Перед відправленням роботи викладачу студент виконує підготовчий чекліст:

- [ ] Перевірено локальний запуск і коректність роботи всіх сторінок та сценаріїв;
- [ ] Оновлено файл звіту `docs/labs/lab-XX.md` та таблицю виконання в `README.md`;
- [ ] Зафіксовано всі зміни фінальним комітом;
- [ ] Надіслано зміни на GitHub (`git push origin main`);
- [ ] Створено та опубліковано анотований тег (`git push origin lab-XX`);
- [ ] Створено Pull Request (починаючи з лабораторної роботи №25).

> [!IMPORTANT]
> **Зразок повідомлення викладачу для здавання роботи:**
>
> ```text
> ПІБ: Шевченко Тарас Григорович
> Група: ІПЗ-21
> Лабораторна робота: №04 (Семантична структура та форми)
> Репозиторій: https://github.com/username/web-technologies-NameSurname
> Версія для перевірки (тег lab-04): https://github.com/username/web-technologies-NameSurname/releases/tag/lab-04
> Посилання на коміт версії: https://github.com/username/web-technologies-NameSurname/commit/abcdef1234567890
> Звіт у зданій версії: https://github.com/username/web-technologies-NameSurname/blob/lab-04/docs/labs/lab-04.md
> Опублікований сайт: https://username.github.io/web-technologies-NameSurname/
> Pull Request (починаючи з №25): —
> ```

Посилання на коміт і звіт обов'язково копіюються зі стану зданої версії (за тегом). Посилання лише на поточну гілку `main` є недостатнім, оскільки її вміст продовжуватиме змінюватися під час виконання наступних робіт.

Опублікований сайт також може відображати новішу версію. **Головною основою перевірки є вихідний код зафіксованого коміту, зазначеного під час здавання.**

## 9. Виправлення після перевірки

Зауваження викладача виправляються новими комітами у відповідній робочій гілці. Попередня здана версія обов'язково зберігається в історії Git.

Повторне здавання позначається новим версійним тегом:

- `lab-04-v2` — друге здавання (перша ітерація виправлень);
- `lab-04-v3` — третє здавання тощо.

Приклад фіксації та відправлення виправлень:

```bash
git add .
git commit -m "lab-04: виправлено зауваження до валідації форми"
git tag -a lab-04-v2 -m "lab-04: повторне здавання після виправлень"
git push origin main
git push origin lab-04-v2
```

Студент надсилає нові посилання на оновлений тег і коміт та коротко описує внесені виправлення. Якщо після першого здавання вже розпочато наступні роботи, у звіті зазначається, що нова версія містить також ці напрацювання.

## 10. Особливості перших двох лабораторних

> [!NOTE]
> Лабораторні роботи №1 та №2 виконуються локально, оскільки робота з Git вивчається згідно з програмою на третьому тижні.

Під час виконання лабораторної роботи №3 напрацьовані результати додаються до репозиторію послідовно:
- спочатку додаються матеріали лабораторної №1 з окремим комітом і тегом `lab-01`;
- потім додаються матеріали лабораторної №2 з комітом і тегом `lab-02`;
- після цього виконуються безпосередні завдання лабораторної №3 та створюється тег `lab-03`.

Дати цих комітів відображатимуть фактичний момент інтеграції файлів із Git.

## 11. Перевірка та захист

Викладач перевіряє зазначену версію проєкту: якість вихідного коду, виконання вимог завдання, культуру комітів та оформлення звіту. Для запуску версії певного етапу завантажується або локально відкривається відповідний тег.

Під час захисту лабораторної роботи студент повинен:
- вільно орієнтуватися у структурі створеного проєкту та архітектурі файлів;
- обґрунтувати вибір використаних семантичних тегів, правил CSS або JavaScript-рішень;
- продемонструвати працездатність інтерфейсу та його поведінку на різних пристроях;
- за потреби виконати невелику контрольну зміну в коді за вказівкою викладача для підтвердження самостійності виконання роботи.

### 12.1. Документація та навчальні посібники

- [MDN Web Docs (Українська / Англійська)](https://developer.mozilla.org/uk/) — головний офіційний довідник вебтехнологій (HTML, CSS, JavaScript, Web APIs);
- [Сучасний підручник з JavaScript](https://uk.javascript.info/) — фундаментальний навчальний курс з JavaScript від основ до поглиблених концепцій;
- [web.dev від Google](https://web.dev/) — практичні посібники та найкращі сучасні практики веброзробки, адаптивності та продуктивності.

### 12.2. Робота з Git та GitHub

- [Книга Pro Git (Український переклад)](https://git-scm.com/book/uk/v2) — офіційний повний посібник із роботи з системою контролю версій Git;
- [Learn Git Branching](https://learngitbranching.js.org/?locale=uk) — інтерактивний візуальний тренажер для освоєння гілок, комітів і злиття в Git;
- [gitignore.io](https://www.toptal.com/developers/gitignore) — генератор шаблонів файлу `.gitignore` для будь-яких стеків розробки та операційних систем;
- [Документація GitHub Pages](https://docs.github.com/uk/pages) — офіційний посібник із розгортання та хостингу статичних сайтів безпосередньо з репозиторію.

### 12.3. Валідатори та інструменти якості

- [W3C HTML Validator](https://validator.w3.org/) — офіційний сервіс перевірки валідності та стандартів HTML-розмітки;
- [W3C CSS Validator](https://jigsaw.w3.org/css-validator/) — офіційний валідатор синтаксису та властивостей каскадних таблиць стилів CSS;
- [Can I use](https://caniuse.com/) — актуальні таблиці сумісності та підтримки технологій HTML5, CSS та JS у різних браузерах;
- [PageSpeed Insights](https://pagespeed.web.dev/) — інструмент аудиту продуктивності, швидкості та доступності (Lighthouse).

### 12.4. Вебдизайн, доступність та ресурси

- [Figma](https://www.figma.com/) — популярний хмарний інструмент для створення макетів, UI-елементів та інтерактивних прототипів;
- [WebAIM Contrast Checker](https://webaim.org/resources/contrastchecker/) — калькулятор коефіцієнта контрастності тексту та фону за стандартами доступності WCAG;
- [Google Fonts](https://fonts.google.com/) — безкоштовна бібліотека вебшрифтів для підключення до проєкту;
- [Tabler Icons](https://tabler.io/icons) та [Lucide Icons](https://lucide.dev/) — великі каталоги чистих векторних SVG-іконок з відкритим кодом;
- [Markdown Guide](https://www.markdownguide.org/cheat-sheet/) — швидка шпаргалка із синтаксису розмітки Markdown для оформлення звітів і документації.
