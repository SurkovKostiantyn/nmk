## План лекції

- анатомія об'єктів у сучасному JavaScript - посилальна природа даних у пам'яті (Stack vs Heap), семантика рівності за посиланням, причини важливості розуміння посилальної моделі для веброзробника (побічні ефекти, спільний стан, оптимізація рендерингу) та синтаксичні оптимізації ES6+ (shorthand properties, computed property names);
- деструктуризація об'єктів та масивів (Destructuring Assignment) - базовий механізм вилучення даних, перейменування властивостей (аліаси), значення за замовчуванням, глибока вкладена деструктуризація та патерн налаштувань функцій (Options Object);

- механіка копіювання об'єктів (Shallow vs Deep Copy) - поверхневе копіювання через `Object.assign()` та spread, пастка спільних посилань на вкладені структури, обмеження класичного методу `JSON.parse(JSON.stringify())` та сучасний стандарт `structuredClone()`;
- інспекція, ітерація та трансформація об'єктів - статичні методи `Object.keys()`, `Object.values()`, `Object.entries()`, зворотне збирання об'єктів через `Object.fromEntries()`, безпечна перевірка наявності властивостей (`Object.hasOwn`, оператори `?.` та `??`);
- контроль мутабельності та рівні захисту об'єктів - відмінність між `const` та незмінністю значень, методи `Object.preventExtensions()`, `Object.seal()`, `Object.freeze()` та реалізація рекурсивного глибокого заморожування `deepFreeze()`;
- організація та підготовка даних до взаємодії з бекендом - архітектурна концепція DTO (Data Transfer Object), трансляція конвенцій найменування (camelCase у snake_case), санітизація, суворе приведення типів та збирання фінального JSON Payload для REST API;
- практичний кейс проєкту TechShop - проектування сервісного модуля оформлення замовлення (Order Processing Service) з глибоким клонуванням стану кошика, збиранням DTO та безпечною обробкою серверної відповіді.

## Перелік умовних скорочень

- API (Application Programming Interface) - інтерфейс прикладного програмування;
- DTO (Data Transfer Object) - об'єкт передачі даних між клієнтом і сервером або підсистемами;

- CRUD (Create, Read, Update, Delete) - базовий набір операцій керування сутностями;
- RAM (Random Access Memory) - оперативна пам'ять пристрою;
- UI (User Interface) - користувацький інтерфейс;
- HTTP (HyperText Transfer Protocol) - протокол передачі гіпертексту для клієнт-серверної взаємодії;
- ISO (International Organization for Standardization) - міжнародний стандарт, зокрема формату представлення дати й часу ISO 8601;
- UUID (Universally Unique Identifier) - стандартизований 128-бітний унікальний ідентифікатор.

Проте всі ці системи — інтерфейсні форми, локальне сховище та URL-адреса — об'єднує один спільний знаменник: **об'єкти JavaScript**. Кожна сутність у реальному веб-додатку (товар інтернет-магазину, обліковий запис покупця, рядок замовлення, конфігурація фільтрів каталогу) зберігається, обробляється та передається саме у вигляді об'єкта.

З наближенням до взаємодії зі справжнім серверним бекендом (теми 23–24) вимоги до чистоти, структуризації та безпеки маніпуляцій з об'єктами зростають у рази:
- бекенд очікує суворого контракту даних - серверний скрипт на PHP, Node.js або Python викине фатальну помилку, якщо клієнт передасть зайві технічні поля інтерфейсу, переплутає число з рядком або передасть непередбачений формат ключів;
- пряма мутація об'єктів у клієнтській пам'яті породжує важковиправні баги - якщо функція оновлення кількості товару випадково змінить оригінальний об'єкт у каталозі через спільне посилання, це спотворить стан усього магазину;
- серіалізація та копіювання мають приховані підводні камені - наївне клонування через `JSON.parse(JSON.stringify())` втрачає спеціальні типи даних, видаляє поля зі значенням `undefined` та призводить до аварійної зупинки скрипта при виявленні циклічних посилань.

Мета цієї лекції — комплексно опанувати поглиблені механізми сучасної мови JavaScript (стандарти ES6–ES2023) для безпечної, елегантної та продуктивної роботи з об'єктами: від синтаксису деструктуризації та операторів Spread/Rest до створення глибоких копій через нативний API `structuredClone()`, керування незмінністю через `Object.freeze()` та формування професійних об'єктів передачі даних (DTO) для надійної комунікації з бекендом.

## 1. Об'єкти в пам'яті JavaScript та сучасні можливості ES6+

### 1.1. Посилальна модель даних: Stack проти Heap

Для розуміння того, чому об'єкти в JavaScript поводяться не так, як звичайні числа чи рядки, необхідно звернутися до архітектури керування оперативною пам'яттю у рушіях JavaScript (таких як Google V8 або SpiderMonkey).

Пам'ять програми логічно розділена на дві основні області:
- стек (Call Stack / Execution Stack) - швидка, фіксованого розміру область оперативної пам'яті, де зберігаються примітивні значення фіксованої довжини (числа `Number`, булеві значення `Boolean`, порожні типи `null` і `undefined`), контексти виконання функцій та посилання на змінні;
- купа (Memory Heap) - простора динамічна область пам'яті довільного розміру, де виділяється місце для складних структур даних змінного розміру: об'єктів, масивів, функцій і регулярних виразів.

Примітивні типи даних копіюються **за значенням (by value)**. Коли ми присвоюємо одну примітивну змінну іншій, створюється абсолютно незалежна копія цього бінарного значення у новому осередку стека:

```javascript
let basePrice = 1200;
let discountedPrice = basePrice; // у стек записується незалежна копія числа 1200

discountedPrice = 999;
console.log(basePrice);       // 1200 (оригінал не змінився)
console.log(discountedPrice); // 999
```

Об'єкти та масиви мають **посилальний тип (Reference Type)**. Коли у коді створюється об'єктний літерал `{ title: "Ноутбук" }`, сам вміст об'єкта розміщується у динамічній купі (Heap). У змінну ж у стеку записується лише **посилання** — числова адреса комірки в купі, де цей об'єкт фізично розташований.

```text
Стек (Stack):                           Купа (Memory Heap):
┌─────────────────────────┐             ┌──────────────────────────────────────────────┐
│ productA ───► @addr0x01 │ ──────────► │ @addr0x01: { id: 101, title: "Ноутбук ASUS" } │
│ productB ───► @addr0x01 │ ───────────┘ └──────────────────────────────────────────────┘
└─────────────────────────┘
```

Якщо ми присвоїмо об'єкт іншій змінній, скопіюється не сам об'єкт, а лише адреса посилання:

```javascript
const productA = { id: 101, title: "Ноутбук ASUS", price: 28000 };

// Копіюється лише адреса пам'яті (@addr0x01), а не сам об'єкт:
const productB = productA;

// Мутація властивості через нову змінну:
productB.price = 24999;

// Оригінал також змінився, оскільки обидві змінні дивляться на один об'єкт у купі!
console.log(productA.price); // 24999
console.log(productA === productB); // true (порівнюються адреси в купі)
```

Це пояснює фундаментальне правило операторів строгої рівності `===` для об'єктів:
- оператор `===` порівнює не вміст об'єктів, а їхні адреси в оперативній пам'яті;
- два різні об'єкти з абсолютно ідентичними наборами ключів і значень ніколи не є рівними між собою, оскільки кожен новий літерал `{}` виділяє нову ділянку пам'яті в купі.

```javascript
const item1 = { id: 1, title: "Миша" };
const item2 = { id: 1, title: "Миша" };

console.log(item1 === item2); // false (різні ділянки пам'яті)
console.log(item1 == item2);  // false
```

### 1.2. Чому веброзробнику критично важливо розуміти посилальну модель

Нерозуміння того, як об'єкти розташовуються в пам'яті (Stack vs Heap) та як працюють спільні посилання, є однією з найчастіших причин появи прихованих та важковідтворюваних дефектів («плаваючих» багів) у сучасних веб-додатках. У невеликих навчальних скриптах мутація об'єкта може здаватися незначною, але у комерційних проектах рівня інтернет-магазину TechShop це безпосередньо впливає на коректність бізнес-розрахунків, стабільність збереження стану та швидкодію інтерфейсу.

Ключові причини необхідності суворого контролю посилань у веб-розробці:
- запобігання непередбачуваним побічним ефектам (Side Effects) - коли допоміжна функція змінює властивості переданого об'єкта, спотворюючи первинні дані каталогу чи профілю користувача в інших частинах програми;
- уникнення витоку та перекриття спільного стану (Shared State) - коли різні замовлення чи компоненти помилково використовують посилання на один і той самий об'єкт налаштувань у пам'яті;
- забезпечення коректної роботи стандартних методів пошуку колекцій - методи `includes()`, `indexOf()` та структури `Set` порівнюють саме адреси пам'яті, через що пошук ідентичного за вмістом об'єкта завершується невдачею;
- коректна робота реактивних систем та алгоритмів оновлення DOM (Change Detection) - сучасні фронтенд-архітектури оптимізують перемалювання екрана за рахунок швидкого порівняння посилань (`oldState !== newState`), тому мутація існуючого об'єкта блокує оновлення інтерфейсу;
- запобігання витокам оперативної пам'яті (Memory Leaks) - збирач сміття браузера (Garbage Collector) не може очистити пам'ять, якщо в замиканнях чи глобальних реєстрах залишається бодай одне активне посилання на застарілий об'єкт.

Розглянемо чотири показові практичні кейси з веб-розробки, які ілюструють ці загрози та шляхи їх вирішення.

#### Кейс 1: Побічні ефекти та випадкова мутація глобального каталогу товарів

Уявіть ситуацію: в інтернет-магазині TechShop реалізовано модальне вікно швидкого перегляду зі спеціальною персональною знижкою для клієнта. Розробник пише функцію для розрахунку акційної вартості:

```javascript
// Завантажений з сервера або Web Storage глобальний каталог:
const catalogProduct = {
  id: "LP-101",
  title: "Ноутбук ASUS Vivobook",
  price: 30000,
  inStock: true
};

// Небезпечна функція: мутує вхідний аргумент
function applyPromoDiscount(product, percent) {
  // Помилка: розробник вважає, що product — це незалежна локальна копія
  product.price = product.price * (1 - percent / 100);
  return product;
}

// 1. Користувач відкриває вікно швидкого перегляду зі знижкою 10%:
const modalProduct = applyPromoDiscount(catalogProduct, 10);
console.log("Ціна в модальному вікні:", modalProduct.price); // 27000 грн

// 2. Користувач закриває вікно й повертається до загального каталогу:
// НАСЛІДКИ: ціна товару в каталозі безповоротно впала до 27000 грн!
console.log("Ціна на вітрині магазину:", catalogProduct.price); // 27000 грн

// 3. Якщо користувач повторно відкриє картку товару або перемалює сторінку:
applyPromoDiscount(catalogProduct, 10);
console.log("Ціна після другого відкриття:", catalogProduct.price); // 24300 грн (ціна зменшується з кожним кліком!)
```

Причина дефекту полягає в тому, що змінна `product` всередині функції вказує на ту саму ділянку динамічної пам'яті (Heap), де зберігається `catalogProduct`. Мутація властивості `price` зіпсувала початковий стан усього каталогу товарів.

Архітектурно правильне рішення — проектування «чистих функцій» (Pure Functions), які повертають новий об'єкт без мутації вхідного:

```javascript
// Чиста функція (Pure Function): не змінює вхідний аргумент і не створює побічних ефектів
function calculatePromoProduct(product, percent) {
  return {
    // 1. Фігурні дужки {} виділяють абсолютно новий об'єкт у динамічній пам'яті (нова адреса в Heap)
    // 2. Оператор spread (...) копіює всі властивості оригіналу (id, title, inStock) у цей новий об'єкт
    ...product,

    // 3. Властивість price, вказана нижче за spread, перезаписує скопійовану ціну
    // Мутації оригіналу НЕ відбувається — нове значення записується виключно в новий об'єкт!
    price: Math.round(product.price * (1 - percent / 100))
  };
}

// Демонстрація безпеки виклику:
const promoLaptop = calculatePromoProduct(catalogProduct, 10);

console.log("Акційна ціна нового об'єкта:", promoLaptop.price);       // 27000
console.log("Ціна в оригінальному каталозі:", catalogProduct.price);  // 30000 (залишилася непошкодженою!)
console.log("Чи це різні адреси в пам'яті?:", promoLaptop !== catalogProduct); // true
```

#### Кейс 2: Пастка спільного посилання в конфігураціях за замовчуванням (Shared Mutable State)

Часто для економії коду розробники створюють єдиний шаблон за замовчуванням для нових сутностей веб-додатка:

```javascript
// Загальний шаблон налаштувань кошика:
const defaultCartConfig = {
  currency: "UAH",
  tags: [] // вкладений масив є посилальним типом даних!
};

// Створюємо замовлення для двох різних користувачів магазину:
const orderUserA = { orderId: "ORD-01", ...defaultCartConfig };
const orderUserB = { orderId: "ORD-02", ...defaultCartConfig };

// Користувач А замовляє послугу спеціального маркування:
orderUserA.tags.push("Крихкий вантаж");

// Перевіряємо замовлення користувача B:
console.log(orderUserB.tags); // ["Крихкий вантаж"] (чужий тег з'явився у замовленні користувача B!)
```

Оператор `{ ...defaultCartConfig }` скопіював примітив `currency` за значенням, але для властивості `tags` скопіював лише адресу посилання на масив у купі. У результаті обидва користувачі ділять один спільний масив тегів.

Правильне рішення полягає у використанні фабричної функції (Factory Function), яка при кожному виклику ініціалізує нову ізольовану структуру в пам'яті:

```javascript
function createOrderConfig() {
  return {
    currency: "UAH",
    tags: [] // щоразу виділяється новий незалежний осередок у Heap
  };
}
```

#### Кейс 3: Збій пошуку та перевірки дублікатів у колекціях

Уявімо роботу зі списком «Обране» (Wishlist). Розробник намагається перевірити, чи додано товар у список:

```javascript
const wishlist = [
  { id: 101, title: "Клавіатура Keychron" },
  { id: 102, title: "Миша Logitech" }
];

// Спроба перевірити наявність товару методом includes():
const alreadyInWishlist = wishlist.includes({ id: 101, title: "Клавіатура Keychron" });
console.log(alreadyInWishlist); // false!

// Спроба знайти позицію для видалення через indexOf():
const itemIndex = wishlist.indexOf({ id: 101, title: "Клавіатура Keychron" });
console.log(itemIndex); // -1 (товар не знайдено!)
```

Методи `includes()` та `indexOf()` порівнюють значення за допомогою оператора строгої рівності `===`. Оскільки літерал `{ id: 101, ... }` створюється під час виклику методу, він отримує нову адресу пам'яті в купі, яка ніколи не збіжиться з адресою об'єкта, що вже лежить у масиві. В інтерфейсі це призводить до додавання нескінченних дублікатів товару.

Правильне рішення — пошук сутностей за унікальним примітивним ідентифікатором:

```javascript
// Перевірка через предикатну функцію:
const exists = wishlist.some(item => item.id === 101);
console.log(exists); // true

// Пошук індексу за первинним ключем:
const correctIndex = wishlist.findIndex(item => item.id === 101);
console.log(correctIndex); // 0
```

#### Кейс 4: Збій відстеження змін у реактивних інтерфейсах (Change Detection)

У сучасних веб-додатках продуктивність досягається за рахунок швидкої перевірки поверхневої рівності (Shallow Equality Check). Якщо об'єкт стану не змінив своєї адреси в пам'яті, браузер вважає, що інтерфейс оновлювати не потрібно:

```javascript
let currentAppState = {
  cartItemsCount: 0,
  user: { name: "Олександр", isAuthenticated: true }
};

// Функція оновлення шапки сайту, оптимізована для економії ресурсів процесора:
function updateHeaderView(nextState, prevState) {
  // Якщо адреси посилань збігаються, рендеринг DOM пропускається:
  if (nextState === prevState) {
    console.log("Посилання не змінилося. Перемалювання DOM пропущено.");
    return;
  }
  
  const badge = document.getElementById("cartBadge");
  if (badge) {
    badge.textContent = nextState.cartItemsCount;
  }
  console.log("DOM оновлено! Нова кількість товарів у шапці:", nextState.cartItemsCount);
}

// 1. Помилкова мутація на місці:
const oldState = currentAppState;
currentAppState.cartItemsCount = 3; // змінили властивість, але адреса лишилася старою!

updateHeaderView(currentAppState, oldState);
// Виведе: "Посилання не змінилося. Перемалювання DOM пропущено."
// Результат: користувач додав товари, а в шапці сайту лічильник кошика показує 0!

// 2. Правильне неруйнівне оновлення зі зміною посилання:
const freshState = {
  ...currentAppState,
  cartItemsCount: 4
};

updateHeaderView(freshState, currentAppState);
// Виведе: "DOM оновлено! Нова кількість товарів у шапці: 4" (Інтерфейс коректно оновився)
```

### 1.3. Лаконічний синтаксис ES6+ для роботи з властивостями

Стандарт ECMAScript 2015 (ES6) суттєво спростив декларацію та динамічну генерацію властивостей об'єктів.

Сучасні синтаксичні оптимізації створення об'єктів:
- скорочений запис властивостей (Property Shorthand) - якщо назва змінної, значення якої ми передаємо, збігається з назвою ключа створюваного об'єкта, запис можна скоротити, опустивши двокрапку та повтор імені;
- скорочений запис методів (Method Definition Shorthand) - замість тривалого запису `sayHi: function() {}` використовується лаконічний функціональний синтаксис `sayHi() {}`;
- обчислювані імена властивостей (Computed Property Names) - синтаксис квадратних дужок `[expression]: value` всередині об'єктного літерала дозволяє обчислювати назву ключа динамічно на основі довільного виразу JavaScript під час ініціалізації.

```javascript
const id = "prod-942";
const title = "Клавіатура Keychron K2";
const price = 4200;
const dynamicCategoryKey = "category_hardware";

// Традиційний синтаксис (ES5):
const legacyProduct = {
  id: id,
  title: title,
  price: price,
  calculateTax: function() {
    return this.price * 0.2;
  }
};
legacyProduct[dynamicCategoryKey] = "Периферія";

// Сучасний синтаксис ES6+:
const modernProduct = {
  id,
  title,
  price,
  [dynamicCategoryKey]: "Периферія", // динамічний ключ обчислюється на місці
  [`created_${Date.now()}`]: true,   // ключ із результатом виразу
  calculateTax() {
    return this.price * 0.2;
  }
};
```

Обчислювані імена ключів є незамінними при написанні універсальних обробників подій введення у формі. Замість написання окремої функції для кожного інпуту, розробник прив'язує атрибут `name` інпуту безпосередньо до стану об'єкта:

```javascript
const orderDraft = {};

function handleInputChange(event) {
  const { name, value } = event.target;
  // Динамічно оновлюємо відповідну властивість за іменем поля форми:
  orderDraft[name] = value;
}
```

## 2. Деструктуризація об'єктів та масивів (Destructuring Assignment)

**Деструктуризація** — це синтаксичний механізм мови JavaScript, що дозволяє «розпаковувати» властивості об'єктів або елементи масивів у окремі самостійні змінні за допомогою лаконічного дзеркального синтаксису.

### 2.1. Деструктуризація об'єктів: синтаксис, перейменування та значення за замовчуванням

До появи ES6 для вилучення полів об'єкта доводилося писати громіздкий код із багаторазовим зверненням до батьківської змінної:

```javascript
const order = {
  orderId: "ORD-8941",
  customerName: "Олена Петренко",
  amount: 5400,
  isPaid: false
};

// Традиційний підхід ES5:
const orderId = order.orderId;
const customerName = order.customerName;
const amount = order.amount;
```

Сучасний синтаксис деструктуризації дозволяє виконати це в один рядок:

```javascript
// Декларуємо змінні, чиї імена збігаються з ключами об'єкта order:
const { orderId, customerName, amount, isPaid } = order;

console.log(orderId);      // "ORD-8941"
console.log(customerName); // "Олена Петренко"
```

#### Перейменування властивостей (Alias / Renaming)
Якщо ім'я властивості в об'єкті конфліктує з існуючою змінною в поточній області видимості або не відповідає внутрішньому стилю коду, її можна перейменувати через синтаксис `ключ_в_об'єкті: нове_ім'я_змінної`:

```javascript
const product = {
  id: "P-100",
  title: "Монітор Dell 27\"",
  price: 11500,
  qty: 3
};

// Перейменовуємо qty у quantity, а title у productName:
const { title: productName, qty: quantity, price } = product;

console.log(productName); // "Монітор Dell 27\""
console.log(quantity);    // 3
// Змінної qty не існує — вона була лише джерелом для quantity!
```

#### Значення за замовчуванням (Default Values)
Якщо властивість відсутня в об'єкті або дорівнює `undefined`, деструктуризація дозволяє підставити резервне значення через знак рівності `=`. Якщо ж властивість передана зі значенням `null`, `false` або `0`, значення за замовчуванням **не застосовується**, оскільки це значення вважається визначеним:

```javascript
const userProfile = {
  id: 42,
  username: "surkov_k",
  role: "moderator",
  avatar: null
};

const { 
  username, 
  role = "customer",             // role присутня, тому "customer" не використається
  status = "active",             // status відсутній (undefined) -> присвоїться "active"
  avatar = "/assets/default.png" // avatar дорівнює null -> лишиться null!
} = userProfile;

console.log(status); // "active"
console.log(avatar); // null
```

Можна поєднувати перейменування та значення за замовчуванням в єдиній конструкції:

```javascript
const settings = { theme_mode: "dark" };

// Перейменовуємо snake_case ключ і задаємо дефолт:
const { theme_mode: themeMode = "light", font_size: fontSize = 16 } = settings;

console.log(themeMode); // "dark"
console.log(fontSize);  // 16
```

### 2.2. Вкладена (глибока) деструктуризація

Реальні відповіді серверних REST API часто містять глибоку ієрархію об'єктів. Деструктуризація дозволяє витягувати поля з будь-якого рівня вкладеності без створення проміжних змінних:

```javascript
const apiResponse = {
  status: 200,
  data: {
    customer: {
      personalInfo: {
        firstName: "Олександр",
        lastName: "Коваленко"
      },
      contacts: {
        email: "alex@example.com",
        phone: "+380501112233"
      }
    },
    delivery: {
      city: "Київ",
      warehouseId: 44
    }
  }
};

// Витягуємо лише firstName, email та city в окремі змінні:
const {
  data: {
    customer: {
      personalInfo: { firstName },
      contacts: { email }
    },
    delivery: { city }
  }
} = apiResponse;

console.log(firstName); // "Олександр"
console.log(email);     // "alex@example.com"
console.log(city);      // "Київ"
```

> [!WARNING]
> Якщо проміжний об'єкт виявиться `null` або `undefined` (наприклад, якщо `data.customer` відсутній у відповіді), спроба вкладеної деструктуризації викине фатальну помилку `TypeError: Cannot read properties of undefined`.
> Для безпечної роботи завжди надавайте проміжним вкладеним рівням порожні об'єкти за замовчуванням:
> `const { data: { customer: { contacts: { phone } = {} } = {} } = {} } = unsafeResponse;`

### 2.3. Деструктуризація масивів

На відміну від об'єктів, де вилучення відбувається **за іменами ключів**, у масивах деструктуризація базується **на порядкових позиціях (індексах)** елементів.

Ключові можливості деструктуризації масивів:
- позиційне зіставлення - змінним присвоюються значення елементів з відповідними індексами `[0]`, `[1]`, `[2]`;
- пропуск небажаних елементів - якщо певний елемент не потрібен, його позицію можна пропустити за допомогою коми без вказування імені змінної;
- обмін значеннями без тимчасової змінної - класична задача перестановки двох змінних вирішується в один рядок;
- деструктуризація результатів методів - зручне отримання значень з кортежів `Object.entries()`, результатів пошуку `RegExp.exec()` чи розділення рядків `string.split()`.

```javascript
const techCoordinates = [50.4501, 30.5234, 120]; // [lat, lng, altitude]

// Базове вилучення:
const [latitude, longitude] = techCoordinates;
console.log(latitude); // 50.4501

// Пропуск другого елемента за допомогою коми:
const [lat, , altitude] = techCoordinates;
console.log(altitude); // 120

// Елегантний обмін значень змінних без третьої тимчасової змінної:
let sortField = "price";
let sortDirection = "asc";

[sortField, sortDirection] = [sortDirection, sortField];
console.log(sortField);     // "asc"
console.log(sortDirection); // "price"
```

### 2.4. Деструктуризація у параметрах функцій: патерн Options Object

У класичному процедурному програмуванні функції часто приймають довгий перелік позиційних аргументів:

```javascript
// Антипатерн позиційних параметрів:
function createProduct(title, price, category, isAvailable, discountPercent, taxRate, sku) {
  // Важко згадати точний порядок при виклику, а необов'язкові параметри змушують писати null
}
createProduct("Смартфон", 19000, "Phones", true, null, null, "SKU-99");
```

Сучасний стандарт проектування чистих інтерфейсів вимагає передавати один об'єкт налаштувань (**Options Object**) та деструктуризувати його безпосередньо у списку параметрів функції:

```javascript
function renderProductCard({
  id,
  title,
  price,
  currency = "грн",
  inStock = true,
  discount = 0,
  badges = []
} = {}) {
  const finalPrice = discount > 0 ? price * (1 - discount / 100) : price;
  
  return `
    <article class="product-card" data-id="${id}">
      <h3>${title}</h3>
      <p class="price">${finalPrice.toLocaleString()} ${currency}</p>
      <span class="badge ${inStock ? "badge--instock" : "badge--out"}">
        ${inStock ? "В наявності" : "Під замовлення"}
      </span>
      ${badges.map(b => `<span class="tag">${b}</span>`).join("")}
    </article>
  `;
}

// Виклик стає повністю самодокументованим, порядок параметрів не має значення:
const cardHtml = renderProductCard({
  title: "Планшет Apple iPad Air",
  price: 32000,
  id: "tab-11",
  badges: ["Хіт продажу", "Безкоштовна доставка"]
});
```

Зверніть увагу на конструкцію `= {}` у кінці списку параметрів функції. Вона дозволяє викликати функцію взагалі без аргументів `renderProductCard()`, не викликаючи помилку розіменування `undefined`.

## 3. Оператори Spread та Rest для об'єктів: неруйнівні маніпуляції

Синтаксис трьох крапок `...` виконує дві діаметрально протилежні ролі залежно від контексту використання:
- оператор розпакування (Spread Operator) - «розгортає» всі власні перелічувані властивості існуючого об'єкта в новий об'єктний літерал;
- оператор залишку (Rest Operator) - «збирає» всі невилучені при деструктуризації властивості в окремий новий об'єкт.

### 3.1. Оператор розпакування (Spread Operator `...`)

Оператор Spread є основним інструментом **іммутабельного (неруйнівного) оновлення даних**. Замість мутації вихідного об'єкта ми створюємо новий екземпляр, зберігаючи всі старі властивості та перекриваючи лише необхідні:

```javascript
const originalProduct = {
  id: "P-500",
  title: "Ігрові навушники SteelSeries",
  price: 4500,
  category: "Audio",
  inStock: true
};

// Створюємо оновлений об'єкт: змінюємо ціну та додаємо знижку
const updatedProduct = {
  ...originalProduct,
  price: 3999,
  discount: 11,
  updatedAt: new Date().toISOString()
};

console.log(updatedProduct.price);    // 3999
console.log(originalProduct.price);  // 4500 (оригінальний об'єкт залишився непошкодженим!)
```

#### Правило порядку при злитті властивостей
В об'єктному літералі JavaScript властивості обробляються зліва направо. Якщо властивість із певним ім'ям зустрічається кілька разів, **останнє (крайнє праворуч) значення завжди перезаписує всі попередні**:

```javascript
const defaultFilter = {
  page: 1,
  limit: 20,
  sort: "popular_desc",
  inStockOnly: true
};

const userSelection = {
  page: 3,
  sort: "price_asc"
};

// Злиття налаштувань: userSelection перекриває дефолти
const activeFilter = {
  ...defaultFilter,
  ...userSelection
};

console.log(activeFilter);
// { page: 3, limit: 20, sort: 'price_asc', inStockOnly: true }
```

### 3.2. Оператор залишку (Rest Operator `...rest`)

Під час деструктуризації об'єкта оператор `...` збирає всі властивості, які не були витягнуті явно, у самостійний новий об'єкт:

```javascript
const clientUser = {
  id: 771,
  login: "dev_expert",
  email: "dev@techshop.ua",
  role: "customer",
  passwordHash: "e10adc3949ba59abbe56e057f20f883e",
  twoFactorToken: "847102"
};

// Відокремлюємо чутливі системні дані від публічної інформації користувача:
const { passwordHash, twoFactorToken, ...safePublicProfile } = clientUser;

console.log(safePublicProfile);
// { id: 771, login: 'dev_expert', email: 'dev@techshop.ua', role: 'customer' }
```

Це найбезпечніший і найшвидший патерн для видалення небажаних властивостей з об'єкта. Використання оператора `delete object.property` вважається поганою практикою у сучасному JavaScript, оскільки мутація форми об'єкта змушує рушій V8 відмовитися від внутрішніх оптимізацій прихованих класів (Hidden Classes), сповільнюючи виконання програми.

## 4. Поверхневе та глибоке копіювання: механіка, пастки та стандарти

Одна з найпоширеніших причин критичних помилок у фронтенд-розробці — нерозуміння різниці між копіюванням за посиланням, поверхневим клонуванням та повним глибоким копіюванням.

### 4.1. Поверхневе копіювання (Shallow Copy): `Object.assign()` проти Spread

Обидва синтаксиси — `{ ...original }` та `Object.assign({}, original)` — створюють **поверхневу копію (Shallow Copy)**.

Як працює поверхневе копіювання:
- новий кореневий об'єкт створюється у новій ділянці пам'яті в купі;
- примітивні властивості першого рівня (рядки, числа, булеві значення) копіюються за значенням;
- вкладені об'єкти, масиви та функції першого рівня **не дублюються**, а копіюються як ті самі адреси посилань.

```javascript
const originalCart = {
  cartId: "CART-10",
  totalAmount: 18500,
  shippingAddress: {
    city: "Львів",
    street: "вул. Городоцька",
    building: 15
  },
  items: ["Товар 1", "Товар 2"]
};

// Створюємо поверхневу копію через spread:
const copiedCart = { ...originalCart };

// 1. Зміна примітиву першого рівня не шкодить оригіналу:
copiedCart.totalAmount = 21000;
console.log(originalCart.totalAmount); // 18500 (все добре)

// 2. Зміна властивості у вкладеному об'єкті призводить до небезпечної мутації оригіналу!
copiedCart.shippingAddress.city = "Київ";
copiedCart.items.push("Товар 3");

console.log(originalCart.shippingAddress.city); // "Київ" (ОРИГІНАЛ СПОТВОРЕНО!)
console.log(originalCart.items); // ["Товар 1", "Товар 2", "Товар 3"]
```

Чому це сталося? Обидва об'єкти — `originalCart` та `copiedCart` — отримали власні незалежні поля `totalAmount`, але їхні поля `shippingAddress` містять абсолютно однакову адресу в купі: `@addr0x99`. Змінюючи адресу через один об'єкт, ви автоматично змінюєте її для всіх інших посилань у системі.

#### Різниця між `Object.assign()` та Spread
Метод `Object.assign(target, ...sources)` копіює всі перелічувані властивості з джерел `sources` у цільовий об'єкт `target` та повертає його.

Ключові відмінності:
- метод `Object.assign()` **мутує** свій перший аргумент (`target`), тому для створення нового об'єкта першим аргументом обов'язково треба передавати порожній літерал `{}`: `Object.assign({}, source)`;
- метод `Object.assign()` викликає сеттери (Setters) на цільовому об'єкті, тоді як оператор Spread просто визначає нові власні властивості в новоствореному об'єкті;
- у сучасному коді синтаксис Spread `{ ...source }` є переважним завдяки своїй декларативності та кращій оптимізації в компіляторах.

### 4.2. Глибоке копіювання (Deep Copy): класичний метод через JSON

Щоб створити повністю незалежну копію об'єкта, включно з усіма рівнями вкладеності масивів та внутрішніх об'єктів, застосовують **глибоке копіювання (Deep Copy)**.

Протягом тривалого часу найвідомішим трюком у спільноті JavaScript була подвійна серіалізація через об'єкт `JSON`:

```javascript
const deepClone = JSON.parse(JSON.stringify(originalCart));

deepClone.shippingAddress.city = "Одеса";
console.log(originalCart.shippingAddress.city); // "Львів" (оригінал цілий!)
```

Механізм роботи простий: об'єкт спочатку перетворюється на звичайний текст, а потім з цього тексту створюються абсолютно нові екземпляри об'єктів у купі без збереження старих посилань.

Проте трюк із JSON має **критичні обмеження та приховані загрози**, через які його категорично заборонено використовувати на складних структурах даних:

```javascript
const complexData = {
  title: "Договір постачання",
  signedAt: new Date("2026-03-01T10:00:00Z"), // об'єкт дати Date
  calculateFine: () => 500,                   // функція / метод
  secretKey: Symbol("order_secret"),          // тип Symbol
  notes: undefined,                           // тип undefined
  errorCounter: NaN,                          // спеціальне числове значення
  infinityMetric: Infinity,                   // нескінченність
  uniqueTags: new Set(["gadget", "bestseller"]) // колекція Set
};

const brokenClone = JSON.parse(JSON.stringify(complexData));

console.log(typeof brokenClone.signedAt); // "string" (об'єкт Date втратив методи і став рядком!)
console.log(brokenClone.calculateFine);   // undefined (функція безслідно видалена!)
console.log(brokenClone.secretKey);       // undefined (символ безслідно видалений!)
console.log(brokenClone.notes);           // undefined (поле зникло з ключів об'єкта)
console.log(brokenClone.errorCounter);    // null (NaN перетворився на null!)
console.log(brokenClone.infinityMetric);  // null (Infinity перетворився на null!)
console.log(brokenClone.uniqueTags);      // {} (Set перетворився на порожній об'єкт!)
```

Найнебезпечніший випадок — **циклічні посилання (Circular References)**, коли об'єкт через одне зі своїх полів посилається сам на себе (або через коло взаємних посилань):

```javascript
const user = { name: "Іван" };
const department = { name: "ІТ-відділ", lead: user };
user.worksIn = department; // циклічне посилання!

JSON.stringify(user);
// Викидає фатальну помилку: TypeError: Converting circular structure to JSON
```

### 4.3. Сучасний стандарт: нативна функція `structuredClone()`

Починаючи з 2022 року, у специфікаціях HTML Living Standard та ECMAScript з'явилася вбудована глобальна функція **`structuredClone()`**. Вона реалізує алгоритм структурованого клонування, який раніше використовувався браузером для передачі даних через `postMessage` у Web Workers та в сховище `IndexedDB`.

Функція підтримується всіма актуальними браузерами (Chrome 98+, Firefox 94+, Safari 15.4+) та Node.js починаючи з версії 17:

```javascript
const richOrder = {
  id: "ORD-99",
  createdAt: new Date(),
  flags: new Set(["urgent", "vip"]),
  metadata: new Map([["source", "google_ads"]]),
  items: [
    { title: "Ноутбук", price: 30000 }
  ]
};

// Створюємо справжню глибоку копію:
const clonedOrder = structuredClone(richOrder);

// Перевірка незалежності та типів даних:
clonedOrder.items[0].price = 28000;
console.log(richOrder.items[0].price); // 30000 (оригінал не змінився!)

console.log(clonedOrder.createdAt instanceof Date); // true (типи зберігаються!)
console.log(clonedOrder.flags instanceof Set);      // true
console.log(clonedOrder.flags.has("urgent"));       // true
```

#### Ключові можливості та обмеження `structuredClone()`
Можливості алгоритму structuredClone:
- підтримка вкладених структур будь-якої глибини - рекурсивно дублює масиви, прості об'єкти та словники;
- підтримка циклічних посилань - коректно розпізнає посилання на той самий вузол без переповнення стека;
- коректне клонування спеціальних типів - підтримує `Date`, `RegExp`, `Map`, `Set`, `ArrayBuffer`, `Uint8Array`, `Error`, `Blob`, `File`;
- збереження спеціальних значень - `undefined`, `NaN`, `Infinity`, `BigInt` залишаються собою.

Обмеження structuredClone:
- не можна клонувати функції та методи об'єктів - спроба передати функцію призведе до викидання помилки `DOMException: DataCloneError`;
- не можна клонувати DOM-вузли - елементи на кшталт `document.getElementById("btn")` не клонуються;
- не клонує ланцюжок прототипів - клонований екземпляр класу перетворюється на звичайний об'єкт із прототипом `Object.prototype`, втрачаючи зв'язок зі своїм класом;
- не копіює дескриптори властивостей - властивості, які були доступні лише для читання (`writable: false`) або створені через гетери (`get()`), стають звичайними записуваними полями.

Порівняльна таблиця стратегій копіювання:

| Характеристика | Посилання (`b = a`) | Поверхневе (`{ ...a }`) | Серіалізація JSON | Нативний `structuredClone()` |
| :--- | :--- | :--- | :--- | :--- |
| **Створення нового кореневого об'єкта** | Ні (одна адреса) | Так | Так | Так |
| **Незалежність першого рівня** | Ні | Так | Так | Так |
| **Незалежність вкладених об'єктів** | Ні | Ні (посилання) | Так | Так |
| **Збереження об'єктів `Date`** | Так | Так | Ні (стає String) | Так (лишається Date) |
| **Підтримка `Map`, `Set`, `BigInt`** | Так | Так | Ні (втрачаються) | Так |
| **Підтримка циклічних посилань** | Так | Так | Ні (викидає Error) | Так |
| **Копіювання методів/функцій** | Так | Так | Ні (видаляються) | Ні (викидає Error) |

## 5. Інспекція, ітерація та конвеєрна трансформація об'єктів

У лекції 15 ми детально розібрали потужні декларативні методи масивів: `map`, `filter`, `reduce`, `find`. Проте звичайний об'єкт JavaScript не є ітерованою колекцією (Iterable) за замовчуванням: над ним не можна безпосередньо викликати `.map()` або обійти його за допомогою циклу `for...of`.

Для того щоб поєднати гнучкість об'єктних структур із потужністю конвеєрів обробки масивів, стандартна бібліотека JavaScript надає статичні методи класу `Object`.

### 5.1. Статичні методи: `keys()`, `values()`, `entries()`

Методи інспекції об'єкта:
- `Object.keys(obj)` - повертає масив власних перелічуваних строкових імен ключів об'єкта;
- `Object.values(obj)` - повертає масив значень усіх власних перелічуваних властивостей об'єкта;
- `Object.entries(obj)` - повертає масив пар виду `[key, value]`, де кожен елемент є двоелементним масивом (кортежем).

```javascript
const productMetrics = {
  views: 1240,
  addedToCart: 156,
  purchased: 42,
  returns: 2
};

console.log(Object.keys(productMetrics));
// ['views', 'addedToCart', 'purchased', 'returns']

console.log(Object.values(productMetrics));
// [1240, 156, 42, 2]

console.log(Object.entries(productMetrics));
// [
//   ['views', 1240],
//   ['addedToCart', 156],
//   ['purchased', 42],
//   ['returns', 2]
// ]
```

### 5.2. Зворотне збирання через `Object.fromEntries()`

Метод `Object.fromEntries(iterable)` виконує зворотну дію: він приймає ітерований список пар `[key, value]` і збирає з нього новий повноцінний об'єкт.

Завдяки зв'язці `Object.entries()` та `Object.fromEntries()` народжується універсальний архітектурний шаблон **«Трансформаційний конвеєр об'єкта»**:

```text
[Вихідний об'єкт] ──► Object.entries() ──► [Масив пар [ключ, значення]]
                                                      │
                                                      ▼
                                       [.filter() / .map() масиву]
                                                      │
                                                      ▼
[Оновлений об'єкт] ◄── Object.fromEntries() ◄── [Трансформований масив]
```

### 5.3. Практичні патерни конвеєрної обробки

#### Патерн 1: Очищення форми або фільтрів від порожніх значень
Коли користувач заповнює фільтри в каталозі товарів, більшість полів залишаються порожніми рядками або `null`. Відправляти такі дані на бекенд некоректно. Очистимо об'єкт в один функціональний ланцюжок:

```javascript
const rawFilterPayload = {
  category: "laptops",
  brand: "lenovo",
  searchQuery: "",
  minPrice: 15000,
  maxPrice: null,
  isAvailable: true,
  warrantyYears: undefined
};

// Видаляємо всі властивості, значення яких є "", null або undefined:
const cleanFilterPayload = Object.fromEntries(
  Object.entries(rawFilterPayload).filter(([key, value]) => {
    return value !== "" && value !== null && value !== undefined;
  })
);

console.log(cleanFilterPayload);
// { category: 'laptops', brand: 'lenovo', minPrice: 15000, isAvailable: true }
```

#### Патерн 2: Модифікація значень (мапування цін)
Нехай нам необхідно перерахувати ціни оптового каталогу в гривню за курсом валют:

```javascript
const wholesalePricesUSD = {
  cpu_i7: 310,
  ram_32gb: 95,
  ssd_1tb: 70
};

const exchangeRate = 41.5;

const wholesalePricesUAH = Object.fromEntries(
  Object.entries(wholesalePricesUSD).map(([part, priceUSD]) => [
    part,
    Math.round(priceUSD * exchangeRate)
  ])
);

console.log(wholesalePricesUAH);
// { cpu_i7: 12865, ram_32gb: 3943, ssd_1tb: 2905 }
```

### 5.4. Безпечна перевірка існування властивостей

У повсякденній роботі виникає потреба перевірити, чи містить об'єкт певну властивість, не читаючи її значення безпосередньо.

Сучасні інструменти перевірки властивостей:
- метод `Object.hasOwn(obj, prop)` - сучасний нативний метод (введений в ECMAScript 2022), що безпечно перевіряє наявність власної властивості; є заміною застарілого `obj.hasOwnProperty()`, який ламався на об'єктах без прототипу `Object.create(null)` або якщо ім'я `hasOwnProperty` було перекрите;
- оператор `in` - перевіряє наявність властивості як у самому об'єкті, так і у всьому ланцюжку його прототипів;
- оператор опціонального ланцюжка (Optional Chaining `?.`) - дозволяє безпечно зчитувати глибокі вкладені властивості без викидання помилки `TypeError`, якщо проміжний рівень дорівнює `null` або `undefined`;
- оператор нульового злиття (Nullish Coalescing `??`) - повертає праве значення тільки якщо ліве значення дорівнює суворо `null` або `undefined` (на відміну від оператора `||`, який спрацьовує на `0`, `""` та `false`).

```javascript
const serverConfig = {
  port: 8080,
  features: {
    enableCashback: false
  }
};

// 1. Безпечна перевірка власної властивості:
console.log(Object.hasOwn(serverConfig, "port"));       // true
console.log(Object.hasOwn(serverConfig, "toString"));   // false (це прототипна властивість!)
console.log("toString" in serverConfig);                // true (знаходить у прототипі)

// 2. Опціональний ланцюжок + нульове злиття:
const maxLimit = serverConfig.database?.connection?.limit ?? 10;
console.log(maxLimit); // 10 (помилки немає, повернуто дефолт)

// 3. Різниця між ?? та ||:
const cashbackStatus1 = serverConfig.features.enableCashback || true;  // true (помилка: 0 або false затирається!)
const cashbackStatus2 = serverConfig.features.enableCashback ?? true;  // false (коректно збережено булеве значення)
```

## 6. Контроль мутабельності та рівні захисту об'єктів

### 6.1. Чому ключове слово `const` не захищає об'єкт від змін

Початківці часто помилково вважають, що оголошення об'єкта через ключове слово `const` робить його повністю незмінним:

```javascript
const systemSettings = {
  version: "1.0.0",
  environment: "production"
};

// Це викликає помилку TypeError: Assignment to constant variable:
// systemSettings = { version: "2.0.0" };

// Але пряма модифікація внутрішнього стану працює безперешкодно!
systemSettings.version = "2.0.0";
systemSettings.debugMode = true;
delete systemSettings.environment;

console.log(systemSettings);
// { version: '2.0.0', debugMode: true }
```

Ключове слово `const` захищає **лише зв'язку змінної у стеку**: воно гарантує, що змінна завжди посилатиметься на одну й ту саму адресу в купі пам'яті. Проте сама купа залишається абсолютно відкритою для додавання, видалення та зміни властивостей.

У великих додатках неконтрольовані мутації призводять до так званого ефекту «примарної дії на відстані» (Spooky Action at a Distance), коли зміна об'єкта в одному модулі неочікувано ламає роботу зовсім іншого компонента.

### 6.2. Рівні захисту в стандарті ECMAScript

Для контролю мутабельності об'єктів стандарт JavaScript пропонує три ступені захисту за наростанням суворості.

Ступені захисту об'єктів:
- `Object.preventExtensions(obj)` - заборона розширення; забороняє додавати нові властивості до об'єкта, проте дозволяє змінювати значення існуючих полів та видаляти їх через `delete`;
- `Object.seal(obj)` - запечатування; забороняє додавати нові та видаляти існуючі властивості (робить усі поля `configurable: false`), але дозволяє змінювати значення існуючих властивостей;
- `Object.freeze(obj)` - повне заморожування; найвищий ступінь захисту; забороняє додавання нових властивостей, видалення існуючих та зміну значень існуючих полів (робить їх `writable: false, configurable: false`).

```javascript
"use strict"; // у суворому режимі порушення захисту викидає виняток TypeError

const siteConfig = {
  apiUrl: "https://api.techshop.ua/v1",
  timeout: 5000
};

// Заморожуємо об'єкт:
Object.freeze(siteConfig);

console.log(Object.isFrozen(siteConfig)); // true

// Спроба змінити поле викине помилку (у non-strict режимі тихо проігнорується):
try {
  siteConfig.timeout = 10000;
} catch (error) {
  console.error("Мутація заборонена:", error.message);
}
```

### 6.3. Реалізація глибокого заморожування (Deep Freeze)

Аналогічно до поверхневого копіювання, метод `Object.freeze()` є **поверхневим (Shallow Freeze)**. Якщо об'єкт містить вкладені об'єкти або масиви, вони залишаються повністю мутабельними:

```javascript
const companyInfo = Object.freeze({
  title: "TechShop Inc.",
  contacts: {
    city: "Харків",
    phone: "102"
  }
});

companyInfo.contacts.phone = "0-800-500-100"; // Працює без помилок! Вкладений об'єкт не заморозився!
console.log(companyInfo.contacts.phone); // "0-800-500-100"
```

Щоб повністю убезпечити структури конфігурацій чи початковий стан додатку, розробники пишуть рекурсивну функцію `deepFreeze`:

```javascript
function deepFreeze(targetObject) {
  // Отримуємо всі власні імена властивостей:
  const propNames = Object.getOwnPropertyNames(targetObject);

  // Рекурсивно заморожуємо всі вкладені об'єкти:
  for (const name of propNames) {
    const value = targetObject[name];
    if (value && typeof value === "object" && !Object.isFrozen(value)) {
      deepFreeze(value);
    }
  }

  // Заморожуємо сам батьківський об'єкт:
  return Object.freeze(targetObject);
}

// Демонстрація роботи deepFreeze:
const immutableState = deepFreeze({
  appId: "SHOP_APP",
  endpoints: {
    checkout: "/orders/create",
    auth: "/auth/login"
  }
});

// Тепер захищений і внутрішній рівень:
try {
  immutableState.endpoints.checkout = "/hacked";
} catch (e) {
  console.log("Глибоке заморожування спрацювало успішно!");
}
```

## 7. Організація та підготовка даних до роботи з бекендом (Data Preparation for Backend/API)

Коли фронтенд взаємодіє з сервером, обмін інформацією майже завжди відбувається у форматі JSON через HTTP-запити. Проте наївне надсилання об'єктів безпосередньо зі стану компонентів чи полів HTML-форми призводить до помилок архітектури та проблем із безпекою.

### 7.1. Архітектурний шаблон DTO (Data Transfer Object)

**DTO (Об'єкт передачі даних)** — це простий структурний об'єкт, який не містить бізнес-логіки та поведінкових методів, а призначений виключно для транспортування даних через мережу між клієнтом і сервером.

Чому клієнтський стан не повинен надсилатися на сервер «як є»:
- внутрішній стан інтерфейсу містить візуальні поля - наприклад, прапорці `isDropdownOpen`, `isHovered`, активні кроки майстра замовлення, які серверу не потрібні;
- клієнтські кешовані дані є надлишковими - наприклад, об'єкт товару в кошику містить повний опис, URL-картинки, відгуки та рейтинг; серверу для створення замовлення потрібні лише `productId` та `quantity`;
- безпека та цілісність бізнес-правил - клієнт ніколи не повинен передавати на бекенд фінальну ціну зі знижкою, яку він порахував сам у браузері, оскільки зловмисник може підробити запит і вказати ціну в 1 гривню; остаточний розрахунок вартості завжди здійснює бекенд;
- розбіжність структур і форматів - клієнт може зберігати дату у вигляді об'єкта `Date`, а бекенд вимагати рядок формату ISO 8601 чи Unix Timestamp.

```text
Клієнтський стан UI (Кошик):              Чистий DTO для відправки на POST /api/orders:
┌───────────────────────────────────┐     ┌───────────────────────────────────────────┐
│ id: "cart-1"                      │     │ {                                         │
│ isCartModalOpen: false            │     │   "customer_phone": "+380501234567",     │
```

### 7.2. Трансляція стилів найменування (camelCase проти snake_case)

В індустрії веб-розробки існують усталені традиції оформлення назв ключів:
- мова JavaScript та веб-браузери за замовчуванням орієнтовані на стиль **camelCase** (`customerId`, `deliveryDate`, `totalPrice`);
- реляційні бази даних (PostgreSQL, MySQL) та популярні серверні мови/фреймворки (PHP/Laravel, Python/Django) традиційно використовують стиль **snake_case** (`customer_id`, `delivery_date`, `total_price`).

Для забезпечення чистоти коду клієнтський JavaScript повинен всередині працювати зі звичним `camelCase`, а перед відправкою автоматично транслювати ключі у `snake_case`.

Реалізуємо універсальні функції трансформації ключів:

```javascript
// Конвертація одного рядка: "shippingAddressId" -> "shipping_address_id"
function toSnakeCase(str) {
  return str.replace(/([A-Z])/g, "_$1").toLowerCase();
}

// Конвертація одного рядка: "shipping_address_id" -> "shippingAddressId"
function toCamelCase(str) {
  return str.replace(/_([a-z])/g, (_, letter) => letter.toUpperCase());
}

// Рекурсивна трансформація всіх ключів об'єкта або масиву об'єктів:
function convertKeysToSnakeCase(data) {
  if (Array.isArray(data)) {
    return data.map(item => convertKeysToSnakeCase(item));
  }
  
  if (data !== null && typeof data === "object" && !(data instanceof Date)) {
    return Object.fromEntries(
      Object.entries(data).map(([key, value]) => [
        toSnakeCase(key),
        convertKeysToSnakeCase(value)
      ])
    );
  }
  
  return data;
}

// Демонстрація конвертації перед відправкою на сервер:
const clientPayload = {
  customerProfile: {
    firstName: "Михайло",
    phoneNumber: "+380671112233"
  },
  deliveryMethod: "nova_poshta",
  estimatedDeliveryDate: "2026-04-10"
};

const serverPayload = convertKeysToSnakeCase(clientPayload);
console.log(serverPayload);
// {
//   customer_profile: {
//     first_name: 'Михайло',
//     phone_number: '+380671112233'
//   },
//   delivery_method: 'nova_poshta',
//   estimated_delivery_date: '2026-04-10'
// }
```

### 7.3. Нормалізація, очищення та приведення типів (Sanitization & Normalization)

Отримані з елементів форми значення (`HTMLInputElement.value`) завжди повертаються у вигляді **рядків (`String`)**, навіть якщо інпут мав тип `type="number"` або `type="range"`.

Перед формуванням DTO дані мають бути санітизовані та нормалізовані:
- рядки очищаються від випадкових пробілів на кінцях за допомогою `.trim()`;
- числові поля обов'язково конвертуються за допомогою `Number()`, `parseInt()` або `parseFloat()` з обов'язковою перевіркою `!Number.isNaN()`;
- порожні необов'язкові текстові поля переводяться в `null`, щоб сервер не записував у базу порожні рядки `""`;
- дати приводяться до строгого формату UTC ISO 8601 (`date.toISOString()`).

## 8. Практичний кейс проєкту TechShop: Сервісний шар підготовки замовлення (Order Processing Service)

Об'єднаємо всі вивчені інструменти — деструктуризацію, глибоке клонування через `structuredClone`, конвеєрну фільтрацію ключів, захист від мутацій та генерацію DTO — у єдиний повноцінний сервісний модуль оформлення замовлення інтернет-магазину **TechShop**.

Цей модуль моделює поведінку перед відправкою даних за допомогою `fetch` на серверний ендпоінт `POST /api/v1/orders`.

```javascript
/**
 * Сервісний модуль оформлення та підготовки замовлень TechShop
 */
class OrderProcessingService {
  /**
   * Створення сервісу з базовими системними налаштуваннями
   * Використовуємо деструктуризацію Options Object із дефолтними значеннями
   */
  constructor({
    apiEndpoint = "https://api.techshop.ua/v1/orders",
    allowedPaymentMethods = ["card_online", "cash_on_delivery", "apple_pay"],
    currency = "UAH"
  } = {}) {
    this.apiEndpoint = apiEndpoint;
    this.currency = currency;
    // Заморожуємо список дозволених методів оплати від випадкової мутації
    this.allowedPaymentMethods = Object.freeze([...allowedPaymentMethods]);
  }

  /**
   * Головний метод створення DTO замовлення
   * @param {Object} rawFormData - сирі дані з полів HTML-форми
   * @param {Array} rawCartItems - масив товарів із кошика (з localStorage)
   * @returns {Object} чистий, безпечний DTO для відправки на сервер
   */
  buildOrderDTO(rawFormData, rawCartItems) {
    // 1. Захист вихідних даних: глибоко клонуємо кошик, щоб не пошкодити клієнтський стан
    const safeCart = structuredClone(rawCartItems);

    // 2. Деструктуризація сирих даних форми з перейменуванням та значеннями за замовчуванням
    const {
      client_name: rawName = "",
      client_phone: rawPhone = "",
      client_email: rawEmail = "",
      delivery_city: rawCity = "",
      delivery_branch: rawBranch = "",
      payment_type: rawPayment = "card_online",
      order_comment: rawComment = "",
      promo_code: rawPromo = null
    } = rawFormData;

    // 3. Санітизація та перевірка даних клієнта
    const cleanCustomer = {
      fullName: rawName.trim(),
      phone: rawPhone.replace(/[^\d+]/g, "").trim(),
      email: rawEmail.trim().toLowerCase()
    };

    if (!cleanCustomer.fullName || cleanCustomer.phone.length < 10) {
      throw new Error("Некоректні персональні дані покупця!");
    }

    // 4. Валідація методу оплати за білим списком (Allowlist)
    const paymentMethod = this.allowedPaymentMethods.includes(rawPayment)
      ? rawPayment
      : "card_online";

    // 5. Очищення та нормалізація кошика: вилучаємо лише необхідні серверу поля
    // Використовуємо деструктуризацію у параметрах колбека map()
    const cleanItems = safeCart.map(({ id, quantity, price }) => {
      const parsedQty = parseInt(quantity, 10);
      const parsedPrice = parseFloat(price);

      if (Number.isNaN(parsedQty) || parsedQty <= 0) {
        throw new Error(`Некоректна кількість товару з ID ${id}`);
      }

      return {
        productId: id,
        quantity: parsedQty,
        clientUnitCost: Number(parsedPrice.toFixed(2)) // ціна для звірки на бекенді
      };
    });

    if (cleanItems.length === 0) {
      throw new Error("Неможливо оформити порожнє замовлення!");
    }

    // 6. Формування плоского або структурованого клієнтського об'єкта
    const clientOrderObject = {
      customer: cleanCustomer,
      delivery: {
        city: rawCity.trim(),
        branchId: parseInt(rawBranch, 10) || null
      },
      paymentMethod,
      comment: rawComment.trim() || null,
      promoCode: rawPromo ? rawPromo.trim().toUpperCase() : null,
      items: cleanItems,
      currency: this.currency,
      clientTimestamp: new Date().toISOString()
    };

    // 7. Видаляємо null-властивості на вищому рівні доставки чи промокоду через конвеєр
    const sanitizedOrder = Object.fromEntries(
      Object.entries(clientOrderObject).filter(([_, value]) => value !== null)
    );

    // 8. Трансляція ключів об'єкта з camelCase у snake_case для бекенда
    const serverPayloadDTO = convertKeysToSnakeCase(sanitizedOrder);

    // 9. Заморожуємо згенерований DTO перед поверненням
    return deepFreeze(serverPayloadDTO);
  }

  /**
   * Метод підготовки фінального JSON Payload та заголовків для HTTP Fetch
   */
  prepareRequestPayload(orderDTO) {
    return {
      url: this.apiEndpoint,
      method: "POST",
      headers: {
        "Content-Type": "application/json; charset=UTF-8",
        "Accept": "application/json"
      },
      // Серіалізуємо перевірений і заморожений DTO у чистий JSON-рядок:
      body: JSON.stringify(orderDTO)
    };
  }

  /**
   * Безпечна обробка відповіді бекенда за допомогою нових можливостей ES
   */
  parseServerResponse(rawJsonResponse) {
    // Безпечне зчитування через оператори ?. та ??
    const orderId = rawJsonResponse?.data?.order_id ?? "UNKNOWN";
    const status = rawJsonResponse?.status ?? 500;
    const isSuccess = rawJsonResponse?.success === true;

    // Перевірка наявності властивості помилки через Object.hasOwn:
    if (!isSuccess || Object.hasOwn(rawJsonResponse, "error")) {
      const errorMessage = rawJsonResponse?.error?.message ?? "Помилка обробки замовлення сервером";
      return {
        success: false,
        error: errorMessage
      };
    }

    return {
      success: true,
      orderId,
      status,
      confirmationMessage: `Дякуємо! Ваше замовлення #${orderId} успішно прийнято.`
    };
  }
}
```

## Висновки

- посилальна модель даних - примітиви передаються за значенням і зберігаються у стеку, тоді як об'єкти розташовані в купі пам'яті (Heap) і копіюються за адресою посилання; порівняння через `===` перевіряє рівність адрес у пам'яті, а не ідентичність вмісту;
- сучасні синтаксичні оптимізації ES6+ - скорочений запис властивостей (Property Shorthand), методів та обчислювані імена ключів (`[expression]`) зменшують обсяг коду та дозволяють будувати динамічні структури на льоту;
- деструктуризація як стандарт чистого коду - дозволяє вилучати властивості об'єктів та елементи масивів у локальні змінні, перейменовувати їх, встановлювати дефолтні значення та реалізовувати патерн параметрів функцій Options Object;
- неруйнівне оновлення через Spread та Rest - оператор `...` дозволяє створювати нові об'єкти на основі існуючих із точковою зміною полів та ізолювати небажані чи конфіденційні властивості без використання небезпечного оператора `delete`;
- обмеження поверхневого копіювання - оператори Spread та `Object.assign()` дублюють лише перший рівень властивостей, залишаючи вкладені об'єкти та масиви спільними посиланнями на оригінал;
- нативний стандарт глибокого копіювання - глобальна функція `structuredClone()` є сучасною безпечною заміною трюку з `JSON.parse(JSON.stringify())`, коректно обробляючи об'єкти дат, множини, карти та циклічні посилання;
- конвеєрна обробка об'єктів - комбінація методів `Object.entries()` та `Object.fromEntries()` відкриває можливість фільтрувати та трансформувати об'єкти за допомогою потужних методів масивів (`map`, `filter`);
- захист від мутацій - ключове слово `const` блокує лише переприсвоєння змінної, тоді як реальну незмінність вмісту забезпечують методи `Object.freeze()` та рекурсивне заморожування `deepFreeze()`;
- проектування DTO перед взаємодією з бекендом - клієнтський стан повинен обов'язково очищатися від зайвих UI-полів, нормалізуватися, валідуватися та транслюватися у відповідну конвенцію найменування ключів (наприклад, snake_case) перед серіалізацією в JSON.

## Запитання для самоперевірки

- У чому полягає відмінність між збереженням примітивних типів даних і об'єктів в оперативній пам'яті (Stack vs Heap)?
- Чому вираз `{ a: 1 } === { a: 1 }` повертає `false`, а присвоєння `const b = a` призводить до зміни об'єкта `a` при модифікації `b`?
- Як працює деструктуризація об'єкта з перейменуванням властивості та одночасним встановленням значення за замовчуванням?
- У чому полягає перевага патерну передачі аргументів Options Object над класичними позиційними параметрами функцій?
- Чому оператор розпакування `{ ...product }` називають поверхневою копією (Shallow Copy) і яка небезпека виникає при зміні його вкладеного масиву або об'єкта?
- Які критичні обмеження та недоліки має метод глибокого копіювання через `JSON.parse(JSON.stringify(obj))`?
- Які переваги надає нативна функція `structuredClone()` і які типи даних вона відмовляється клонувати, викидаючи виняток `DataCloneError`?
- Як за допомогою методів `Object.entries()` та `Object.fromEntries()` видалити з об'єкта всі властивості, значення яких дорівнюють `null` або `""`?
- Чому ключове слово `const` не захищає властивості об'єкта від зміни і в чому полягає різниця між методами `Object.seal()` та `Object.freeze()`?
- Що таке DTO (Data Transfer Object) і чому клієнтський стан кошика покупок не можна надсилати на бекенд у сирому вигляді без трансформації та очищення?
