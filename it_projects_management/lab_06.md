# Лабораторна робота №6 (2 години)

**Тема:** Декомпозиція робіт (WBS) на основі користувацьких історій

Практика багаторівневої структуризації обсягу проєкту (Scope Management): систематичний перехід від користувацьких вимог (User Stories та Use Cases з Лабораторної роботи №5) до ієрархічної структури робіт (Work Breakdown Structure), перевірка "Правила 100%" та "Правила 8/80", складання Словника WBS (WBS Dictionary).

**Мета:** Навчитися трансформувати функціональні специфікації та User Stories у повну деревоподібну структуру конкретних технічних пакетів робіт (Work Packages), закріплювати інженерні зони відповідальності та формувати основу для подальшого оцінювання строків і бюджету IT-проєкту.

**Технологічний стек:** Draw.io / Miro / Lucidchart (для графічної схеми дерева WBS) + Google Docs / Microsoft Word / Excel (для словника WBS).

---

## Завдання

У Лабораторній роботі №5 ви сформували базу вимог для свого IT-проєкту: написали 3 деталізовані User Stories із критеріями приймання (Acceptance Criteria) у форматі Gherkin (Given-When-Then) та описали складний Use Case.

Тепер ці вимоги необхідно декомпозувати на конкретні інженерні задачі для команди розробки. Вам потрібно побудувати повну деревоподібну структуру робіт проєкту (WBS) та оформити формальний опис для кінцевих пакетів робіт.

### Перелік завдань:

1. Побудувати графічну діаграму WBS (мінімум 3–4 рівні глибини) з прямою інтеграцією модулів та User Stories з Лабораторної №5.
2. Провести валідацію виділених пакетів робіт (Work Packages) за "Правилом 100%" та "Правилом 8/80 годин".
3. Скласти паспорт-словник WBS (WBS Dictionary) для двох ключових пакетів робіт різної технічної спеціалізації (наприклад, Backend API та Frontend UI).

## Хід виконання роботи

### Крок 1. Графічна побудова WBS на основі вимог Лабораторної №5

Ієрархічна структура робіт (WBS) організовує та визначає весь обсяг робіт проєкту. Кожен наступний рівень представляє все більш деталізований опис елементів.

Дотримуйтесь **Правила 100%**: сума дочірніх елементів на кожному рівні повинна повністю покривати батьківський блок (без пропусків та без зайвих робіт, які не узгоджені зі стейкхолдерами):

- **Рівень 1 (Корінь):** Назва вашого проєкту (наприклад: *1.0 Інформаційна система "SmartCity Delivery"*).
- **Рівень 2 (Фази або великі підсистеми):** Основні блоки:
  - *1.1 Дослідження та проєктування архітектури*;
  - *1.2 Модуль авторизації та облікових записів* (сюди входять вимоги з Лаб №5);
  - *1.3 Каталог товарів / послуг*;
  - *1.4 Модуль оформлення замовлення та оплати*;
  - *1.5 Комплексне тестування та розгортання*.
- **Рівень 3 (Компоненти та вимоги):** Декомпозиція на базі ваших User Stories з Лаб №5. Наприклад, модуль 1.4 розбивається на:
  - *1.4.1 Корзина користувача (User Story 1)*;
  - *1.4.2 Інтеграція платіжного шлюзу (User Story 2)*;
  - *1.4.3 Сповіщення клієнта (Email/SMS)*.
- **Рівень 4 (Пакети робіт — Work Packages):** Кінцеві інженерні задачі, які передаються конкретному фахівцю. Наприклад, блок 1.4.2 розбивається на:
  - *1.4.2.1 Розробка Backend API ендпоінтів для отримання платіжного токена*;
  - *1.4.2.2 Верстка платіжної форми на клієнті (Web/Mobile)*;
  - *1.4.2.3 Обробка Webhook-відповідей платіжної системи та збереження чеків у БД*.

_Побудуйте схему в Draw.io або Miro та додайте експортоване зображення у звіт._

### Крок 2. Валідація пакетів робіт за "Правилом 8/80"

Пакет робіт (Work Package) — це атомарний елемент на самому низу дерева WBS:

- Робота не повинна бути надто дрібною (менше 8 годин / 1 робочого дня), інакше менеджер потоне в мікроменеджменті;
- Робота не повинна бути надто великою (понад 80 годин / 10 робочих днів), оскільки для неї неможливо точно оцінити ризики та відстежити статус виконання.

Оберіть зі створеного дерева 4 пакети робіт різного спрямування (Backend, Frontend, QA, DevOps). Для кожного вкажіть:
1. Повний код WBS (наприклад, 1.2.1.3);
2. Назву задачі;
3. Приблизну планову тривалість у годинах (перевірте діапазон 8–80 годин);
4. Призначену технічну роль виконавця.

### Крок 3. Складання Словника WBS (WBS Dictionary)

Словник WBS деталізує зміст пакета робіт, усуваючи неоднозначність між бізнес-аналітиком, розробником та тестувальником.

Оберіть **2 пакети робіт** з Кроку 2 і детально заповніть для них шаблон:

| Параметр Словника WBS | Пакет робіт №1 (Backend) | Пакет робіт №2 (Frontend / Client) |
| :--- | :--- | :--- |
| **Код та назва WBS:** | 1.4.2.1 REST API платіжного шлюзу | 1.4.2.2 Платіжний UI-екран |
| **Батьківська User Story (Лаб №5):** | US-02 "Оплата замовлення банківською карткою" | US-02 "Оплата замовлення банківською карткою" |
| **Технічний опис задачі:** | Реалізація контролера платежів, шифрування токенів, взаємодія з LiqPay/Stripe SDK | Верстка адаптивної форми оплати, валідація полів карти за алгоритмом Луна |
| **Відповідальна роль:** | Backend Developer (Node.js / Java / Go) | Frontend Developer (React / Vue / Flutter) |
| **Критерії завершення (DoD / Acceptance):** | Код покритий unit-тестами на 80%, API задокументовано в Swagger, статус 200 OK | Форма валідує поля на клієнті, плавний лоадер при затримці, немає помилок у консолі |
| **Необхідні ресурси та залежності:** | Доступ до Sandbox API платіжного сервісу | Готовий макет у Figma, опублікований ендпоінт бекенду |
| **Оцінка трудомісткості:** | 24 години | 16 годин |

## Контрольні запитання

1. У чому полягає суть "Правила 100%" при побудові WBS та як воно запобігає розширенню меж проєкту (Scope Creep)?
2. Чому пакети робіт (Work Packages) не рекомендується дробити менше 8 годин або об'єднувати у блоки понад 80 годин?
3. Чим відрізняється дерево WBS від організаційної структури команди (OBS) та від беклогу задач у Scrum?
4. Яку роль відіграє Словник WBS (WBS Dictionary) у врегулюванні спорів щодо приймання робіт замовником?

## Критерії оцінювання

- Побудова багаторівневої структури WBS із дотриманням правила 100%: до 40 балів;
- Чітка прив'язка до User Stories з Лабораторної №5 та валідація правила 8/80: до 25 балів;
- Складання детального Словника WBS (WBS Dictionary) для 2 пакетів робіт: до 25 балів;
- Відповіді на контрольні запитання: до 10 балів.
