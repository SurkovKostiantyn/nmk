# Лекція 7 (2 години). Рендеринг списків, алгоритм ключів (Keys) та патерни умовного відображення

## План лекції

- 1. Декларативний рендеринг колекцій даних: трансформація масивів за допомогою функціонального методу `map()`;
- 2. Алгоритмічна роль пропу `key` у механізмі Reconciliation: відстеження переміщення, вставки та видалення вузлів;
- 3. Чому використання індексу масиву як ключа (`key={index}`) є небезпечним антипатерном: аналіз багів втрати локального стану;
- 4. Стратегії вибору та генерації стабільних ключів: ID сутностей бази даних, `crypto.randomUUID()` та синтетичні ключі;
- 5. Патерни умовного відображення: тернарний оператор, патерн раннього повернення (Early Return) та оператор нульового злиття (`??`);
- 6. Проєктування інтерфейсних станів: обробка порожніх колекцій (Empty States) та патерн скелетон-завантаження (Skeleton UI).

## Перелік умовних скорочень

- **UI** (User Interface) — користувацький інтерфейс;
- **DOM** (Document Object Model) — об'єктна модель документа браузера;
- **vDOM** (Virtual Document Object Model) — віртуальна об'єктна модель документа у пам'яті;
- **UUID** (Universally Unique Identifier) — універсальний унікальний ідентифікатор;
- **FSM** (Finite State Machine) — скінченний автомат станів.

## Вступ

Більшість веб-інтерфейсів працюють із динамічними колекціями інформації: стрічками новин, каталогами товарів, коментарями, таблицями аналітики та списками завдань. У декларативній парадигмі React розробник не маніпулює циклами створення вузлів вручну, а трансформує масив сирих даних у масив елементів Virtual DOM.

У цій лекції детально аналізується механізм рендерингу списків, розкривається фундаментальна алгоритмічна роль пропу `key` для процесу Reconciliation, розбираються приховані баги використання індексів масиву як ключів та наводяться кращі інженерні практики реалізації умовного відображення інтерфейсу (порожні стани, помилки, скелетон-завантажувачі).

## 1. Декларативний рендеринг колекцій даних: метод `map()`

В імперативному JavaScript для виведення списку використовувалися цикли `for` або `forEach` із ручним додаванням вузлів у DOM (`list.appendChild(item)`).

У React діє принцип **декларативної трансформації**:
- ми беремо масив об'єктів даних JavaScript;
- за допомогою чистого функціонального методу масиву `map()` перетворюємо кожен об'єкт на JSX-елемент;
- React автоматично бере отриманий масив React-елементів і відмальовує його у браузері.

```tsx
interface Product {
  id: string;
  title: string;
  price: number;
}

const PRODUCTS: Product[] = [
  { id: 'p1', title: 'Механічна клавіатура', price: 2800 },
  { id: 'p2', title: 'Бездротова миша', price: 1400 },
  { id: 'p3', title: 'USB-C хаб', price: 950 },
];

export function ProductList() {
  return (
    <ul className="product-list">
      {PRODUCTS.map((product) => (
        <li key={product.id} className="product-item">
          <span className="product-title">{product.title}</span>
          <strong className="product-price">{product.price} грн</strong>
        </li>
      ))}
    </ul>
  );
}
```

Чому `map()`, а не `forEach()`?
Метод `forEach()` нічого не повертає (`undefined`) і слугує для виконання побічних ефектів. Метод `map()` є чистою функцією, яка повертає **новий масив**, що ідеально відповідає вимогам JSX до виразів (Expressions).

## 2. Алгоритмічна роль пропу `key` у механізмі Reconciliation

Коли ви рендерите список без передачі спеціального пропу `key`, React виводить у консоль попередження:
`Warning: Each child in a list should have a unique "key" prop.`

Чому `key` є критично важливим для швидкодії та коректності додатку?

### Як React порівнює дочірні елементи без ключів

Уявіть список із двох елементів:

```html
<!-- Старе дерево: -->
<ul>
  <li>Тарас</li>
  <li>Олена</li>
</ul>
```

Користувач додав новий запис "Богдан" у **початок списку**:

```html
<!-- Нове дерево: -->
<ul>
  <li>Богдан</li>
  <li>Тарас</li>
  <li>Олена</li>
</ul>
```

Без ключів React порівнює дочірні елементи суто за їхнім порядковим номером (індексом):
- елемент #0: був "Тарас", став "Богдан" -> React вирішує: *"текст першого li змінився, перемальовую текстовий вузол"*;
- елемент #1: була "Олена", став "Тарас" -> React вирішує: *"текст другого li змінився, перемальовую текстовий вузол"*;
- елемент #2: раніше не існував, тепер "Олена" -> React вирішує: *"створюю новий li і вставляю в кінець"*.

Результат: React мутував усі існуючі DOM-вузли замість того, щоб просто вставити один новий елемент у початок. Для списку з 1000 елементів це призводить до катастрофічного падіння швидкодії (Reflow/Repaint).

### Як функціонує алгоритм із ключами (`key`)

Ключ `key` — це унікальний рядковий або числовий ідентифікатор, який слугує "паспортом" конкретного елемента між рендерингами:

```jsx
<ul>
  <li key="user-1">Тарас</li>
  <li key="user-2">Олена</li>
</ul>

<!-- Новий рендер із додаванням Богдана: -->
<ul>
  <li key="user-3">Богдан</li>
  <li key="user-1">Тарас</li>
  <li key="user-2">Олена</li>
</ul>
```

Завдяки ключам алгоритм Reconciliation миттєво розуміє:
- елемент із ключем `"user-1"` не змінився, він просто перемістився з позиції 0 на позицію 1;
- елемент із ключем `"user-2"` не змінився, він перемістився з позиції 1 на позицію 2;
- з'явився новий ключ `"user-3"`, для якого потрібно створити рівно один новий DOM-вузол і помістити його на початок.

Ключі дозволяють React відстежувати рух елементів, їх пересортування, видалення та додавання з мінімальною кількістю операцій над реальним DOM.

## 3. Чому використання індексу масиву як ключа є небезпечним антипатерном

Найпоширенішою помилкою серед початківців є спроба позбутися попередження React за допомогою передачі індексу масиву:

```jsx
// НЕБЕЗПЕЧНИЙ АНТИПАТЕРН:
{items.map((item, index) => (
  <TodoItem key={index} data={item} />
))}
```

### Коли індекс призводить до критичних багів?

Якщо елементи списку мають **власний локальний стан (`useState`)** або є некерованими інпутами (наприклад, чекбокси, поля введення тексту), використання індексів ламає інтерфейс при зміні порядку або видаленні.

Сценарій катастрофи:
- у вас є список із трьох завдань: Завдання А (індекс 0), Завдання Б (індекс 1), Завдання В (індекс 2);
- користувач поставив галочку (чекбокс) біля Завдання А; стан чекбокса зберігається всередині DOM-вузла або локального `useState` компонента `<TodoItem key={0} />`;
- користувач видаляє Завдання А зі списку;
- тепер Завдання Б стає першим і **отримує індекс 0**!
- React бачить: *"компонент із key={0} як був на екрані, так і залишився, я просто передам йому нові пропси"*;
- внутрішній стан компонента не скидається! У результаті галочка, яка належала видаленому Завданню А, раптово опиняється біля Завдання Б!

Коли індекси допустимі?
Використання `key={index}` дозволене виключно тоді, коли одночасно виконуються три умови:
- список є абсолютно статичним (ніколи не фільтрується, не сортується і не змінює склад);
- елементи не мають власного локального стану;
- елементи не містять некерованих полів форм.

## 4. Стратегії вибору та генерації стабільних ключів

Вимоги до ключа:
- **Унікальність серед сусідів (Unique Among Siblings):** Ключі мають бути унікальними лише в межах конкретного масиву. Два різні списки можуть мати однакові ключі без конфліктів.
- **Стабільність у часі (Stable Across Rerenders):** Ключ не повинен змінюватися між повторними рендерингами одного й того самого об'єкта.

### Чому категорично заборонено генерувати ключі "на льоту"?

```jsx
// КАТАСТРОФІЧНИЙ АНТИПАТЕРН:
{items.map((item) => (
  <ListItem key={Math.random()} item={item} /> // АБО key={crypto.randomUUID()}
))}
```

Що відбувається під час кожного рендерингу:
- функція `Math.random()` генерує нове випадкове число;
- React порівнює старе дерево з новим і бачить, що жоден старий ключ не збігся з новим;
- React вирішує, що **всі старі компоненти видалено, і створює весь список з нуля**;
- повністю втрачається фокус у полях введення, скидаються всі локальні стани, а браузер починає гальмувати через постійне перемальовування.

### Правильні джерела ключів

- ID із бази даних - первинні ключі (`id`, `uuid`, `_id`), отримані від бекенду — це найкраще та найнадійніше джерело;
- генерація ID під час створення об'єкта - якщо елемент створюється на клієнті (наприклад, додається нове завдання через форму), генеруйте унікальний ідентифікатор **один раз під час створення об'єкта** за допомогою стандарту `crypto.randomUUID()`:

```tsx
const handleAddTodo = (text: string) => {
  const newTodo = {
    id: crypto.randomUUID(), // Генерується один раз і фіксується у стані!
    text,
    completed: false,
  };
  setTodos((prev) => [...prev, newTodo]);
};
```

## 5. Патерни умовного відображення інтерфейсу

Умовний рендеринг дозволяє показувати різні фрагменти інтерфейсу залежно від поточного стану (авторизований користувач, триває завантаження, виникла помилка).

### Патерн 1. Раннє повернення (Early Return)

Якщо весь компонент не повинен відображатися або має відобразити альтернативний екран (наприклад, стан помилки чи лоадер), використовується патерн раннього повернення з функції:

```tsx
export function UserProfile({ user, isLoading, error }: UserProfileProps) {
  if (isLoading) {
    return <div className="spinner">Завантаження профілю...</div>;
  }

  if (error) {
    return <div className="error-alert">Помилка: {error}</div>;
  }

  if (!user) {
    return null; // Нічого не рендеримо
  }

  // Основний рендеринг за наявності валідних даних
  return (
    <div className="profile-card">
      <h2>{user.name}</h2>
      <p>{user.email}</p>
    </div>
  );
}
```

Переваги Early Return:
- чистий код без громіздких вкладених умов всередині основної верстки;
- легке читання та розуміння крайніх випадків (Edge Cases).

### Патерн 2. Тернарний оператор (`condition ? A : B`)

Тернарний оператор є основним інструментом перемикання між двома станами всередині JSX-розмітки:

```tsx
<button className={isSubscribed ? 'btn-secondary' : 'btn-primary'}>
  {isSubscribed ? 'Відписатися' : 'Підписатися'}
</button>
```

### Патерн 3. Логічний оператор `&&` та оператор нульового злиття `??`

Оператор `&&` використовується, коли елемент потрібно показати за умови істинності, або не показувати взагалі:

```tsx
<div className="header">
  <h1>Панель керування</h1>
  {isAdmin && <button>Налаштування системи</button>}
</div>
```

Оператор `??` (Nullish Coalescing) використовується для виведення дефолтного значення, якщо поле дорівнює `null` або `undefined`:

```tsx
<p>Опис: {product.description ?? 'Опис відсутній'}</p>
```

## 6. Проєктування інтерфейсних станів: Empty States та Skeleton UI

Професійний інтерфейс повинен коректно реагувати на будь-який стан списку: завантаження, порожній результат фільтрації чи наявність даних.

### Обробка порожніх колекцій (Empty States)

Замість того, щоб показувати користувачеві порожній білий екран при нульовій кількості товарів або завдань, обов'язково проєктується інформативний Empty State:

```tsx
export function TaskList({ tasks, onAddTask }: TaskListProps) {
  if (tasks.length === 0) {
    return (
      <div className="empty-state">
        <img src="/empty-folder.svg" alt="Порожньо" />
        <h3>Завдань не знайдено</h3>
        <p>Створіть своє перше завдання або змініть параметри пошуку.</p>
        <button onClick={onAddTask}>Створити завдання</button>
      </div>
    );
  }

  return (
    <ul>
      {tasks.map((task) => (
        <li key={task.id}>{task.title}</li>
      ))}
    </ul>
  );
}
```

### Патерн скелетон-завантаження (Skeleton UI)

Замість звичайного кругового спінера, сучасні додатки (YouTube, Facebook, LinkedIn) використовують **Skeleton UI** — мерехтливі сірі блоки, що повторюють геометрію майбутнього контенту:
- знижує сприйнятий користувачем час очікування (Perceived Performance);
- усуває стрибки макета (Cumulative Layout Shift — CLS), оскільки скелетон заздалегідь резервує точні геометричні розміри майбутнього блоку.

```tsx
function ProductCardSkeleton() {
  return (
    <div className="card animate-pulse">
      <div className="bg-slate-200 h-48 rounded-md mb-4" />
      <div className="bg-slate-200 h-6 w-3/4 rounded mb-2" />
      <div className="bg-slate-200 h-4 w-1/2 rounded" />
    </div>
  );
}
```

## Висновки

- декларативність методу `map()` - перетворення масивів даних у масиви React-елементів є стандартом побудови колекцій інтерфейсу;
- критична роль `key` - ключ є ідентифікатором узгодження для алгоритму Reconciliation, що мінімізує операції перемалювання DOM при вставках, сортуванні та видаленні;
- небезпека індексів масиву - використання `key={index}` призводить до перенесення чужого локального стану між елементами при зміні порядку та видаленні;
- стабільність ключів - генерація ключів "на льоту" (через `Math.random()`) змушує React знищувати та створювати дерево з нуля під час кожного рендерингу;
- патерни умовного відображення - патерн Early Return структурує код обробки завантаження та помилок, а тернарні оператори та `&&` керують точковим відображенням у розмітці;
- якість UX - проєктування інформативних порожніх станів (Empty States) та скелетонів завантаження формує преміальний рівень надійності веб-додатку.

## Запитання для самоперевірки

- чому функціональний метод масиву `map()` підходить для генерації списків у JSX, а метод `forEach()` — ні;
- як саме алгоритм Reconciliation використовує проп `key` для оптимізації оновлення DOM при вставці елемента в початок списку;
- опишіть сценарій виникнення бага зі збереженням чужого стану форми при використанні індексів масиву як ключів (`key={index}`);
- чому категорично заборонено генерувати значення для пропу `key` за допомогою функції `Math.random()` всередині тіла компонента;
- у чому полягає перевага патерна раннього повернення (Early Return) при обробці станів завантаження або помилок;
- чому використання скелетонів завантаження (Skeleton UI) є кращою практикою, ніж використання простого спінера по центру сторінки?
