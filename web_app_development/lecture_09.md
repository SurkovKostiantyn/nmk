- 5. Проблема застарілих замикань (Stale Closures) та подвійне виконання ефектів у React StrictMode;

## Перелік умовних скорочень

- **UI** (User Interface) — користувацький інтерфейс;
- **DOM** (Document Object Model) — об'єктна модель документа браузера;
- **vDOM** (Virtual Document Object Model) — віртуальна об'єктна модель документа;
- **API** (Application Programming Interface) — інтерфейс прикладного програмування;
- **HTTP** (HyperText Transfer Protocol) — мережевий протокол передачі гіпертексту.

## Вступ

Функціональні компоненти React за своєю фундаментальною філософією є чистими функціями: вони приймають пропси й стан та повертають JSX-розмітку. Проте реальний світ вимагає взаємодії із зовнішніми "нечистими" системами: надсилання HTTP-запитів до сервера, підключення WebSocket-з'єднань, пряме читання геопозиції з браузерного API чи запуск таймерів. Усі ці операції називаються **побічними ефектами (Side Effects)**.

У цій лекції детально аналізується фазова модель рендерингу React, розкривається внутрішня робота хука `useEffect`, пояснюється механізм функцій очищення (Cleanup) для запобігання витокам пам'яті, розбирається феномен застарілих замикань (Stale Closures) та наводяться практичні інженерні правила щодо того, коли використання `useEffect` є надлишковим або шкідливим.

## 1. Концепція побічних ефектів у декларативному UI

У математичному сенсі чиста функція не повинна мати жодного впливу на навколишнє середовище, окрім повернення значення.
Що вважається побічним ефектом (Side Effect) у фронтенд-розробці:
- зміна заголовка вкладки браузера (`document.title = 'Нове повідомлення'`);
- запуск таймерів (`setInterval`, `setTimeout`);
- відправка мережевого запиту `fetch()` до зовнішнього REST API;
- ручне додавання глобального слухача подій (`window.addEventListener('resize', ...)`);
- запис або читання даних із `localStorage`.

### Чому не можна виконувати побічні ефекти безпосередньо в тілі компонента?

```tsx
// КАТАСТРОФІЧНИЙ АНТИПАТЕРН:
export function BrokenFeed() {
  const [posts, setPosts] = useState([]);

  // ПРЯМИЙ ВИКЛИК ЕФЕКТУ ПІД ЧАС РЕНДЕРУ:
  fetch('/api/posts')
    .then((res) => res.json())
    .then((data) => setPosts(data)); // ВИКЛИКАЄ НЕСКІНЧЕННИЙ ЦИКЛ!

  return <div>{posts.length} постів</div>;
}
```

Чому цей код заморозить браузер (Infinite Render Loop):
- React викликає `BrokenFeed()`, запускається `fetch()`;
- коли дані приходять, викликається `setPosts(data)`, що змушує React запустити **новий рендеринг**;
- під час нового рендерингу знову викликається функція `BrokenFeed()`, яка знову запускає `fetch()`;
- утворюється нескінченний цикл запитів, який перевантажує мережу та блокує процесор.

Побічні ефекти повинні виконуватися не під час рендерингу, а **після того, як інтерфейс уже успішно відображено на екрані**. Саме цю задачу вирішує хук `useEffect`.

## 2. Життєвий цикл: фаза рендеру (Render Phase) проти фази фіксації (Commit Phase)

React розділяє виконання коду на два чітко розмежованих етапи:

```
[ Фаза 1: Render Phase ]                     [ Фаза 2: Commit Phase ]
Виклик функції компонента                   react-dom оновлює реальний DOM
Генерація Virtual DOM           ───────>    Браузер перемальовує пікселі (Paint)
(Має бути абсолютно чистою!)                Виконання useEffect (Побічні ефекти)
```

- **Render Phase (Фаза рендерингу):** React викликає ваші компоненти, щоб обчислити нове дерево Virtual DOM. Ця фаза може викликатися повторно, ставитися на паузу або перезапускатися конкурентним рушієм. Вона зобов'язана бути чистою від будь-яких побічних ефектів.
- **Commit Phase (Фаза фіксації):** Бібліотека `react-dom` вносить зміни в реальний браузерний DOM.
- **Після Commit Phase:** Браузер відмальовує новий екран, і лише після цього асинхронно викликаються функції, передані в `useEffect`. Це гарантує, що важкі мережеві операції не блокують первинну появу інтерфейсу перед користувачем.

## 3. Анатомія хука `useEffect` та масив залежностей

Синтаксис хука `useEffect`:

```tsx
useEffect(() => {
  // Код побічного ефекту
  return () => {
    // Опціональна функція очищення (Cleanup)
  };
}, [dependency1, dependency2]); // Масив залежностей
```

Поведінка хука повністю визначається його другим аргументом — **масивом залежностей (Dependency Array)**.

### Три сценарії конфігурації масиву залежностей

#### Сценарій 1. Масив залежностей відсутній (`useEffect(fn)`)

```tsx
useEffect(() => {
  console.log('Виконується після КОЖНОГО рендерингу компонента');
});
```

Ефект запускається після першого монтування і після **кожного наступного рендерингу**, викликаного зміною будь-якого стану чи пропсів. Використовується рідко (наприклад, для логування тривалості кожного кадру).

#### Сценарій 2. Порожній масив залежностей (`useEffect(fn, [])`)

```tsx
useEffect(() => {
  console.log('Виконується рівно ОДИН РАЗ після монтування (Mount)');
}, []);
```

Ефект запускається лише один раз, коли компонент уперше з'явився на екрані. Аналог старого методу життєвого циклу `componentDidMount`. Ідеально підходить для глобальної ініціалізації: підключення WebSocket, підписка на події клавіатури, завантаження початкових конфігурацій.

#### Сценарій 3. Масив із конкретними залежностями (`useEffect(fn, [id, query])`)

```tsx
useEffect(() => {
  console.log(`Виконується при монтуванні ТА щоразу, коли змінився id: ${id}`);
}, [id]);
```

React зберігає значення `id` з попереднього рендеру. Під час нового рендеру він порівнює `prevId === nextId` за допомогою `Object.is`:
- якщо `id` збігається — ефект пропускається;
- якщо `id` змінився — ефект виконується наново.

Правило лінтера `react-hooks/exhaustive-deps`:
Будь-яка реактивна змінна (стан або проп), яка використовується всередині тіла `useEffect`, **зобов'язана бути вказана у масиві залежностей**. Приховування залежностей призводить до критичних багів застарілих даних.

## 4. Функція очищення (Cleanup Function) та робота з `AbortController`

Якщо ваш побічний ефект створює довгоживучу підписку або таймер, він залишатиметься в пам'яті браузера навіть після того, як користувач перейде на іншу сторінку і компонент демонтується (Unmount). Це явище називається **витоком пам'яті (Memory Leak)**.

Для запобігання витокам пам'яті ефект може повернути функцію очищення (**Cleanup Function**):

```tsx
export function WindowWidthTracker() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    const handleResize = () => setWidth(window.innerWidth);

    // 1. Створюємо слухач подій
    window.addEventListener('resize', handleResize);

    // 2. Повертаємо функцію очищення:
    return () => {
      // Знімаємо слухач, коли компонент демонтується!
      window.removeEventListener('resize', handleResize);
    };
  }, []); // Порожній масив: підписка при Mount, відписка при Unmount

  return <div>Ширина вікна: {width}px</div>;
}
```

### Коли викликається функція Cleanup?

- при повному демонтуванні компонента (Unmount) з DOM;
- **перед кожним повторним запуском ефекту**, якщо змінилися залежності в масиві! Це дозволяє очистити старий побічний ефект перед створенням нового.

### Скасування асинхронних запитів через `AbortController` (Проблема Race Condition)

Класичний баг "перегонів запитів" (Race Condition):
- користувач швидко перемикає вкладки "Користувач 1" та "Користувач 2";
- запит для Користувача 1 завис на повільній мережі на 3 секунди;
- запит для Користувача 2 повернувся миттєво за 200 мс;
- через 3 секунди повертається повільний запит для Користувача 1 і перезаписує стан! Користувач бачить чужі застарілі дані.

Вирішення за допомогою вбудованого в браузер `AbortController`:

```tsx
useEffect(() => {
  const controller = new AbortController();

  async function fetchUserData() {
    try {
      const res = await fetch(`/api/users/${userId}`, {
        signal: controller.signal, // Передаємо сигнал відміни
      });
      const data = await res.json();
      setUser(data);
    } catch (err: any) {
      if (err.name !== 'AbortError') {
        setError('Помилка завантаження');
      }
    }
  }

  fetchUserData();

  // Функція очищення скасовує попередній запит у мережі!
  return () => {
    controller.abort();
  };
}, [userId]);
```

## 5. Застарілі замикання (Stale Closures) та подвійне монтування у StrictMode

### Проблема застарілих замикань (Stale Closures)

Функції в JavaScript "замикають" змінні з області видимості, у якій вони були створені.
Якщо всередині `useEffect` використовується таймер або колбек, який звертається до стану, але цей стан не додано в залежності:

```tsx
// БАГ ЗАСТАРІЛОГО ЗАМИКАННЯ:
useEffect(() => {
  const timer = setInterval(() => {
    // Тут count НАЗАВЖДИ зафіксований зі значенням 0 із першого рендеру!
    setCount(count + 1); // 0 + 1 = 1 кожну секунду, лічильник зависне на 1!
  }, 1000);

  return () => clearInterval(timer);
}, []); // Порожній масив залежностей
```

Виправлення: використання функціонального оновлення `setCount(prev => prev + 1)` позбавляє від необхідності читати зовнішню змінну `count`.

### Чому React StrictMode викликає ефекти двічі?

У режимі розробки (`<React.StrictMode>`) розробники часто помічають дивну поведінку: `console.log` всередині `useEffect` спрацьовує двічі!
Це не баг, а спеціальна діагностична можливість React:
- React спеціально монтує компонент -> негайно викликає Cleanup -> і монтує знову (Mount -> Unmount -> Mount);
- мета цієї перевірки — переконатися, що розробник **не забув написати функцію Cleanup**;
- якщо компонент підключає слухач чи таймер і коректно його очищає, подвійний монтаж пройде непомітно;
- якщо ж у коді відсутній Cleanup, подвійний монтаж миттєво розкриє витік пам'яті. У продакшн-збірці подвійний виклик вимикається автоматично.

## 6. Каталог антипатернів: коли `useEffect` використовувати НЕ потрібно

Найпоширеніша помилка сучасних фронтенд-розробників — використання `useEffect` там, де він взагалі не потрібен. Офіційна команда React присвятила цьому спеціальний розділ документації *"You Might Not Need an Effect"*.

### Антипатерн 1. Обчислення похідного стану (Derived State)

```tsx
// АНТИПАТЕРН: ЗАЙВИЙ СТАН ТА ЗАЙВИЙ ЕФЕКТ
const [firstName, setFirstName] = useState('');
const [lastName, setLastName] = useState('');
const [fullName, setFullName] = useState('');

useEffect(() => {
  setFullName(`${firstName} ${lastName}`); // Викликає ЗАЙВИЙ повторний рендер!
}, [firstName, lastName]);

// ПРАВИЛЬНИЙ ІНЖЕНЕРНИЙ ПІДХІД:
// Обчислюйте значення на льоту під час рендерингу!
const fullName = `${firstName} ${lastName}`;
```

Якщо значення можна вирахувати з існуючих пропсів або стану, ніколи не створюйте під нього окремий `useState` та `useEffect`.

### Антипатерн 2. Обробка дій користувача всередині ефекту

```tsx
// АНТИПАТЕРН: СТЕЖИТИ ЗА ПРАПОРЦЕМ ПОДІЇ В ЕФЕКТІ
const [isBuying, setIsBuying] = useState(false);

useEffect(() => {
  if (isBuying) {
    sendBuyRequest();
    showToast('Куплено!');
  }
}, [isBuying]);

// ПРАВИЛЬНИЙ ІНЖЕНЕРНИЙ ПІДХІД:
// Виконуйте бізнес-логіку прямо в обробнику події кнопки!
const handleBuyClick = async () => {
  await sendBuyRequest();
  showToast('Куплено!');
};
```

Код, який повинен виконатися **через конкретну дію користувача** (клік, відправка форми), повинен знаходитися в обробнику події, а не в `useEffect`. `useEffect` призначений виключно для коду, який повинен виконатися **через сам факт відображення компонента**.

## Висновки

- суть побічного ефекту - `useEffect` слугує мостом між декларативним Virtual DOM та зовнішніми нечистими системами браузера або мережі;
- чистота Render Phase - виконання побічних ефектів дозволене виключно після фіксації в DOM (Commit Phase), прямий виклик ефектів під час рендеру призводить до зациклення;
- масив залежностей - визначає частоту запуску ефекту; усі реактивні змінні з тіла ефекту мають бути обов'язково задекларовані згідно з правилом `exhaustive-deps`;
- захист від витоків через Cleanup - повернення функції очищення є обов'язковим для таймерів, глобальних слухачів подій та мережевих підписок;
- уникнення Race Conditions - використання `AbortController` у функції очищення гарантує скасування застарілих мережевих відповідей;
- мінімізація використання - похідні дані та обробка дій користувача мають обчислюватися безпосередньо в рендері або колбеках подій без залучення `useEffect`.

## Запитання для самоперевірки

- що таке Side Effect (побічний ефект) у контексті React і чому його заборонено виконувати в тілі компонента під час рендерингу;
- у чому полягає різниця між фазою рендерингу (Render Phase) та фазою фіксації (Commit Phase) у життєвому циклі компонента;
- опишіть поведінку хука `useEffect` при трьох варіантах масиву залежностей: відсутній, порожній `[]`, та з масивом змінних `[id]`;
- коли саме викликається функція очищення (Cleanup Function) і які інженерні задачі вона виконує;
- як використання `AbortController` допомагає уникнути проблеми стану гонитви (Race Condition) при зміні параметрів запиту;
- поясніть, чому підрахунок повного імені `fullName` на базі `firstName` та `lastName` через `useEffect` є антипатерном?
