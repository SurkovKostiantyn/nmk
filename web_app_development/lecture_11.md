## Перелік умовних скорочень

- **UI** (User Interface) — користувацький інтерфейс;
- **DOM** (Document Object Model) — об'єктна модель документа браузера;
- **vDOM** (Virtual Document Object Model) — віртуальна об'єктна модель документа;
- **AST** (Abstract Syntax Tree) — абстрактне синтаксичне дерево програми;
- **FPS** (Frames Per Second) — кількість кадрів за секунду;
- **INP** (Interaction to Next Paint) — метрика швидкості відгуку інтерфейсу на взаємодію користувача.

## Вступ

Декларативна модель React спирається на просту та елегантну формулу: `UI = f(state)`. Кожного разу, коли стан програми змінюється, React повторно викликає функції-компоненти для обчислення оновленого віртуального дерева (vDOM). У більшості стандартних інтерфейсів цей процес виконується настільки швидко, що користувач не помічає жодних затримок.

Проте зі зростанням складності веб-додатку — появою великих інтерактивних таблиць, складних фільтрів даних, графіків та вкладених ієрархій — неконтрольовані каскадні ререндери та важкі повторні обчислення починають блокувати головний потік браузера (Main Thread). Це призводить до падіння частоти кадрів нижче 60 FPS та погіршення ключових метрик взаємодії (зокрема Google Core Web Vitals INP).

У цій лекції детально аналізується ментальна модель рендерингу, розбираються класичні ручні методи мемоїзації (`React.memo`, `useCallback`, `useMemo`), розглядається революційний React 19 Compiler, який автоматизує мемоїзацію на рівні білда, досліджуються конкурентні механізми пріоритезації (`useTransition`, `useDeferredValue`) та методи діагностики швидкодії у профайлері React DevTools.

## 1. Ментальна модель рендерингу React та референтна рівність

Головна причина низької продуктивності фронтенд-застосунків полягає у хибному розумінні того, **коли** і **чому** React повторно відмальовує компоненти.

### За замовчуванням: рендеринг батька оновлює все дочірнє піддерево

Фундаментальне правило рендерингу в React говорить: коли стан (`useState` або `useReducer`) всередині компонента змінюється, React за замовчуванням рекурсивно викликає рендеринг цього компонента та **абсолютно всіх його дочірніх компонентів**, незалежно від того, чи змінилися їхні пропси:

- рендеринг батьківського компонента `Page` призводить до виклику функцій `Header`, `Sidebar`, `Content` та всіх їхніх нащадків;
- віртуальний рендеринг (Render Phase) — це просто виконання JavaScript-функцій для побудови нового vDOM-дерева;
- фіксація в DOM (Commit Phase) відбувається лише тоді, коли React виявляє реальні зміни між старим та новим vDOM.

Хоча Commit Phase оптимізовано за допомогою алгоритму Reconciliation, виконання сотень функцій у фазі Render Phase може призводити до значних затримок обчислень.

### Проблема референтної рівності (Referential Equality)

У мові JavaScript примітивні типи (числа, рядки, булеві значення) порівнюються за значенням, тоді як складні типи (об'єкти, масиви, функції) — за посиланням у купі пам'яті (Heap):

```javascript
// Порівняння за значенням
10 === 10; // true
'React' === 'React'; // true

// Порівняння за посиланням
({ id: 1 }) === ({ id: 1 }); // false
(() => {}) === (() => {});   // false
```

Кожного разу, коли функціональний компонент виконується під час повторного рендерингу:
- усі оголошені всередині нього об'єкти створюються заново з новими адресами в пам'яті;
- усі стрілкові функції та обробники створюються заново з новими посиланнями;
- якщо такий об'єкт чи функція передаються дочірньому компоненту як пропс, дочірній компонент вважає, що отримав абсолютно нові дані.

## 2. Класична мемоїзація: `React.memo` та `useCallback`

Для зупинки каскадного рендерингу дочірніх компонентів React надає компонент вищого порядку (HOC) — `React.memo`.

### Компонентний бар'єр `React.memo`

`React.memo` загортає компонент та перехоплює процес його оновлення. Перед тим як виконати рендеринг, `React.memo` порівнює попередні пропси компонента з новими за допомогою поверхневого порівняння (`Object.is`):

```tsx
interface UserCardProps {
  name: string;
  role: string;
  onSelect: (name: string) => void;
}

export const UserCard = React.memo(function UserCard({ name, role, onSelect }: UserCardProps) {
  console.log(`Рендеринг картки: ${name}`);
  return (
    <div className="card">
      <h3>{name}</h3>
      <p>{role}</p>
      <button onClick={() => onSelect(name)}>Обрати</button>
    </div>
  );
});
```

Якщо `name`, `role` та `onSelect` не змінилися порівняно з минулим рендерингом, React повністю пропускає виконання функції `UserCard` та повторне обчислення її розмітки.

### Чому `React.memo` ламається без `useCallback`

Якщо батьківський компонент передає обробник кліку у вигляді інлайн-функції, оптимізація `React.memo` повністю руйнується:

```tsx
// Батьківський компонент (АНТИПАТЕРН)
export function UserList() {
  const [count, setCount] = useState(0);

  // Функція створюється заново при КОЖНОМУ рендері UserList
  const handleSelect = (name: string) => {
    console.log(`Обрано користувача: ${name}`);
  };

  return (
    <div>
      <button onClick={() => setCount((c) => c + 1)}>Клік: {count}</button>
      {/* UserCard буде рендеритися повторно при кожному кліку лічильника,
          оскільки handleSelect щоразу має нову адресу в пам'яті */}
      <UserCard name="Олександр" role="Tech Lead" onSelect={handleSelect} />
    </div>
  );
}
```

### Забезпечення стабільності посилань за допомогою `useCallback`

Хук `useCallback` кешує екземпляр функції між послідовними рендерингами доти, доки значення в його масиві залежностей залишаються незмінними:

```tsx
export function UserList() {
  const [count, setCount] = useState(0);

  // Функція зберігає одне й те саме посилання в пам'яті між рендерами
  const handleSelect = useCallback((name: string) => {
    console.log(`Обрано користувача: ${name}`);
  }, []); // Порожній масив означає створення один раз при монтуванні

  return (
    <div>
      <button onClick={() => setCount((c) => c + 1)}>Клік: {count}</button>
      {/* Тепер UserCard НЕ буде рендеритися при зміні count! */}
      <UserCard name="Олександр" role="Tech Lead" onSelect={handleSelect} />
    </div>
  );
}
```

## 3. Кешування важких обчислень через `useMemo`

Хук `useMemo` призначений для кешування результату складних, ресурсоємних математичних або алгоритмічних обчислень між повторними рендерингами.

### Анатомія та принцип роботи

```tsx
const memoizedValue = useMemo(() => computeExpensiveValue(a, b), [a, b]);
```

- перший аргумент — чиста функція-обчислювач (Calculator Function), яка повертає значення;
- другий аргумент — масив реактивних залежностей;
- під час першого рендерингу React виконує функцію та запам'ятовує результат;
- під час наступних рендерингів React порівнює елементи масиву залежностей. Якщо вони ідентичні (`Object.is`), повертається вже збережене значення без виклику обчислювальної функції.

### Практичний приклад: важка фільтрація та сортування

```tsx
interface Product {
  id: string;
  title: string;
  price: number;
  category: string;
}

export function ProductCatalog({ products, query }: { products: Product[]; query: string }) {
  // Фільтрація 10 000 елементів займає значний час ЦП
  const filteredProducts = useMemo(() => {
    console.time('filter-benchmark');
    const lowerQuery = query.toLowerCase();
    const result = products.filter((item) =>
      item.title.toLowerCase().includes(lowerQuery)
    );
    console.timeEnd('filter-benchmark');
    return result;
  }, [products, query]);

  return (
    <ul>
      {filteredProducts.map((p) => (
        <li key={p.id}>{p.title} - ${p.price}</li>
      ))}
    </ul>
  );
}
```

### Пастки передчасної оптимізації та вартість мемоїзації

Мемоїзація не є безкоштовною операцією. Кожен виклик `useMemo` чи `useCallback`:
- виділяє додаткову пам'ять під збереження функції-замикання;
- створює масив залежностей у купі пам'яті;
- витрачає цикли процесора під час кожного рендерингу на попарне ітерування та порівняння залежностей.

Критерії доцільності `useMemo`:
- виправдано: важкі цикли (понад 1 000 ітерацій), складні регулярні вирази, операції над масивами з сортуванням та групуванням;
- виправдано: створення конфігураційних об'єктів, які передаються як пропси в мемоїзовані компоненти `React.memo` або в залежності `useEffect`;
- антипатерн: обгортання простих примітивних операцій (`useMemo(() => a + b, [a, b])` або фільтрація масиву з 10 елементів).

## 4. Революція React 19 Compiler (React Forget)

Історично необхідність ручного керування масивами залежностей та розставляння `useMemo`/`useCallback` була однією з головних причин помилок та перевантаження кодової бази React.

### Концепція автоматичної мемоїзації під час збірки

**React Compiler** (раніше відомий як React Forget) — це офіційний компілятор на базі аналізу AST-дерева JavaScript, розроблений командою Meta.

Він працює як плагін для збирача (Babel, Vite, Next.js SWC) і перетворює код безпосередньо під час етапу білда:

- компілятор аналізує граф потоку даних та керування у кожному компоненті;
- автоматично визначає, які обчислення залежать від яких реактивних значень;
- автоматично генерує низькорівневі кеш-структури (внутрішній примітив `useMemoCache`), інкапсулюючи оптимізацію без необхідності участі розробника.

### Порівняння коду до та після компіляції

Код, який пише розробник у React 19:

```tsx
export function ShoppingCart({ items, discount }: { items: Item[]; discount: number }) {
  const total = items.reduce((sum, item) => sum + item.price, 0);
  const finalPrice = total * (1 - discount);

  return (
    <div className="cart">
      <p>Сума: {finalPrice} грн</p>
    </div>
  );
}
```

Код, який генерує React Compiler (концептуальний вигляд):

```javascript
function ShoppingCart(props) {
  const $ = useMemoCache(4);
  const { items, discount } = props;
  
  let total;
  if ($[0] !== items) {
    total = items.reduce((sum, item) => sum + item.price, 0);
    $[0] = items;
    $[1] = total;
  } else {
    total = $[1];
  }

  let finalPrice;
  if ($[2] !== total || $[3] !== discount) {
    finalPrice = total * (1 - discount);
    $[2] = total;
    $[3] = discount;
  } else {
    finalPrice = $[3];
  }

  return /* JSX */;
}
```

Завдяки React Compiler потреба у ручному виклику `useMemo`, `useCallback` та `React.memo` практично зникає, залишаючи їх лише для вузькоспеціалізованих архітектурних випадків.

## 5. Конкурентні можливості React (Concurrent Features)

Традиційний рендеринг у JavaScript є синхронним: якщо важке обчислення триває 200 мілісекунд, браузер повністю "зависає" — користувач не може натиснути кнопку, скролити сторінку або вводити текст.

Конкурентний режим React (Concurrent Mode) дозволяє розділяти процес рендерингу на дрібні кванти часу, призупиняти обчислення та надавати пріоритет критично важливим подіям взаємодії.

### Пріоритети оновлення інтерфейсу

Усі оновлення стану в React поділяються на два класи:

- термінові оновлення (Urgent Updates) — пряма взаємодія людини з пристроєм: введення символу в поле пошуку (`input`), клік по кнопці, перемикання чекбокса. Мають відображатися миттєво (в межах 16 мс) для збереження плавності;
- нетермінові фонові оновлення (Transition Updates) — перехід між сторінками, оновлення списку результатів пошуку, фільтрація аналітичного графіка. Можуть зачекати без створення дискомфорту для користувача.

### Хук `useTransition`

Хук `useTransition` дозволяє позначити будь-яку зміну стану як низькопріоритетну (фонову), що запобігає зависанню полів вводу:

```tsx
import { useState, useTransition, ChangeEvent } from 'react';

export function SearchFilter({ allItems }: { allItems: string[] }) {
  const [inputValue, setInputValue] = useState('');
  const [searchQuery, setSearchQuery] = useState('');
  const [isPending, startTransition] = useTransition();

  const handleChange = (e: ChangeEvent<HTMLInputElement>) => {
    // 1. Термінове оновлення: відображаємо введений символ в інпуті миттєво
    setInputValue(e.target.value);

    // 2. Нетермінове оновлення: фільтрація великого масиву позначається як Transition
    startTransition(() => {
      setSearchQuery(e.target.value);
    });
  };

  const filteredItems = allItems.filter((item) =>
    item.toLowerCase().includes(searchQuery.toLowerCase())
  );

  return (
    <div>
      <input
        type="text"
        value={inputValue}
        onChange={handleChange}
        placeholder="Пошук серед 50,000 записів..."
      />
      {isPending && <span className="spinner">Оновлення списку...</span>}
      <ul style={ { opacity: isPending ? 0.6 : 1 } }>
        {filteredItems.map((item, idx) => (
          <li key={idx}>{item}</li>
        ))}
      </ul>
    </div>
  );
}
```

### Хук `useDeferredValue`

Якщо стан приходить від батьківського компонента через пропси і розробник не має прямого доступу до функції `setState`, для відкладеного рендерингу використовується `useDeferredValue`:

```tsx
import { useDeferredValue, useMemo } from 'react';

export function SlowList({ query }: { query: string }) {
  // Відкладає оновлення значення query, повертаючи старе, поки новий рендер триває у фоні
  const deferredQuery = useDeferredValue(query);

  const isStale = query !== deferredQuery;

  const items = useMemo(() => {
    // Важкі обчислення на базі відкладеного значення
    return generateHugeList(deferredQuery);
  }, [deferredQuery]);

  return (
    <div style={ { opacity: isStale ? 0.5 : 1 } }>
      {items.map((item) => (
        <div key={item.id}>{item.text}</div>
      ))}
    </div>
  );
}
```

## 6. Профілювання та діагностика продуктивності через React DevTools Profiler

Перед тим як застосовувати будь-які методи оптимізації, інженер зобов'язаний виміряти реальну продуктивність застосунку за допомогою інструменту **React DevTools Profiler**.

### Основні режими відображення профайлера

- графік Flamegraph — показує ієрархічне дерево компонентів під час кожного зафіксованого коміту. Колір блоку вказує на витрачений час (сірий — компонент не рендерився, синій/жовтий — рендерився, червоний — зайняв найбільше часу процесора);
- рейтинговий список (Ranked Chart) — сортує всі компоненти поточного коміту за спаданням часу їхнього рендерингу, дозволяючи миттєво знайти головне "вузьке місце" (bottleneck);
- діагностика причин ("Why did this render?") — спеціальна опція налаштувань DevTools, яка відображає точну причину оновлення конкретного вузла (наприклад: *props changed: onSelect*, *hook 1 changed*).

### Практичний алгоритм оптимізації

- 1. Вимірювання базової продуктивності — запис профілю взаємодії (клік, введення) у продакшн-збірці або режимі профілювання;
- 2. Виявлення джерел затримок — пошук компонентів із червоним забарвленням або високим значенням `Render duration`;
- 3. Усунення зайвих ререндерів — перевірка причин оновлення та виправлення референтної рівності пропсів;
- 4. Повторний замір — верифікація того, що час рендерингу дійсно зменшився без деградації читабельності коду.

## Висновки

- ментальна модель каскадного рендерингу - зміна стану батьківського компонента автоматично викликає рендеринг усього його дочірнього дерева;
- бар'єр мемоїзації з `React.memo` - зупиняє каскадний рендеринг шляхом поверхневого порівняння пропсів (`Object.is`);
- референтна стабільність через `useCallback` - зберігає ідентичність посилання функцій-обробників у купі пам'яті між повторними викликами компонента;
- виправдане використання `useMemo` - доцільне лише для справді ресурсоємних операцій (великі масиви, сортування) або стабілізації складних об'єктів пропсів;
- революція React 19 Compiler - автоматизує розрахунок та кешування залежностей на рівні AST-компіляції збірки проекту;
- конкурентна пріоритезація через `useTransition` та `useDeferredValue` - розділяє оновлення інтерфейсу на термінові та фонові для забезпечення максимальної плавності відгуку інтерфейсу.

## Запитання для самоперевірки

- яка принципова різниця між фазою обчислення віртуального дерева (Render Phase) та фазою фіксації змін у реальному DOM (Commit Phase);
- чому передача інлайн стрілкової функції у пропси компонента, огорнутого в `React.memo`, призводить до втрати мемоїзації;
- у яких конкретних сценаріях витрати ресурсів процесора на виконання `useMemo` перевищують користь від його застосування;
- яким чином React 19 Compiler автоматизує збереження значень без потреби ручного виклику `useCallback` та `useMemo`;
- чим термінові оновлення стану (Urgent Updates) відрізняються від переходів (Transitions) за пріоритетом черги завдань браузера;
- як хук `useDeferredValue` допомагає оптимізувати плавність введення тексту в інпутах при фільтрації великих списків;
- яку інформацію надає режим Ranked Chart в інструменті React DevTools Profiler при дослідженні вузьких місць швидкодії.
