# Лекція 16 (2 години). Fullstack React та Server-Side Rendering: Server Components (RSC) та Next.js 15+

## План лекції

- 1. Еволюція стратегій рендерингу веб-застосунків: порівняльний аналіз CSR, SSR, SSG та ISR;
- 2. Архітектурна революція React Server Components (RSC): прямий доступ до серверних ресурсів без збільшення клієнтського бандлу;
- 3. Межі виконання та директиви середовищ: правила використання `'use client'` та `'use server'`;
- 4. Екосистема Next.js 15+ з App Router: файлова ієрархічна маршрутизація, серверні лейаути та потокова передача через `Suspense`;
- 5. Серверні дії (Server Actions): пряма мутація баз даних та обробка форм без написання проміжних REST API ендпоінтів;
- 6. Вбудовані оптимізації Next.js: робота із зображеннями (`next/image`), шрифтами (`next/font`) та динамічними метаданими для SEO.

## Перелік умовних скорочень

- **UI** (User Interface) — користувацький інтерфейс;
- **DOM** (Document Object Model) — об'єктна модель документа браузера;
- **CSR** (Client-Side Rendering) — рендеринг на стороні клієнта;
- **SSR** (Server-Side Rendering) — рендеринг на стороні сервера;
- **SSG** (Static Site Generation) — статична генерація сторінок під час збірки;
- **ISR** (Incremental Static Regeneration) — інкрементна статична регенерація;
- **RSC** (React Server Components) — серверні компоненти React;
- **SEO** (Search Engine Optimization) — пошукова оптимізація веб-ресурсів.

## Вступ

Протягом першого десятиліття свого існування React асоціювався майже виключно з клієнтським рендерингом (Client-Side Rendering, CSR). Традиційний SPA завантажував браузером майже порожній HTML-файл з одним тегом `<div id="root"></div>` та важким JavaScript-бандлом на кілька мегабайтів. Лише після повного завантаження та парсингу цього скрипту користувач бачив перший інтерфейс. Це призводило до незадовільних показників першого завантаження (First Contentful Paint, FCP) та ускладнювало індексацію сторінок пошуковими роботами (SEO).

Сьогодні React еволюціонував у повноцінний **Fullstack-фреймворк**. Завдяки появі концепції **React Server Components (RSC)** та фреймворку **Next.js 15+**, розробники отримали можливість запускати компоненти безпосередньо в середовищі Node.js/Edge, звертатися до баз даних без проміжних API-ендпоінтів та надсилати клієнту виключно готовий HTML і легкий код інтерактивності.

У цій лекції детально розглядаються всі класичні та сучасні стратегії рендерингу (CSR, SSR, SSG, ISR), розкривається внутрішня природа React Server Components, аналізується файлова маршрутизація Next.js App Router, демонструється мутація даних через Server Actions та досліджуються вбудовані засоби веб-оптимізації.

## 1. Еволюція стратегій рендерингу веб-застосунків

Вибір правильної стратегії рендерингу визначає швидкість завантаження додатку, навантаження на сервер та видимість для пошукових систем.

### Порівняльний аналіз стратегій

- клієнтський рендеринг (CSR) — браузер отримує порожній HTML і самостійно завантажує дані через API. Ідеально підходить для закритих панелей керування (Admin Dashboards, SaaS-продукти), де SEO не має значення, але критична висока інтерактивність;
- серверний рендеринг на льоту (SSR) — при кожному новому HTTP-запиті сервер генерує свіжий HTML з актуальними даними і відправляє його браузеру. Забезпечує миттєвий перший показ (FCP) та відмінне SEO, проте збільшує навантаження на процесор сервера та час першого байта (Time to First Byte, TTFB);
- статична генерація (SSG) — сторінки генеруються у вигляді статичних HTML-файлів лише один раз під час етапу складання проєкту (`build time`). Забезпечує блискавичну доставку через CDN (Content Delivery Network), але не підходить для даних, які часто змінюються;
- інкрементна статична регенерація (ISR) — дозволяє фоново оновлювати окремі статичні сторінки за заданим таймаутом (наприклад, раз на 60 секунд) без повної перезбірки всього веб-сайту.

## 2. Архітектурна революція React Server Components (RSC)

Класичний SSR мав суттєве обмеження — процес **гідратації (Hydration)**. Навіть якщо сервер згенерував HTML, весь JavaScript-код цих компонентів однаково мав завантажуватися браузером, щоб "оживити" слухачі подій. Якщо сторінка використовувала важкі бібліотеки для форматування тексту чи підсвічування коду (наприклад, 100 Кб бібліотеки Markdown), цей код потрапляв у клієнтський бандл.

### Концепція Server Components

**React Server Components (RSC)** — це компоненти, які виконуються **виключно на сервері** і **ніколи не додаються до клієнтського JavaScript-бандлу**.

Переваги RSC:
- нульовий розмір бандлу (Zero Bundle Size) — бібліотеки, які використовуються всередині RSC, залишаються на сервері;
- прямий доступ до внутрішньої інфраструктури — серверні компоненти можуть безпосередньо звертатися до файлової системи, підключатися до PostgreSQL/MongoDB або читати секретні ключі середовища (Environment Variables) без ризику їх витоку на клієнт;
- автоматична асинхронність — серверні компоненти є звичайними асинхронними функціями (`async function`), що дозволяє використовувати прямий `await` прямо в тілі компонента без `useEffect` та `useState`.

### Приклад прямого читання з бази даних у RSC

```tsx
// src/app/users/page.tsx (Серверний компонент за замовчуванням у Next.js)
import { db } from '@/lib/db';

export default async function UsersPage() {
  // Прямий запит до бази даних прямо в тілі компонента
  const users = await db.user.findMany({
    orderBy: { createdAt: 'desc' },
  });

  return (
    <div className="container">
      <h1>Список зареєстрованих користувачів</h1>
      <ul>
        {users.map((user) => (
          <li key={user.id}>
            <strong>{user.name}</strong> — {user.email}
          </li>
        ))}
      </ul>
    </div>
  );
}
```

У клієнтський браузер передається чистий HTML-код списку, а бібліотека роботи з базою даних не додає жодного байта до ваги сторінки.

## 3. Межі виконання та директиви середовищ: `'use client'` та `'use server'`

У гібридній fullstack-архітектурі серверні та клієнтські компоненти працюють пліч-о-пліч у єдиному дереві додатку.

### Директива `'use client'`

У Next.js App Router **усі компоненти за замовчуванням вважаються серверними (Server Components)**.

Директива `'use client'` вказується на першому рядку файлу і позначає перехід через так званий "клієнтський бар'єр" (Client Boundary). Вона повідомляє збирачу, що цей файл та всі його дочірні імпорти є клієнтськими компонентами:

```tsx
// src/components/CounterButton.tsx
'use client';

import { useState } from 'react';

export function CounterButton() {
  // Клієнтські хуки дозволені лише в Client Components
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount((c) => c + 1)}>
      Поточний клік: {count}
    </button>
  );
}
```

Коли використовувати `'use client'`:
- якщо компоненту потрібні слухачі подій (`onClick`, `onChange`, `onSubmit`);
- якщо компонент використовує стан або ефекти (`useState`, `useReducer`, `useEffect`);
- якщо потрібен доступ до браузерних API (`window`, `localStorage`, `navigator.geolocation`).

Коли НЕ використовувати `'use client'`:
- для простого відображення статичного контенту або списків;
- для читання даних із сервера;
- для компонентів-контейнерів лейауту.

### Патерн передачі серверних компонентів як `children`

Клієнтський компонент не може безпосередньо імпортувати та рендерити серверний компонент. Проте він може приймати серверні компоненти через пропс `children` (патерн інверсії керування):

```tsx
// ClientModal.tsx ('use client')
'use client';
export function ClientModal({ children }: { children: React.ReactNode }) {
  const [isOpen, setIsOpen] = useState(true);
  if (!isOpen) return null;
  return <div className="modal">{children}</div>;
}

// Page.tsx (Server Component)
import { ClientModal } from './ClientModal';
import { ServerData } from './ServerData';

export default function Page() {
  return (
    <ClientModal>
      {/* ServerData виконується на сервері та передається у вигляді HTML! */}
      <ServerData />
    </ClientModal>
  );
}
```

## 4. Екосистема Next.js 15+ з App Router

Next.js 15+ використовує сучасну модель файлової маршрутизації **App Router** (папка `app/`), побудовану навколо ієрархічних угод іменування файлів.

### Спеціальні файлові конвенції

- `layout.tsx` — спільна оболонка для сегмента та всіх його вкладених маршрутів. Зберігає стан при переходах;
- `page.tsx` — унікальний інтерфейс конкретного маршруту, доступний за URL;
- `loading.tsx` — автоматичний стан завантаження на базі React `Suspense`, що відображається під час очікування асинхронних операцій у `page.tsx`;
- `error.tsx` — межа перехоплення помилок (Error Boundary), яка повинна бути обов'язково клієнтським компонентом (`'use client'`);
- `not-found.tsx` — інтерфейс помилки 404 для маршруту або виклику функції `notFound()`.

### Потокова передача даних (Streaming) через React `Suspense`

Next.js дозволяє не чекати завантаження найповільнішого блоку даних перед відправкою сторінки. За допомогою компонента `<Suspense>` швидкі блоки відправляються браузеру миттєво, а важкі — довантажуються через відкрите HTTP-з'єднання у вигляді потоку:

```tsx
// src/app/dashboard/page.tsx
import { Suspense } from 'react';
import { FastStats } from '@/components/FastStats';
import { SlowAnalyticsChart } from '@/components/SlowAnalyticsChart';

export default function DashboardPage() {
  return (
    <div>
      <h1>Аналітична панель</h1>
      
      {/* Рендериться миттєво */}
      <FastStats />

      {/* Показує скелетон і довантажується потоком у міру готовності сервера */}
      <Suspense fallback={<div>Завантаження важкого графіка...</div>}>
        <SlowAnalyticsChart />
      </Suspense>
    </div>
  );
}
```

## 5. Серверні дії (Server Actions)

У традиційній архітектурі мутація даних вимагала створення окремого REST-контролера (`/api/feedback`), валідації в ньому, написання виклику `fetch` на клієнті та обробки статусу відповіді.

**Server Actions** у Next.js 15 дозволяють оголошувати асинхронні серверні функції, які викликаються прямо з нативних HTML-форм або користувацьких кнопок:

```tsx
// src/app/actions.ts
'use server';

import { revalidatePath } from 'next/cache';
import { db } from '@/lib/db';

export async function addCommentAction(formData: FormData) {
  const content = formData.get('content') as string;
  const author = formData.get('author') as string;

  if (!content || !author) {
    throw new Error('Усі поля форми обов’язкові');
  }

  // 1. Прямий запис у базу даних на сервері
  await db.comment.create({
    data: { content, author },
  });

  // 2. Інвалідація кешу сторінки для миттєвого оновлення розмітки
  revalidatePath('/blog/post-1');
}
```

Використання дії у формі на сторінці:

```tsx
// src/app/blog/post-1/page.tsx
import { addCommentAction } from '@/app/actions';

export default function CommentForm() {
  return (
    <form action={addCommentAction} className="comment-form">
      <input type="text" name="author" placeholder="Ваше ім’я" required />
      <textarea name="content" placeholder="Ваш коментар..." required />
      <button type="submit">Надіслати коментар</button>
    </form>
  );
}
```

Більше того: форми на базі Server Actions працюють навіть тоді, коли у користувача повільне з'єднання або JavaScript ще не встиг завантажитися в браузері (Progressive Enhancement).

## 6. Вбудовані оптимізації Next.js

Next.js містить спеціалізовані модулі для автоматичного вирішення найскладніших проблем продуктивності та SEO.

### Оптимізація зображень через `next/image`

Звичайний тег `<img src="...">` часто спричиняє зміщення макета (Cumulative Layout Shift, CLS) та завантажує важкі нестиснені файли. Компонент `Image` від Next.js автоматично:
- конвертує зображення в сучасні формати нового покоління (WebP або AVIF);
- змінює розмір зображення під точні габарити дисплея пристрою користувача;
- запобігає зсувам макета за рахунок резервування співвідношення сторін;
- ледаче завантажує картинки (Lazy Loading), коли вони з'являються у зоні видимості вікна (Viewport).

### Оптимізація шрифтів через `next/font`

Модуль `next/font` автоматично завантажує Google Fonts під час складання проєкту, вбудовує шрифтові гліфи прямо в CSS та хостить їх на власному домені, усуваючи сторонні мережеві запити та блокування рендерингу (Zero Layout Shift).

### Динамічні метадані для SEO

```tsx
// src/app/products/[id]/page.tsx
import { Metadata } from 'next';

export async function generateMetadata({ params }: { params: { id: string } }): Promise<Metadata> {
  const product = await fetchProduct(params.id);

  return {
    title: `${product.title} | Інтернет-магазин`,
    description: product.description,
    openGraph: {
      images: [product.imageUrl],
    },
  };
}
```

## Висновки

- еволюція стратегій рендерингу - поєднання CSR, SSR, SSG та ISR дозволяє вибирати оптимальний баланс між швидкістю доставки контенту, свіжістю даних та SEO;
- революція Server Components - виконання коду на сервері забезпечує нульовий вплив важких бібліотек на клієнтський бандл і прямий доступ до баз даних;
- суворі межі середовищ - директива `'use client'` позначає компоненти з інтерактивністю та хуками, а решта компонентів залишаються суто серверними;
- компонентна потокова передача (Streaming) - використання React `Suspense` дозволяє відправляти готові блоки сторінки без очікування повільних операцій;
- простота мутацій через Server Actions - виконання операцій запису даних на сервері з нативних форм без потреби створення класичних REST API;
- вбудований комплекс оптимізацій - автоматичне стиснення медіа, хостинг шрифтів та динамічна генерація метаданих виводять веб-додаток на найвищі оцінки Core Web Vitals.

## Запитання для самоперевірки

- яка головна різниця між рендерингом на стороні сервера (SSR) та статичною генерацією сторінок (SSG);
- як архітектура React Server Components вирішує проблему надмірного розміру клієнтського JavaScript-бандлу;
- у яких конкретних випадках розробник зобов'язаний додавати директиву `'use client'` на початку файлу компонента;
- чи може клієнтський компонент приймати серверний компонент через пропс `children`, і як це працює під капотом;
- яку задачу вирішує потокова передача контенту (Streaming) за допомогою обгортки `<Suspense>` у Next.js App Router;
- у чому полягає перевага Server Actions перед традиційним підходом надсилання запитів через клієнтський `fetch` до REST API ендпоінтів;
- як вбудований компонент `next/image` запобігає погіршенню показника стабільності макета (CLS) у Google Core Web Vitals.
