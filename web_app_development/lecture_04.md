# Лекція 4 (2 години). Стилізація сучасного React: Tailwind CSS, CSS Modules та дизайн-системи

## План лекції

- 1. Еволюція підходів до стилізації у веб-розробці: від глобального каскаду до ізольованих компонентів;
- 2. Модульний CSS (CSS Modules): інкапсуляція стилів, локальна область видимості та автоматичні хеші;
- 3. Зліт та криза парадигми CSS-in-JS: чому Styled Components та Emotion поступаються позиціями в епоху React Server Components;
- 4. Парадигма Utility-First CSS (Tailwind CSS): принципи роботи, JIT-компілятор, позбавлення мертвого CSS та вирішення конфліктів за допомогою `clsx` і `tailwind-merge`;
- 5. Концепція Headless UI та компонентні системи нового покоління: архітектура Radix UI, філософія shadcn/ui та бібліотека `class-variance-authority` (cva);
- 6. Проєктування дизайн-систем: дизайн-токени, системні CSS-змінні та надійна реалізація темної теми (Dark Mode).

## Перелік умовних скорочень

- **CSS** (Cascading Style Sheets) — каскадні таблиці стилів;
- **JIT** (Just-In-Time) — компіляція стилів на льоту під час аналізу вихідного коду;
- **RSC** (React Server Components) — серверні компоненти React;
- **UI** (User Interface) — користувацький інтерфейс;
- **CVA** (Class Variance Authority) — бібліотека декларативної типізації варіантів компонентів;
- **BEM** (Block Element Modifier) — класична методологія іменування класів у верстці.

## Вступ

Стилізація користувацьких інтерфейсів пройшла шлях від одного глобального файлу `style.css` до складних компонентних дизайн-систем. У компонентно-орієнтованому світі React традиційний глобальний каскад CSS став джерелом прихованих конфліктів, непередбачуваного перевизначення стилів та роздутих файлів стилів, які ніхто не наважувався видаляти.

Ця лекція розглядає еволюцію інженерних підходів до оформлення інтерфейсів, пояснює причини занепаду бібліотек CSS-in-JS з появою React Server Components, розкриває переваги та архітектуру утилітарного підходу Tailwind CSS і знайомить із сучасною філософією Headless UI та дизайн-систем на базі Radix UI та shadcn/ui.

## 1. Еволюція підходів до стилізації: від глобального каскаду до компонентної ізоляції

Створення та підтримка стилів у великих веб-додатках завжди стикалися з проблемою глобальної області видимості CSS.

### Проблема класичного глобального CSS

За замовчуванням усі CSS-селектори мають глобальну область дії на всій HTML-сторінці:

```css
/* global.css */
.title {
  font-size: 24px;
  color: #1e293b;
}

.button {
  background-color: #2563eb;
  padding: 10px 20px;
}
```

Недоліки глобального CSS на масштабі командної розробки:
- колізії імен (Naming Collisions) - якщо два розробники створюють різні компоненти і використовують однаковий клас `.button` або `.title`, стилі одного компонента непередбачувано зламають інший;
- специфічність каскаду (Specificity Wars) - намагаючись перебити чужі стилі, інженери починають збільшувати вагу селекторів (`body div.main-content .card .button`) та зловживати прапорцем `!important`;
- неможливість безпечного видалення коду (Dead Code Elimination) - видаляючи застарілий компонент, ніхто не видаляє відповідні класи з глобального CSS через страх ненароком зламати іншу сторінку. З роками розмір файлів стилів лише неконтрольовано зростає.

### Методологія BEM як спроба дисципліни

Для боротьби з колізіями індустрія винайшла методологію **BEM (Блок-Елемент-Модифікатор)**: `.card__header--highlighted`.
BEM допоміг створити порядок, але вимагав від розробників вигадувати довгі громіздкі імена класів і спирався виключно на людську дисципліну: одна помилка літерою в селекторі знову ламала верстку.

Постала потреба у технічній ізоляції стилів на рівні збирача коду.

## 2. Модульний CSS (CSS Modules): інкапсуляція на рівні збирача

**CSS Modules** — це підхід, за якого кожен файл стилів прив'язується до конкретного компонента, а збирач автоматично гарантує унікальність кожного імені класу.

### Як працюють CSS Modules

Файл стилів іменується з суфіксом `.module.css` (наприклад, `Button.module.css`):

```css
/* Button.module.css */
.button {
  padding: 10px 20px;
  border-radius: 6px;
  font-weight: 600;
  cursor: pointer;
}

.primary {
  background-color: #3b82f6;
  color: white;
}

.secondary {
  background-color: #e2e8f0;
  color: #1e293b;
}
```

У React-компоненті файл імпортується як звичайний JavaScript-об'єкт:

```tsx
// Button.tsx
import styles from './Button.module.css';

interface ButtonProps {
  children: React.ReactNode;
  variant?: 'primary' | 'secondary';
}

export function Button({ children, variant = 'primary' }: ButtonProps) {
  // Звернення до стилів через властивості об'єкта
  return (
    <button className={`${styles.button} ${styles[variant]}`}>
      {children}
    </button>
  );
}
```

### Механізм трансформації збирачем

Під час збірки Vite або Webpack аналізує файл і трансформує прості імена класів у згенеровані унікальні геші:
- ім'я `.button` замінюється у фінальному CSS на селектор типу `_button_x9f2a_12`;
- об'єкт `styles` у JavaScript містить відповідність: `{ button: "_button_x9f2a_12", primary: "_primary_x9f2a_18" }`.

Переваги CSS Modules:
- повна локальна ізоляція - клас `.button` у модальному вікні та клас `.button` у шапці ніколи не конфліктуватимуть;
- простота міграції - це звичайний стандартизований CSS без вивчення нового синтаксису.

Недоліки:
- велика кількість окремих файлів стилів;
- ускладнена динамічна стилізація за допомогою JavaScript-змінних;
- відсутність єдиної системи консистентних розмірів і кольорів без окремого налаштування CSS-змінних.

## 3. Зліт та криза парадигми CSS-in-JS

У період розквіту React 16 величезну популярність здобули бібліотеки **CSS-in-JS** (Styled Components, Emotion).

### Концепція CSS-in-JS

Ідея полягала в повній відмові від окремих файлів CSS та описі стилів безпосередньо всередині JavaScript/TypeScript за допомогою тегованих шаблонних рядків:

```tsx
// Styled Components
import styled from 'styled-components';

const StyledButton = styled.button<{ $variant: 'primary' | 'secondary' }>`
  padding: 10px 20px;
  border-radius: 6px;
  background-color: ${(props) => (props.$variant === 'primary' ? '#3b82f6' : '#e2e8f0')};
  color: ${(props) => (props.$variant === 'primary' ? '#ffffff' : '#1e293b')};

  &:hover {
    opacity: 0.9;
  }
`;
```

Це давало неймовірну гнучкість: стилі отримували прямий доступ до пропсів та стану компонента.

### Чому CSS-in-JS зазнає кризи в сучасному React?

Починаючи з релізу React 18 і особливо з появою React 19 та архітектури Server Components (RSC), бібліотеки рантаймового CSS-in-JS зіткнулися з фундаментальними архітектурними бар'єрами:

- продуктивність рантайму (Runtime Overhead) - бібліотека повинна під час кожного рендерингу спарсити CSS-рядок у JavaScript, згенерувати унікальний хеш, створити тег `<style>` та вставити його в DOM браузера; це блокує головний потік при частих анімаціях та скролінгу;
- несумісність із React Server Components - компоненти, що виконуються на сервері (RSC), не мають доступу до браузерного DOM і не можуть динамічно інжектувати теги `<style>` у рантаймі; використання Styled Components або Emotion вимагає обов'язкової директиви `'use client'`, позбавляючи проєкт переваг серверного рендерингу;
- роздутий клієнтський бандл - необхідність тягнути у браузер клієнта повноцінний CSS-парсер розміром 15–30 КБ.

Це спричинило масштабний тектонічний зсув індустрії у бік компільованого та утилітарного CSS.

## 4. Парадигма Utility-First CSS: Архітектура Tailwind CSS

**Tailwind CSS** став найпопулярнішим рішенням для стилізації сучасних фронтенд-додатків. Замість написання семантичних класів (`.author-bio-card`), Tailwind пропонує підхід **Utility-First**: стилізація будується за допомогою набору атомарних, вузькоспеціалізованих утилітарних класів безпосередньо у розмітці JSX.

```tsx
export function ProductBadge() {
  return (
    <span className="inline-flex items-center px-2.5 py-0.5 rounded-full text-xs font-medium bg-blue-100 text-blue-800 dark:bg-blue-900 dark:text-blue-300">
      Новинка
    </span>
  );
}
```

### Як функціонує JIT-компілятор Tailwind?

Ранні версії утилітарних бібліотек генерували велетенський CSS-файл з усіма можливими комбінаціями класів (розміром понад 10 МБ).
Сучасний Tailwind використовує **Just-In-Time (JIT) рушій**:
- сканує всі вихідні файли (`.tsx`, `.ts`, `.html`) під час збірки;
- за допомогою регулярних виразів знаходить класи, які дійсно використовуються у коді;
- генерує на льоту виключно ті CSS-правила, які присутні у проєкті;
- підсумковий розмір CSS-файлу для навіть величезного продакшн-застосунку зазвичай становить **менше 10–15 КБ** (у заархівованому вигляді Gzip).

### Переваги підходу Utility-First

- відсутність вигадування імен класів - розробнику більше не потрібно страждати над назвами типу `wrapper-inner-container-left`;
- стабільний розмір CSS - незалежно від того, додаєте ви 10 нових сторінок чи 100, розмір CSS майже не збільшується, оскільки базові класи (`flex`, `p-4`, `text-sm`) перевикористовуються;
- безпечний рефакторинг - видаляючи компонент JSX, ви автоматично очищаєте стилі; видалення коду більше ніколи не зламає іншу сторінку;
- дизайн-система за замовчуванням - Tailwind надає вивірену шкалу відступів, типографіки, радіусів та гармонійних кольорів.

### Вирішення колізій класів: бібліотеки `clsx` та `tailwind-merge`

При створенні гнучких компонентів виникає потреба об'єднувати базові класи компонента з класами, які передає споживач через проп `className`.

Проста конкатенація рядків призводить до серйозного бага:

```tsx
// НАЇВНИЙ ПІДХІД (БАГ):
function Button({ className, variant }) {
  // Базовий колір bg-blue-500, але споживач передав className="bg-red-500"
  return <button className={`bg-blue-500 text-white ${className}`}>Клік</button>;
}
```

У фінальному класі опиняться обидва класи: `class="bg-blue-500 text-white bg-red-500"`.
Який колір переможе? Це визначить не порядок у рядку `className`, а порядок оголошення цих класів у внутрішньому файлі CSS Tailwind! Результат стає непередбачуваним.

Індустріальний стандарт вирішення проблеми — утиліта `cn` на базі `clsx` та `tailwind-merge`:

```bash
npm install clsx tailwind-merge
```

Створення стандартної функції `cn`:

```typescript
// src/utils/cn.ts
import { clsx, type ClassValue } from 'clsx';
import { twMerge } from 'tailwind-merge';

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs));
}
```

Як це працює:
- `clsx` обробляє умовні класи (об'єкти, масиви, булеві перевірки);
- `tailwind-merge` знає конфліктні утиліти Tailwind і гарантовано видаляє старі класи при появі нових (видалить `bg-blue-500`, якщо з'явився `bg-red-500`).

## 5. Концепція Headless UI та сучасні компонентні системи

Сучасний підхід до побудови інтерфейсів відкидає старі важкі бібліотеки (Bootstrap, Material UI), які нав'язували власну візуальну тему та важко кастомізувалися.

### Що таке Headless UI?

**Headless UI** (інтерфейс "без голови") — це бібліотека, яка надає 100% складної логіки компонента (доступність WAI-ARIA, керування фокусом клавіатури, відкриття/закриття модалок, стан випадаючих меню), але **не містить жодного власного рядка CSS-стилів**.

Візуальне оформлення повністю залишається за розробником за допомогою Tailwind CSS.

Яскраві представники Headless-підходу:
- **Radix UI Primitives** - еталон доступності (a11y) та модульності;
- **Headless UI** (від команди Tailwind Labs);
- **React Aria** (від компанії Adobe).

### Філософія системи shadcn/ui

Проєкти нового покоління масово використовують **shadcn/ui**.
Головна концепція: **"Це не бібліотека, яку ви встановлюєте через npm. Це код, який копіюється у ваш репозиторій"**.

- ви виконуєте команду CLI (наприклад, `npx shadcn@latest add button`);
- компонент завантажується безпосередньо у вашу папку `src/components/ui/button.tsx`;
- компонент побудований на базі Radix UI (логіка та доступність) + Tailwind CSS (стилі через `cn`);
- ви маєте 100% контроль над кодом компонента і можете модифікувати будь-яку його частину без обмежень сторонніх бібліотек.

### Типізація варіантів за допомогою `class-variance-authority` (CVA)

Для зручного створення багатоваріантних компонентів (Button з розмірами `sm/md/lg` та кольорами `primary/secondary/ghost`) використовується бібліотека `class-variance-authority`:

```bash
npm install class-variance-authority
```

Приклад професійного компонента кнопки:

```tsx
// src/components/ui/Button.tsx
import React from 'react';
import { cva, type VariantProps } from 'class-variance-authority';
import { cn } from '@/utils/cn';

const buttonVariants = cva(
  // Базові класи для всіх кнопок:
  'inline-flex items-center justify-center rounded-md text-sm font-medium transition-colors focus-visible:outline-none focus-visible:ring-2 disabled:pointer-events-none disabled:opacity-50',
  {
    variants: {
      variant: {
        primary: 'bg-blue-600 text-white hover:bg-blue-700 shadow-sm',
        secondary: 'bg-slate-100 text-slate-900 hover:bg-slate-200',
        danger: 'bg-red-600 text-white hover:bg-red-700',
        outline: 'border border-slate-300 bg-transparent hover:bg-slate-100',
      },
      size: {
        sm: 'h-8 px-3 text-xs',
        md: 'h-10 px-4 text-sm',
        lg: 'h-12 px-6 text-base',
      },
    },
    defaultVariants: {
      variant: 'primary',
      size: 'md',
    },
  }
);

interface ButtonProps
  extends React.ButtonHTMLAttributes<HTMLButtonElement>,
    VariantProps<typeof buttonVariants> {}

export function Button({ className, variant, size, ...props }: ButtonProps) {
  return (
    <button
      className={cn(buttonVariants({ variant, size, className }))}
      {...props}
    />
  );
}
```

## 6. Проєктування дизайн-систем: дизайн-токени та темна тема (Dark Mode)

Для забезпечення цілісності великого цифрового продукту використовується методологія **дизайн-токенів (Design Tokens)**.

### Організація системних токенів через змінні CSS

Замість жорсткого прописування шістнадцяткових кольорів (`#3b82f6`) у верстці, колірна палітра описується як набір семантичних CSS-змінних у файлі стилів:

```css
/* src/index.css */
@layer base {
  :root {
    --background: 0 0% 100%;
    --foreground: 222.2 84% 4.9%;

    --primary: 221.2 83.2% 53.3%;
    --primary-foreground: 210 40% 98%;

    --card: 0 0% 100%;
    --card-foreground: 222.2 84% 4.9%;

    --border: 214.3 31.8% 91.4%;
  }

  .dark {
    --background: 222.2 84% 4.9%;
    --foreground: 210 40% 98%;

    --primary: 217.2 91.2% 59.8%;
    --primary-foreground: 222.2 47.4% 11.2%;

    --card: 222.2 84% 4.9%;
    --card-foreground: 210 40% 98%;

    --border: 217.2 32.6% 17.5%;
  }
}
```

### Реалізація темної теми (Dark Mode) у Tailwind

Найбільш надійною та передбачуваною стратегією перемикання теми є стратегія CSS-класу (`darkMode: 'class'` у Tailwind):
- кореневий HTML-елемент `<html class="dark">` отримує клас `dark`;
- Tailwind активує утиліти з префіксом `dark:` (наприклад, `bg-white dark:bg-slate-900 text-slate-900 dark:text-slate-100`);
- стан збереженої теми фіксується у `localStorage` або синхронізується з системними налаштуваннями ОС через браузерний запит `window.matchMedia('(prefers-color-scheme: dark)')`.

## Висновки

- еволюція від глобального до компонентного - пряме використання глобального CSS призводить до конфліктів імен та надлишкового коду, що змусило індустрію шукати модульні інженерні підходи;
- баланс CSS Modules - забезпечують надійну ізоляцію класів через локальні хеші, проте не вирішують проблеми побудови централізованої дизайн-системи;
- криза CSS-in-JS - накладні витрати на парсинг стилів у рантаймі та несумісність із React Server Components спричинили відтік розробників від бібліотек на кшталт Styled Components;
- ефективність Tailwind CSS - утилітарний підхід у синергії з JIT-компілятором мінімізує обсяг підсумкового CSS, усуває мертвий код та забезпечує консистентність верстки;
- стандарт безпечного злиття класів - комбінація бібліотек `clsx` та `tailwind-merge` у функції `cn` є обов'язковим інструментом для запобігання колізіям стилів у компонентах;
- парадигма Headless UI - сучасні компонентні системи розділяють доступність і поведінку (Radix UI) від візуального оформлення (Tailwind + CVA), забезпечуючи абсолютну гнучкість розробнику.

## Запитання для самоперевірки

- які фундаментальні технічні проблеми глобального каскаду CSS призвели до виникнення компонентних підходів стилізації;
- як саме збирачі коду (Vite, Webpack) забезпечують локальну область видимості в CSS Modules;
- чому бібліотеки рантаймового CSS-in-JS (Styled Components, Emotion) стали небажаними в екосистемі сучасного React 19 та Server Components;
- поясніть механізм роботи JIT-компілятора Tailwind CSS та причини надзвичайно малого розміру підсумкового файлу стилів;
- чому проста конкатенація рядків класів у React є небезпечною і як функція `cn` на базі `tailwind-merge` вирішує конфлікти селекторів;
- у чому полягає фундаментальна концепція підходу Headless UI (на прикладі Radix UI) і які переваги вона надає розробнику дизайн-системи?
