# Лекція 2 (2 години). Сучасне середовище розробки: Vite, екосистема Node.js та стандарти якості

## План лекції

- 1. Еволюція збирачів JavaScript: криза Webpack і Create React App та перехід до Native ESM;
- 2. Архітектура збирача нового покоління Vite: взаємодія Native ESM, esbuild та Rollup;
- 3. Механізм гарячої заміни модулів (HMR): миттєвий відгук та збереження стану через React Fast Refresh;
- 4. Організація архітектури фронтенд-проєкту: класичний шаровий підхід проти Feature-Driven структурування;
- 5. Автоматизований контроль якості коду: ESLint 9 (Flat Config), форматування Prettier та огляд Biome;
- 6. Професійне налаштування робочого місця інженера у VS Code: розширення, автоматизація та налагодження.

## Перелік умовних скорочень

- **CRA** (Create React App) — застарілий офіційний генератор шаблонів React-додатків;
- **ESM** (ECMAScript Modules) — офіційний стандарт модульної системи мови JavaScript;
- **HMR** (Hot Module Replacement) — механізм заміни змінених модулів у браузері без перезавантаження сторінки;
- **AST** (Abstract Syntax Tree) — абстрактне синтаксичне дерево програми;
- **LSP** (Language Server Protocol) — стандартизований протокол взаємодії редактора коду з мовними серверами;
- **FSD** (Feature-Sliced Design) — архітектурна методологія проєктування інтерфейсних додатків.

## Вступ

Продуктивність праці та інженерна ефективність фронтенд-розробника безпосередньо залежать від швидкості та стабільності його інструментарію (Developer Tooling). Довгі роки індустрія мирилася з повільним стартом локальних серверів, тривалою збіркою важких бандлів та непрозорими конфігураціями Webpack. Революція Native ES Modules та поява швидких компіляторів на системних мовах (Go, Rust) докорінно змінили ландшафт веб-розробки.

Ця лекція розкриває внутрішню інженерну архітектуру сучасного збирача Vite, аналізує роботу механізму Hot Module Replacement, знайомить зі стандартами масштабованої структуризації кодової бази та демонструє побудову автоматизованого конвеєра якості коду за допомогою сучасного ESLint 9, Prettier та TypeScript.

## 1. Еволюція збирачів JavaScript: криза Webpack і Create React App та перехід до Native ESM

Щоб зрозуміти причини популярності сучасних інструментів, необхідно проаналізувати шлях еволюції бандлерів JavaScript.

### Як функціонували традиційні збирачі (Bundle-based Dev Server)

Історично JavaScript не мав вбудованої модульної системи на рівні браузерів. Для об'єднання сотень файлів використовувалися збирачі першого та другого поколінь (Browserify, а згодом Webpack).

Принцип роботи традиційного dev-сервера на базі Webpack:
- сервер аналізує точку входу (наприклад, `index.js`);
- рекурсивно сканує весь граф залежностей усього проєкту (включно з усіма сторонніми пакетами з `node_modules`);
- завантажує кожен файл через ланцюжок транспайлерів (Babel, CSS-лоадери);
- об'єднує (бандлить) увесь проєкт у єдиний величезний JavaScript-файл у пам'яті;
- лише після повного завершення побудови бандлу локальний сервер стає готовим приймати HTTP-запити від браузера.

Наслідки для великих комерційних систем:
- час холодного старту (Cold Start) проєкту з тисячами компонентів становив від 40 секунд до 3–5 хвилин;
- кожна зміна рядка коду викликала повну або часткову перебудову бандлу, змушуючи інженера чекати оновлення 5–15 секунд при кожному збереженні файлу.

### Чому індустрія відмовилася від Create React App (CRA)

Протягом багатьох років утиліта Create React App була стандартною рекомендацією для новачків. Проте до 2023 року вона перетворилася на джерело серйозних технічних проблем:
- концепція "чорної скриньки" - конфігурація Webpack була прихована всередині пакету `react-scripts`; змінити будь-яке налаштування було неможливо без виконання деструктивної команди `npm run eject`, яка вивалювала сотні рядків непідтримуваного коду конфігурацій;
- повільність компіляції - CRA використовував застарілі версії Babel та Webpack, що споживали гігабайти оперативної пам'яті;
- відставання від стандартів - затримки з підтримкою сучасного TypeScript, нових версій Node.js та сучасних CSS-інструментів;
- офіційне закриття - команда React офіційно припинила підтримку CRA та вилучила рекомендацію щодо його використання з офіційної документації `react.dev`.

### Перехід до Native ES Modules (ESM)

Сучасні веббраузери отримали повну підтримку специфікації ES2015 Modules:
- браузер нативно розуміє конструкцію `<script type="module" src="/src/main.ts">`;
- браузер здатний самостійно інтерпретувати директиви `import` та `export`, запитуючи кожен необхідний модуль окремим HTTP-запитом без попереднього склеювання файлів у монолітний бандл.

Це відкрило шлях для створення кардинально нової архітектури збирачів.

## 2. Архітектура збирача Vite: синергія Native ESM, esbuild та Rollup

**Vite** (французькою "швидкий", вимовляється як "віт") був створений Еваном Ю (автором Vue.js) і швидко став стандартом де-факто для всієї екосистеми фронтенду, включно з React, Svelte та Solid.

Фундаментальна ідея Vite полягає у чіткому розділенні модулів додатку на дві принципово різні категорії:
- сторонні залежності (Dependencies) - бібліотеки, які рідко змінюються під час розробки (React, React DOM, Lucide, Lodash);
- власний вихідний код (Source Code) - файли проєкту (`.tsx`, `.ts`, `.css`), які інженер постійно редагує.

```
Традиційний Webpack:
[Весь код + Залежності] ---> [Повний бандлінг у пам'яті] ---> [Старт Dev-сервера]

Сучасний Vite:
1. Залежності ---> [Pre-bundling через esbuild (Go)] (мілісекунди)
2. Dev-сервер стартує НЕГАЙНО
3. Браузер запитує App.tsx ---> [Vite транспілює On-Demand] ---> Відповідь браузеру
```

### Попередня оптимізація залежностей за допомогою esbuild

Зовнішні бібліотеки з `node_modules` можуть містити тисячі дрібних внутрішніх файлів або поставлятися у застарілому форматі CommonJS (`module.exports`). Якщо змусити браузер запитувати їх окремо, виникне "мережевий шторм" із сотень паралельних запитів.

Vite вирішує це за допомогою попередньої оптимізації (Pre-bundling):
- залежності скануються та конвертуються в єдині оптимізовані ESM-модулі;
- для цього використовується компілятор **esbuild**, написаний мовою Go;
- завдяки паралельній обробці в пам'яті та нативній компіляції Go, esbuild працює у **10–100 разів швидше** за будь-які аналоги на базі JavaScript/Node.js;
- попередня збірка залежностей для середнього проєкту займає лічені частки секунди.

### Обробка вихідного коду за вимогою (On-Demand Compilation)

Вихідний код вашого проєкту у режимі розробки взагалі не збирається в бандл:
- dev-сервер Vite стартує майже миттєво (за 100–300 мс), незалежно від того, наскільки великим є проєкт;
- коли ви відкриваєте сторінку, браузер читає `index.html`, бачить тег `<script type="module" src="/src/main.tsx">` і надсилає звичайний HTTP GET запит до сервера Vite;
- сервер перехоплює запит, миттєво транспілює конкретний файл `main.tsx` у нативний JavaScript і віддає його браузеру;
- якщо у вашому проєкті 50 сторінок, а ви відкрили лише `/login`, Vite транспілює лише ті модулі, які потрібні для сторінки входу. Решта 49 сторінок не навантажують процесор.

### Чому Rollup використовується для Production-збірки?

Виникає логічне запитання: якщо Native ESM такий зручний, чому не віддавати тисячі окремих файлів і на реальному веб-сервері у продакшні?

Причини обов'язкового бандлінгу для Production:
- мережева затримка (Network Latency) - навіть за протоколу HTTP/2 передача сотень дрібних файлів створює каскади залежностей (Request Waterfalls);
- Tree Shaking - для мінімізації трафіку мобільних користувачів необхідно видалити невикористаний мертвий код з бібліотек, що можливо лише при комплексному статичному аналізі всього графа проєкту;
- оптимізація кешування - розбиття коду на оптимізовані шматки (Chunk Splitting) із геш-сумами в іменах (`app.a8f9c2.js`).

Для виробничої збірки (`npm run build`) Vite використовує перевірений часом збирач **Rollup**, який забезпечує найкращу оптимізацію розміру бандлу в індустрії.

## 3. Механізм гарячої заміни модулів (HMR)

Однією з найвизначніших переваг сучасної розробки є **Hot Module Replacement (HMR)** — протокол заміни модифікованого коду на льоту без повного перезавантаження веб-сторінки (`window.location.reload()`).

### Недоліки повного перезавантаження сторінки (Live Reload)

У класичних середовищах кожне збереження файлу викликало оновлення сторінки в браузері:
- скидався весь поточний стан користувача: відкриті модальні вікна, введені текстові поля у формі реєстрації, обрані вкладки;
- розробник був змушений щоразу повторювати 4–5 кліків мишею, щоб дістатися до досліджуваного стану інтерфейсу;
- це суттєво уповільнювало ітеративний процес верстки та налагодження компонентів.

### React Fast Refresh: оновлення зі збереженням стану

Сучасний HMR у Vite реалізується через офіційний плагін `@vitejs/plugin-react` на базі технології **React Fast Refresh**:
- коли інженер змінює JSX-розмітку або CSS-стилі функціонального компонента, сервер надсилає дельту змін через постійне WebSocket-з'єднання;
- клієнтський рантайм замінює реалізацію функції компонента в дереві Virtual DOM;
- React викликає повторний рендеринг зміненого вузла, **повністю зберігаючи значення хуків `useState` та `useReducer`**;
- швидкість реакції інтерфейсу становить від 10 до 50 мілісекунд і сприймається людиною як абсолютно миттєва.

Обмеження збереження стану Fast Refresh:
- якщо компонент експортує звичайні змінні чи константи, які не є компонентами React, файл змушений перезавантажитися повністю; саме тому лінтер ESLint містить правило `react-refresh/only-export-components`;
- якщо редагується кастомний хук, скидається стан усіх компонентів, які використовують цей хук.

## 4. Організація архітектури фронтенд-проєкту

Правильна структура каталогів проєкту визначає, чи зможе команда підтримувати кодову базу через пів року активної розробки, чи вона перетвориться на хаотичне нагромадження взаємопов'язаних файлів.

### Класичний шаровий підхід (Layer-Based Architecture)

Традиційний підхід групує файли за їхнім технічним типом:

```
src/
|-- components/
|   |-- Header.tsx
|   |-- ProductCard.tsx
|   |-- CartItem.tsx
|-- hooks/
|   |-- useAuth.ts
|   |-- useCart.ts
|-- services/
|   |-- api.ts
|-- types/
|   |-- index.ts
```

Проблеми шарового підходу на великих проєктах:
- висока зачепленість (High Coupling) - щоб зрозуміти, як працює модуль кошика, розробник має одночасно тримати відкритими 5 папок у різних кінцях дерева файлів;
- ризик випадкових побічних ефектів - компоненти починають імпортувати чужі хуки та утиліти без будь-яких архітектурних меж;
- складність видалення - якщо бізнес вирішує видалити функціонал "Відгуки про товари", інженер змушений вручну вишукувати розрізнені файли по всіх шарах проєкту.

### Сучасний модульний підхід (Feature-Driven Architecture)

Професійна розробка групує файли навколо **бізнес-функціоналу (Features)**, залишаючи загальні речі на спільному рівні:

```
src/
|-- components/common/   # Базові UI-елементи без бізнес-логіки (Button, Input, Modal)
|-- layouts/             # Шаблони сторінок (Header, Sidebar, Footer, Container)
|-- features/            # Ізольовані бізнес-модулі
|   |-- auth/            # Модуль авторизації (форми входу, хук useAuth, типи User)
|   |-- catalog/         # Каталог товарів (ProductCard, фільтри, запити)
|   |-- cart/            # Кошик замовлень (компоненти, стейт кошика)
|-- types/               # Загальносистемні типи даних
|-- utils/               # Чисті допоміжні функції (форматування дат, цін)
```

Принципи модульного проєктування:
- автономність фічі - модуль `features/catalog` містить усе необхідне для своєї роботи;
- публічний інтерфейс (Public API через `index.ts`) - фіча експортує назовні лише ті компоненти, які дозволено використовувати іншим частинам системи;
- просте видалення та рефакторинг - для вилучення фічі достатньо видалити одну папку.

## 5. Автоматизований контроль якості коду: ESLint 9, Prettier та Biome

У професійній команді неприпустимо витрачати час на код-рев'ю на обговорення того, де ставити пробіли, коми чи як іменувати змінні. Ці задачі мають виконуватися на 100% автоматизовано.

### Розподіл обов'язків: Лінтер проти Форматера

Інструменти контролю якості вирішують дві принципово різні інженерні задачі:
- **Форматер (Prettier)** відповідає за **стиль оформлення (Formatting Rules)**:
  - довжина рядка (Print Width);
  - подвійні чи одинарні лапки;
  - використання крапок з комою;
  - розмір відступів (2 чи 4 пробіли).
- **Лінтер (ESLint)** відповідає за **якість і логічну коректність коду (Code-Quality Rules)**:
  - виявлення невикористаних змінних та "мертвого" коду;
  - захист від використання небезпечного типу `any` в TypeScript;
  - дотримання суворих правил хуків React (заборона виклику хуків всередині умов або циклів);
  - запобігання втраті асинхронних промісів (Floating Promises).

### Революція ESLint 9: Flat Config

Починаючи з версії ESLint 9, застарілий формат конфігурації `.eslintrc.*` було повністю замінено на єдиний стандарт **Flat Config** (`eslint.config.js`):
- відмова від неявного успадкування - раніше правила могли непередбачувано перезаписуватися через вкладені файли `.eslintrc`; тепер усе налаштування прозоро визначається єдиним JavaScript-масивом;
- нативна підтримка ESM - імпорт плагінів виконується стандартними інструкціями `import` замість магічних рядків;
- гнучкість фільтрації - легке призначення різних правил для вихідного коду, конфігурацій збірки чи тестів за допомогою властивості `files: ['**/*.ts', '**/*.tsx']`.

### Усунення конфліктів між ESLint та Prettier

Якщо правила лінтера та форматера перетинаються (наприклад, ESLint вимагає крапку з комою, а Prettier налаштований її видаляти), виникає нескінченний конфлікт.

Стандартне рішення індустрії:
- використання конфігурації `eslint-config-prettier`;
- вона повністю вимикає в ESLint усі правила, які стосуються візуального форматування, залишаючи лінтеру виключно перевірку логіки та безпеки;
- форматуванням коду займається виключно Prettier.

### Нове покоління: Інструмент Biome

Створений як альтернатива всій екосистемі JS-тулінгу, **Biome** (написаний мовою Rust) об'єднує функції лінтера та форматера в одному бінарному файлі:
- забезпечує швидкість обробки до 30 разів вищу за ESLint на великих кодових базах;
- гарантує повну відсутність конфліктів правил;
- проте для проєктів на React 19 та специфічних бібліотек зв'язка ESLint + Prettier наразі залишається більш поширеною через величезну кількість готових екосистемних плагінів.

## 6. Професійне налаштування робочого місця інженера у VS Code

Середовище розробки Visual Studio Code є найпопулярнішим редактором для React-розробки. Проте без належної автоматизації воно втрачає значну частину своєї сили.

### Обов'язкові розширення (Extensions)

- **ESLint** (від Microsoft) - візуалізує підкресленням логічні помилки коду в реальному часі безпосередньо у редакторі;
- **Prettier - Code formatter** (від Prettier) - автоматично приводить відкритий файл до єдиного командного стилю;
- **Tailwind CSS IntelliSense** - забезпечує автодоповнення класів, попередній перегляд кольорів та валідацію CSS;
- **Error Lens** - виводить текст помилок і попереджень безпосередньо в кінці проблемного рядка коду, позбавляючи потреби наводити курсор миші.

### Командна стандартизація через `.vscode`

Щоб кожен член команди мав однаковий досвід і налаштування без необхідності ручного конфігурування, у репозиторій додається директорія `.vscode`.

Файл `.vscode/settings.json` для автоматичного форматування:

```json
{
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.formatOnSave": true,
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  },
  "typescript.tsdk": "node_modules/typescript/lib"
}
```

Файл `.vscode/extensions.json` для рекомендацій команді:

```json
{
  "recommendations": [
    "dbaeumer.vscode-eslint",
    "esbenp.prettier-vscode",
    "bradlc.vscode-tailwindcss",
    "usernamehw.errorlens"
  ]
}
```

## Висновки

- зміна парадигми збірки - перехід від важкого попереднього бандлінгу (Webpack) до комбінації Native ESM та швидкого компілятора esbuild у Vite забезпечив миттєвий старт локального середовища розробки;
- архітектурна роль Rollup - використання Rollup для продакшн-збірок дозволяє усунути мережеві затримки на клієнті через оптимізоване розділення коду (Chunking) та очищення від мертвого коду (Tree-Shaking);
- продуктивність розробника через HMR - технологія React Fast Refresh замінює змінений код у браузері за лічені мілісекунди зі збереженням поточного стану форм і хуків;
- масштабованість архітектури - модульне зонування (Feature-Driven Structure) усуває зачепленість коду та дозволяє безболісно розвивати окремі бізнес-фічі;
- чітке розділення зон контролю - форматер Prettier відповідає виключно за візуальний стиль, тоді як ESLint 9 (Flat Config) контролює якість, типізацію та логічну безпеку компонентів.

## Запитання для самоперевірки

- чому традиційні збирачі на кшталт Webpack суттєво втрачають у швидкості холодного старту зі зростанням кодової бази проєкту;
- як саме Vite використовує компілятор esbuild на етапі запуску dev-сервера і в чому полягає його перевага над транспайлерами на базі Node.js;
- поясніть механізм роботи React Fast Refresh та назвіть сценарії, коли збереження стану компонента під час HMR стає неможливим;
- у чому полягають недоліки класичного шарового підходу (Layer-based) в організації файлів проєкту на масштабі великої системи;
- яка принципова різниця існує між завданнями, що вирішуються лінтером (ESLint) та форматером коду (Prettier);
- які переваги надає використання нового формату конфігурації Flat Config в ESLint 9 у порівнянні з класичним `.eslintrc`?
