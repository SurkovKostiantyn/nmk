# Лекція 1 (2 години). Еволюція веб-технологій: від імперативного DOM до декларативного React

## План лекції

- 1. Еволюція веб-архітектури: від класичних MPA до SPA та сучасної архітектури островів (Islands Architecture);
- 2. Імперативний підхід проти декларативного: криза прямої маніпуляції DOM та обмеження ранніх MVC-систем;
- 3. Декларативна парадигма React: формула `UI = f(state)`, компонент як чиста функція та односпрямований потік даних;
- 4. Архітектура Virtual DOM: внутрішня будова та оптимізація браузерного рендерингу (Reflow і Repaint);
- 5. Механізм узгодження (Reconciliation): евристичний алгоритм Diffing та архітектура волокон React Fiber;
- 6. Сучасний стан екосистеми React 19: перехід від клієнтської бібліотеки до уніфікованої платформи.

## Перелік умовних скорочень

- **API** (Application Programming Interface) — інтерфейс прикладного програмування;
- **DOM** (Document Object Model) — об'єктна модель документа у браузері;
- **MPA** (Multi-Page Application) — багатосторінковий веб-застосунок;
- **SPA** (Single Page Application) — односторінковий веб-застосунок;
- **vDOM** (Virtual Document Object Model) — віртуальна об'єктна модель документа;
- **UI** (User Interface) — користувацький інтерфейс;
- **RSC** (React Server Components) — серверні компоненти React;
- **SSR** (Server-Side Rendering) — серверне формування HTML-розмітки;
- **CSR** (Client-Side Rendering) — клієнтський рендеринг у браузері.

## Вступ

Для формування інженерного мислення сучасного фронтенд-розробника недостатньо просто вивчити синтаксис хуків або оголошення компонентів. Справжня інженерна експертиза вимагає глибокого розуміння передумов створення бібліотеки: яку саме фундаментальну проблему веб-індустрії вирішує React, чому пряма взаємодія з DOM API виявилася глухим кутом для складних систем та як алгоритми узгодження забезпечують швидкість і стабільність інтерфейсів. 

У цій лекції розглядається еволюція веб-архітектур, аналізуються відмінності між імперативним та декларативним підходами, розкривається внутрішня будова Virtual DOM та механізмів React Fiber, а також окреслюється сучасний ландшафт React 19.

## 1. Еволюція веб-архітектури: від MPA до SPA та архітектури островів

Розвиток веб-технологій за останні три десятиліття пройшов шлях від відображення статичних документів до розподілених реактивних систем.

### Класичні багатосторінкові додатки (MPA — Multi-Page Applications)

В епоху зародження вебу (Web 1.0) браузер використовувався як інструмент перегляду гіпертекстових файлів. Архітектурний шаблон функціонував за прямою схемою:
- перехід користувача за посиланням або відправка форми генерували повноцінний HTTP-запит до веб-сервера;
- бекенд (на мовах Perl, PHP, Java або Ruby) заново збирав усю HTML-сторінку разом зі шапкою, контентом і підвалом;
- браузер повністю знищував попередню сторінку, скидав екран у білий колір і заново завантажував, парсив і малював нове дерево документа;
- скрипти на JavaScript виконували виключно примітивну валідацію полів форм або найпростіші візуальні анімації (падаючий сніг, випадаючі меню).

Головний недолік MPA полягав у повільному зворотному зв'язку: кожна незначна дія вимагала перезавантаження всього контексту сторінки.

### Революція Web 2.0 та поява SPA (Single Page Applications)

Поява об'єкта `XMLHttpRequest` (а згодом стандарту Fetch API) дозволила реалізувати концепцію AJAX — асинхронний обмін даними з сервером без перезавантаження сторінки. Це призвело до виникнення парадигми односторінкових додатків (Single Page Applications — SPA):
- браузер завантажує єдиний мінімальний HTML-контейнер (`<div id="root"></div>`) та об'ємний бандл JavaScript-коду;
- уся подальша маршрутизація, побудова інтерфейсу та управління даними переноситься у браузер клієнта (Client-Side Rendering — CSR);
- веб-сервер перетворюється на постачальника сирих даних (REST API або GraphQL у форматі JSON).

SPA забезпечили плавний, безшовний досвід користувача (User Experience), аналогічний десктопним або мобільним програмам. Проте розвиток SPA приніс новий комплекс інженерних викликів:
- надмірний розмір початкового бандлу - повільне перше завантаження на мобільних пристроях і слабких мережах;
- ускладнення SEO - пошукові роботи не завжди ефективно виконували клієнтський JavaScript для індексації контенту;
- високе навантаження на процесор клієнта - слабкі пристрої перегрівалися під час обробки важких скриптів розмітки.

### Сучасна парадигма: Архітектура островів (Islands Architecture)

Сучасний веб рухається до гібридних рішень, що поєднують переваги MPA та SPA:
- статичний каркас документа формується на сервері (Server-Side Rendering або Static Site Generation) і миттєво віддається браузеру у вигляді чистого швидкого HTML;
- динамічні інтерактивні модулі (кошик замовлень, карусель, поле пошуку) підключаються як ізольовані інтерактивні "острови" (Islands), які завантажують JavaScript лише за потреби;
- саме цю філософію реалізують сучасні метафреймворки (Next.js з App Router, Astro) за підтримки архітектури React Server Components (RSC).

## 2. Імперативний підхід проти декларативного: криза прямої маніпуляції DOM

Щоб оцінити переваги декларативності React, необхідно проаналізувати проблеми традиційного імперативного підходу.

### Імперативна модель (Vanilla JS, jQuery)

Імперативне програмування зосереджується на покроковій інструкції виконання: розробник детально описує **ЯК** саме система повинна дійти до бажаного результату.

Приклад імперативного коду для лічильника завдань (Todo List):

```javascript
// Імперативний код: покрокові інструкції маніпуляцій з DOM
const input = document.getElementById('todo-input');
const addButton = document.getElementById('add-button');
const list = document.getElementById('todo-list');
const countDisplay = document.getElementById('todo-count');

let count = 0;

addButton.addEventListener('click', () => {
  const text = input.value.trim();
  if (!text) return;

  // 1. Створення елемента списку
  const li = document.createElement('li');
  li.textContent = text;

  // 2. Створення кнопки видалення
  const deleteBtn = document.createElement('button');
  deleteBtn.textContent = 'Видалити';
  deleteBtn.addEventListener('click', () => {
    list.removeChild(li);
    count--;
    countDisplay.textContent = `Всього завдань: ${count}`;
  });

  // 3. Збірка елементів та додавання в DOM
  li.appendChild(deleteBtn);
  list.appendChild(li);

  // 4. Ручне оновлення пов'язаних станів
  count++;
  countDisplay.textContent = `Всього завдань: ${count}`;
  input.value = '';
});
```

Уразливості та недоліки імперативного підходу:
- розпорошений стан (Distributed State) - актуальні дані програми зберігаються безпосередньо в структурі DOM-дерева (у текстових вузлах, атрибутах, класах елементів);
- крихкість зв'язків - зміна одного селектора у верстці ламає весь JavaScript-код пошуку елементів;
- ручна синхронізація - при кожній зміні даних розробник зобов'язаний вручну знайти всі елементи на сторінці, які залежать від цієї зміни, та віддати команди на їх перезапис; якщо одне місце забуто, інтерфейс стає несинхронізованим із реальними даними.

### Криза двостороннього зв'язування даних (Two-Way Data Binding) в архітектурах MVC

Спроби перенести класичний патерн MVC (Model-View-Controller) або MVVM у браузер (Backbone.js, AngularJS 1.x) запровадили механізм Two-Way Data Binding (двостороннє зв'язування даних). Зміна в моделі автоматично змінювала вигляд, а зміна у вигляді змінювала модель.

У невеликих додатках це виглядало зручно, але на масштабах великих систем (таких як інтерфейс Facebook) виникла проблема "каскадних хвиль оновлень":
- зміна однієї моделі викликала оновлення представлення;
- представлення тригерило іншу модель;
- починався ланцюжок непередбачуваних оновлень, який було вкрай важко відстежити та налагоджувати;
- класичний симптом проблеми: лічильник нових повідомлень на панелі показував "1", але у випадаючому списку повідомлення було відсутнє, оскільки дві моделі оновилися несинхронно.

## 3. Декларативна парадигма React: `UI = f(state)`

React запропонував радикальний вихід із кризи: повну відмову від ручних маніпуляцій з DOM та перехід до чистої декларативної моделі.

### Декларативний підхід

Декларативне програмування зосереджується на тому, **ЩО** має відображатися, а не на тому, як це створити:
- розробник описує кінцевий вигляд інтерфейсу для кожного можливого стану даних;
- як саме трансформувати поточний HTML у новий вигляд — турбота бібліотеки React;
- розробник взагалі не звертається до `document.createElement`, `appendChild` чи `removeChild`.

### Фундаментальна формула React: `UI = f(state)`

У центрі архітектури React лежить проста математична концепція:
$$\text{UI} = f(\text{state})$$

Де:
- `state` — поточний стан даних системи у пам'яті (об'єкти, масиви, рядки);
- `f` — ваш компонент (функція перетворення даних у вигляд);
- `UI` — згенерований користувацький інтерфейс, що відображається на екрані.

Якщо дані стану змінюються (`state'`), React повторно викликає функцію `f(state')` та самостійно оновлює екран.

Порівняйте декларативний аналог того самого лічильника в React:

```jsx
import { useState } from 'react';

export function TodoApp() {
  const [todos, setTodos] = useState([]);
  const [text, setText] = useState('');

  const handleAdd = () => {
    if (!text.trim()) return;
    setTodos([...todos, { id: crypto.randomUUID(), title: text }]);
    setText('');
  };

  const handleDelete = (id) => {
    setTodos(todos.filter((todo) => todo.id !== id));
  };

  return (
    <div>
      <input value={text} onChange={(e) => setText(e.target.value)} />
      <button onClick={handleAdd}>Додати</button>

      <p>Всього завдань: {todos.length}</p>

      <ul>
        {todos.map((todo) => (
          <li key={todo.id}>
            {todo.title}
            <button onClick={() => handleDelete(todo.id)}>Видалити</button>
          </li>
        ))}
      </ul>
    </div>
  );
}
```

Зверніть увагу:
- відсутні будь-які інструкції створення, видалення чи пошуку HTML-вузлів;
- кількість елементів `todos.length` завжди гарантовано синхронізована зі списком завдань;
- інтерфейс є передбачуваною чистою проєкцією поточного стану масиву `todos`.

### Принцип чистоти компонентів (Pure Functions) та односпрямований потік даних

Для гарантії стабільності React встановлює два суворих правила:
- компонент повинен бути чистою функцією - для однакових вхідних параметрів (пропсів і стану) компонент зобов'язаний повертати однаковий JSX і не змінювати глобальні змінні чи об'єкти поза своїми межами;
- односпрямований потік даних (One-Way Data Flow) - дані завжди рухаються виключно згори донизу (від батьківського компонента до дочірнього через `props`), а сповіщення про події передаються знизу вгору через функції зворотного виклику (Callbacks). Жодних прихованих зворотних зв'язків не існує.

## 4. Архітектура Virtual DOM: внутрішня будова та вартість операцій над DOM

Чому не можна просто повністю видаляти весь реальний HTML сторінки та генерувати його наново при кожній зміні стану? Відповідь криється в анатомії веббраузерів.

### Чому реальний DOM повільний?

Об'єктна модель документа (DOM) у браузері реалізована мовою C++ рушієм браузера (наприклад, Blink у Chromium або Gecko у Firefox). JavaScript взаємодіє з нею через спеціальний міст (Bridge API). 

Операції у внутрішній пам'яті JavaScript надзвичайно швидкі — сучасний V8 виконує мільйони операцій на мілісекунду. Але як тільки скрипт викликає зміну властивості реального DOM-вузла, браузер змушений запустити складний ланцюжок графічних операцій:
- перерахунок каскадних стилів (Recalculate Styles) - визначення CSS-правил для кожного зміненого елемента та його нащадків;
- перерахунок геометричного макета (Layout або Reflow) - обчислення точних піксельних координат (`x`, `y`, ширина, висота) кожного елемента на сторінці;
- розбиття на графічні шари та малювання пікселів (Paint) - заповнення растрової пам'яті кольорами, межами, текстом;
- композитинг шарів (Compositing) - зведення готових шарів у відеопам'яті GPU для фінального виведення на екран.

Найдорожчим процесом є **Reflow**: зміна ширини одного елемента на початку документа змушує браузер перерахувати положення тисяч елементів нижче за ним. Часті прямі звернення до DOM блокують рендеринг і призводять до просідання частоти кадрів нижче критичних 60 FPS (явище "UI Jank").

### Що таке Virtual DOM?

Virtual DOM (vDOM) — це легковажна копія реального DOM у вигляді звичайних невагомих JavaScript-об'єктів, яка повністю зберігається в оперативній пам'яті.

Коли ви пишете JSX:

```jsx
const element = <button className="btn-primary">Зберегти</button>;
```

Транспілятор перетворює його на простий JavaScript-об'єкт наступного вигляду:

```javascript
{
  type: 'button',
  props: {
    className: 'btn-primary',
    children: 'Зберегти'
  },
  key: null,
  ref: null
}
```

Створення, копіювання чи порівняння тисяч таких об'єктів у пам'яті JavaScript триває частки мілісекунди і взагалі не чіпає важкий графічний конвеєр браузера.

### Три фази життєвого циклу рендерингу React

Процес оновлення інтерфейсу в React чітко розмежований на три фази:
- фаза рендерингу (Render Phase) - виконання функцій-компонентів, отримання нового дерева об'єктів Virtual DOM у пам'яті;
- фаза узгодження (Reconciliation Phase) - порівняння нового дерева Virtual DOM із попереднім деревом, обчислення різниці (Diff);
- фаза фіксації (Commit Phase) - бібліотека `react-dom` бере обчислений мінімальний список змін і точково застосовує їх до реального браузерного DOM (наприклад, оновлюючи значення лише одного атрибута або одного текстового вузла).

Завдяки цьому важкі операції браузера зводяться до абсолютно необхідного мінімуму.

## 5. Механізм узгодження (Reconciliation): Diffing та React Fiber

Ключовим серцем продуктивності React є алгоритм, який порівнює два дерева об'єктів Virtual DOM.

### Проблема алгоритмічної складності

Класичні академічні алгоритми пошуку мінімальної кількості операцій для перетворення одного дерева на інше мають обчислювальну складність порядка $O(n^3)$, де $n$ — кількість вузлів у дереві.
Якщо на сторінці знаходиться лише 1000 елементів:
$$n^3 = 1000^3 = 1\,000\,000\,000\text{ операцій!}$$
Такий розрахунок тривав би секунди і повністю заморожував роботу інтерфейсу.

### Евристичний алгоритм Diffing у React ($O(n)$)

Команда інженерів React застосувала евристичний підхід, що спирається на два практичні припущення про природу веб-інтерфейсів, скоротивши складність алгоритму до лінійної $O(n)$:

- евристика 1 (різні типи елементів породжують різні піддерева) - якщо кореневий тег елемента змінився (наприклад, був `<div>`, а став `<section>`), React не витрачає ресурси на поглиблене порівняння дочірніх вузлів; він повністю демонтує (Unmount) старе піддерево разом зі станом і створює нове з нуля;
- евристика 2 (однакові типи елементів зберігають DOM-вузол) - якщо тип елемента зберігся (наприклад, `<div className="before" title="stuff" />` змінився на `<div className="after" title="stuff" />`), React зберігає існуючий реальний вузол DOM у браузері і точково модифікує лише змінений CSS-клас, не торкаючись інших властивостей;
- евристика 3 (стабільні ключі для колекцій — Keys) - при рендерингу списків за допомогою пропу `key` React відстежує рух елементів; якщо в початок списку з 1000 елементів вставляється 1 новий, React завдяки унікальним ключам розуміє, що старі 1000 елементів не змінилися, а лише змістилися, і виконує одну операцію вставки нового вузла замість перемальовування всього списку.

### Еволюція внутрішнього рушія: від Stack Reconciler до React Fiber

До версії React 16 процес узгодження виконувався синхронно за допомогою так званого **Stack Reconciler**:
- рушій викликав рекурсивний обхід дерева компонентів через стек викликів JavaScript;
- поки рекурсія не завершиться, головний потік браузера (Main Thread) був повністю заблокований;
- якщо рендеринг великого дерева займав більше 16 мс, браузер пропускав кадр анімації (Frame Drop), викликаючи смикання інтерфейсу та ігнорування кліків користувача.

У версії React 16 архітектуру було фундаментально переписано з нуля — з'явився рушій **React Fiber**:
- одиницею роботи стало спеціальне "волокно" (Fiber) — JavaScript-об'єкт, що містить посилання на компонент, його стан, пропси, батька, сусіда (sibling) та першу дочірню ноду;
- дерево перетворилося на зв'язний список волокон (Singly Linked List of Fiber Nodes);
- це дозволило розбити важку роботу рендерингу на мікро-кванти часу (Time Slicing);
- рушій Fiber отримав здатність призупиняти обчислення, передавати управління браузеру для обробки натискань клавіш чи анімацій, а потім відновлювати або взагалі скасовувати застарілу роботу;
- архітектура Fiber заклала фундамент для сучасного багатозадачного режиму — **Concurrent React**.

## 6. Сучасний стан екосистеми React 19

З моменту релізу в 2013 році React еволюціонував від невеликої бібліотеки рівня представлення (View Layer) до повномасштабної індустріальної платформи веб-інженерії.

### React як архітектурна основа сучасного вебу

Сьогодні React не обмежується клієнтським рендерингом:
- розмиття кордонів між клієнтом та сервером - концепція React Server Components (RSC) дозволяє компонентам виконуватися безпосередньо на Node.js-сервері, завантажувати дані безпосередньо з баз даних і передавати на клієнт 0 байтів зайвого JavaScript-коду;
- вбудована робота з формами та мутаціями - стандартизація Form Actions у React 19 позбавляє від необхідності ручного написання обробників `event.preventDefault()` та тривіальних станів завантаження;
- революція компілятора (React Compiler / React Forget) - нове покоління інструментів автоматично аналізує граф залежностей коду під час збірки проєкту і виконує мемоїзацію на рівні бінарного дерева, усуваючи потребу в ручному використанні хуків `useMemo` та `useCallback`.

### Структура сучасної інженерної екосистеми React

Сучасний професійний стек навколо React 19 включає перевірені інструменти індустрії:
- збирачі нового покоління - відмова від застарілих Webpack/CRA на користь швидкого Vite на базі Native ESM та esbuild;
- сувора статична типізація - обов'язкове використання TypeScript для гарантії безпеки інтерфейсів, пропсів і стану на етапі написання коду;
- утилітарна стилізація та дизайн-системи - домінування Tailwind CSS у поєднанні з headless-примітивами Radix UI та shadcn/ui;
- чітке розділення стану - винесення клієнтського UI-стану в легковажні сховища (Zustand), а серверного асинхронного стану — у спеціалізовані менеджери кешування (TanStack Query);
- надійна інфраструктура тестування - швидкі юніт-тести з Vitest, поведінкове тестування компонентів з React Testing Library та перехоплення мережевих запитів через Mock Service Worker (MSW).

## Висновки

- еволюція архітектури - веб пройшов шлях від важких серверних MPA до односторінкових SPA, а сьогодні об'єднує їхні сильні сторони в гібридній та острівній архітектурі (Islands Architecture);
- подолання кризи імперативності - пряма маніпуляція з DOM-деревом ускладнює масштабування через розпорошення стану та ризики каскадних розсинхронізацій;
- декларативна філософія - React реалізує принцип `UI = f(state)`, де інтерфейс є передбачуваною проєкцією стану, а компоненти проєктуються як чисті функції з односпрямованим потоком даних;
- швидкість Virtual DOM - операції над об'єктами в пам'яті дозволяють виключити надлишкові та дорогі цикли Reflow і Repaint браузера;
- алгоритм Reconciliation - завдяки евристикам Diffing складність оптимізовано до лінійної $O(n)$, а архітектура React Fiber забезпечує пріоритезацію завдань без блокування інтерфейсу;
- екосистема React 19 - бібліотека виросла в цілісну архітектурну екосистему з підтримкою Server Components, автоматичної компіляторної оптимізації та типобезпечного інструментарію.

## Запитання для самоперевірки

- які ключові технічні недоліки прямої маніпуляції DOM-деревом за допомогою Vanilla JS або jQuery призвели до створення React;
- у чому полягає фундаментальна різниця між імперативною та декларативною моделями опису користувацького інтерфейсу;
- поясніть математичний та інженерний зміст формули `UI = f(state)` в контексті React;
- чому операції зміни властивостей реального DOM у браузері є ресурсомісткими і що таке процеси Reflow та Repaint;
- які два основні припущення (евристики) дозволили інженерам React скоротити алгоритмічну складність узгодження з $O(n^3)$ до $O(n)$;
- чим архітектура рушія React Fiber відрізняється від застарілого Stack Reconciler і як вона запобігає зависанню інтерфейсу?
